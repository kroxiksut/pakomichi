# ADR-026 — 0.1 support matrix after research

**English** · [Русский](../../ru/decisions/ADR-026.md)

**Status:** accepted by the project owner on 2026-10-20. ADR-014 remains in force; this decision narrows the platforms that 0.1 may claim and supersedes nothing. `testing/release-gate.md` and `testing/matrix.md` follow it.  
**Date:** 2026-10-20.

## Context

ADR-014 sets the 0.1 scope as DEB/APT and RPM/DNF4/DNF5 in tested environments, and `testing/matrix.md` requires that the alpha lists only tested combinations. R-001, R-002, R-004, R-005, and R-006 are complete; R-003 is complete only for its read-only part. The research ran on different platform sets, so no platform has yet been covered by every study, and none by Pakomichi itself.

## Decision

1. **Admission rule for a 0.1 claim.** A distribution build may be listed as supported in 0.1 only after, on that exact build: the R-001 selection matrix; for RPM, the R-002 matrix; the delivery subset of R-004 (socket activation, generations with native clients, third-party repositories and removal) on a VM with real systemd and the distribution's default SELinux or AppArmor mode; the SQLite version recorded and the migration tests passed (ADR-020); and E2E-01 or E2E-02 plus the N-tests that apply, run with Pakomichi's own package. For AlmaLinux and Fedora, the delivery subset and the E2E run take place on a VM with SELinux in enforcing mode before support is claimed.
2. **First targets.** The first 0.1 targets are Debian 12, AlmaLinux 9, Fedora 44, and Astra Linux 1.8.6 at `base(orel)` (ordinary update command `apt-get dist-upgrade`, ADR-022). Debian 12, AlmaLinux 9, and Fedora 44 already have the research evidence of R-001, R-004, and (for RPM) R-002. Astra Linux 1.8.6 at `base(orel)` has the R-001 evidence but only the power-loss part of R-004, so a delivery run (the R-004 subset of point 1) on that exact build is required before it is claimed. Every first target still needs everything in point 1 that the table marks as missing.
3. **Conditional and later targets.** Debian 13, Ubuntu 24.04, Ubuntu 26.04, and AlmaLinux 10 may be added in 0.1 only when point 1 is completed for them. RED OS is a later target: it is not among the first targets, and RED OS 8 or 7.3 is claimed only when point 1 is completed for that build. Otherwise these platforms are listed as "not tested", not as supported.
4. **Not claimed in 0.1.** Astra Linux with the closed software environment (ADR-025); Astra Linux 1.7 at any level (the owner considers it outdated, 2026-10-21; its R-001 and SQLite evidence stays on record); RED OS 7.3 until its SQLite version is checked (ADR-020; Astra Linux 1.7.6 was checked on 2026-10-20); ALT Linux; arm64 and aarch64.
5. **Capability claims.** Strict and Attested are claimed only after R-003 is complete and the production verifier is selected (ADR-005, ADR-017 point 9). The RPM Attested exception waits for R-003 (ADR-023). The release notes state the R-005 finding that only a minority of the sampled repositories publish Strict or Attested evidence. ADR-027 admits the Pinned level in 0.1 only behind explicit per-source consent and manual approval of every release; the Signed level is deferred to 0.2.
6. **Release gate.** `testing/release-gate.md` and `testing/matrix.md` are updated in both languages with points 1–5.

## Alternatives and reasons for rejection

- **Claim every platform on which R-001 ran:** R-001 tests the package manager's decisions only, not delivery, signatures, or Pakomichi.
- **Claim only AlmaLinux 9:** the only platform with every study, but it leaves 0.1 without an APT platform.
- **Infer DNF builds from upstream DNF:** R-001 showed that RED OS builds differ.

## Consequences

The research effort for the first targets is a VM run with SELinux or AppArmor enforcing and Pakomichi's own packages, plus the delivery run on Astra Linux 1.8.6 at `base(orel)`; every additional platform adds the missing studies of its row. The number of supported platforms in 0.1 may be smaller than the R-001 list, which `release-gate.md` explicitly allows.
