# ADR-033 — Local API for clients other than the CLI

**English** · [Русский](../../ru/decisions/ADR-033.md)

**Status:** accepted by the project owner on 2026-10-23 as the direction. The limits and timeouts in points 3, 4 and 7 are starting values; the tests of P2-013c check them, and a change is recorded with its test. It refines ADR-029 (points 2, 5 and 8) and supersedes nothing: with the defaults below, the behaviour of ADR-029 does not change.  
**Date:** 2026-10-23.

## Context

A graphical interface is outside 0.1 (ADR-014, `product/scope-0.1.md`), and adding one needs its own decision. The local API it would use is being built now (ADR-029, P2-013): if that API fits only the CLI, a GUI later means changing an accepted protocol under existing clients.

ADR-029 already gives what a GUI needs most: authority from the channel and never from the request, separate status and administrative channels, a plan with a digest before any administrative change, operations that return an identifier at once, and machine-readable reason codes (ADR-031). The API never installs software; the native package manager does (`specifications/cli-api.md`).

What it lacks for a client that is not the CLI:

- **Version skew.** Every wire type rejects unknown fields (ADR-019 point 2). The CLI ships with the service, so this never bites it. A GUI that ships separately, or one written by someone else, breaks on the first new field in a response.
- **Privilege.** A GUI runs as the desktop user, and `admin.sock` accepts only uid 0.
- **A preview.** "Paste a link, see the packages, compatibility and conflicts" must not add a source. Today the closest command, `source add --observe`, changes state.
- **Change notification.** A window must learn that the state changed without polling every second.
- **Policy duplication.** If a client decides which action is possible, or parses a plan from text, policy is implemented twice.
- **Other languages.** The protocol types exist only in Rust.

## Decision

1. **Version negotiation.** Each channel accepts `hello` as the first request: the client lists the protocol versions it supports, and the server answers with the one it chose and a list of capability names (`preview`, `wait_changes`, …). Every change of a request or response shape raises the protocol `schema_version`; ADR-019's strictness stays as it is. The server keeps serving at least the previous version for one release after a new one. A client ignores capability names it does not know; a capability name is data, not a field. A request without `hello` is served as version 1, as ADR-029 defines. Pakomichi's own GUI, when it exists, ships with the service of the same version and still performs `hello`.
2. **Who may confirm an administrative action.** The server decides it in one replaceable step between the plan and the confirmation, and never from a field of the request. The setting is `admin_authorization`; 0.1 implements only `root` (ADR-029 point 2, uid 0 on `admin.sock`), and any other value is refused at start-up. An authorization for desktop users (`pkexec` with a small helper, or polkit checked by the server) is chosen together with the GUI and needs a decision that supersedes ADR-029 point 2. Confirmation itself does not change: the plan digest of ADR-029 point 8.
3. **Preview.** The request `preview` takes one HTTPS URL of a supported forge (GitHub in 0.1) and returns what `source inspect` would show for it: releases, packages and their families, the evidence level that could be reached, compatibility, and conflicts with installed sources and the system namespace. It writes no state: no source, no pin, nothing in the blob store. It runs as an operation (ADR-029 point 6). The server fetches only the forge API and the asset URLs the API returns, never a URL from the request beyond the repository address, and accepts no token from the client. Starting limits: one preview per uid at a time, ten per uid per hour, two in total; a result is kept in memory for 15 minutes. The setting `preview_for_users` (default `true`) allows it on `status.sock`; with `false` it is accepted only on `admin.sock`.
4. **Change notification.** Every status response carries `state_epoch` (random per start of the state owner) and `state_revision` (monotonic within an epoch). The request `wait_changes` with an epoch and a revision returns when the state is newer, or after at most 25 seconds with the revision unchanged; another epoch is answered at once, so a client sees a restart. A waiting connection counts against the per-uid limit of ADR-029 point 9. Subscriptions over a kept connection are not part of 0.1.
5. **The server lists the possible actions.** A status response lists for each object the actions that are possible now: the action name, the object, the channel it needs, and whether it needs a plan (for example: confirm a repository transfer for source X, approve a Pinned release, repair the socket). Clients show these actions and do not derive them. A plan is a structured list of changes (kind, target, digest before and after, reason codes of the risks) in a canonical form defined once in the protocol module; the digest of ADR-029 point 8 covers that form. The CLI prints the same structure as text.
6. **Published schema.** The protocol is published as a JSON Schema next to the specifications and is checked against the Rust types by a test: every pinned wire example validates, and the schema rejects unknown fields as the types do. How the schema is produced (a crate or a hand-written schema compared by the test) is decided by P2-013c.
7. **Packaging and access.** The core packages have no graphical dependencies; a GUI is a separate package, and a server without a desktop never needs it. The setting `status_access` (`all` by default, as ADR-029 point 2; `root` limits `status.sock` to uid 0) is for shared machines where the list of sources is not for every local user.
8. **What stays out.** No installation, upgrade, key import, or source change through the API (`cli-api.md`); a GUI hands over to the software centre or shows the native command. Integration with GNOME Software and KDE Discover goes through AppStream metadata in Pakomichi's repositories, not through this API; it is a separate study for 0.2. No D-Bus service in 0.1 (ADR-029, alternatives).

## Alternatives and reasons for rejection

- **Leave the API CLI-only and design it again for a GUI:** the cheapest now, but it changes an accepted protocol under existing clients later.
- **Relax the strictness of ADR-019 for responses (clients ignore unknown fields):** simpler negotiation, but a field that weakens a protection could be silently ignored by an old client. Rejected; versions are explicit instead.
- **A D-Bus system service with polkit now (as PackageKit or fwupd):** the usual desktop pattern, but a second authority model and a large dependency before any GUI exists (ADR-029). Kept as an option for point 2.
- **Preview by adding a source in observation mode and removing it:** leaves traces (pins, blobs, history) and needs administrator rights for a question that changes nothing.

## Consequences

- P2-013c implements `hello`, `preview`, `wait_changes`, the action list, the structured plan and the schema; the settings `admin_authorization`, `preview_for_users` and `status_access`.
- `specifications/cli-api.md` and `architecture/privileges.md` describe the new requests when they are implemented; `preview` is a network effect that any local user can start, so its limits belong to the privileges document.
- A GUI remains a separate future epic (`roadmap.md`) and needs its own decision, including point 2.

## Verification

Tests start from a failure and assert the promise to the user (AGENTS.md):

- a client of the previous version keeps working after the server adds a response field, and a client that offers only an unsupported version gets the list of supported ones and nothing else;
- a response field added without raising the version fails the schema test;
- a confirmation from a non-root peer is refused while `admin_authorization = root`, and an unknown value of the setting stops the start;
- a preview writes nothing: the state database, the blob store and the source list are byte-identical before and after, including when the preview fails half-way;
- a preview URL with userinfo, another host, a redirect to another host, or a non-HTTPS scheme is refused before any request; the eleventh preview of a uid within an hour and a second parallel one are refused; a client-supplied token is refused;
- `wait_changes` returns within its deadline with an unchanged revision, at once after a change, and at once with another epoch after a restart; a client that waits on all its connections cannot block `ping` of other clients;
- an action that the status does not list is refused when a client requests it anyway;
- a plan changed between showing and confirming is refused, as in ADR-029.
