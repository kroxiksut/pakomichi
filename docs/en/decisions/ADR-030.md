# ADR-030 — Production attestation verifier: `sigstore-verify` behind a Pakomichi policy layer

**English** · [Русский](../../ru/decisions/ADR-030.md)

**Status:** accepted by the project owner on 2026-10-22, with the owner decisions of that day on P1-003c. It fulfils ADR-017 point 9 for the verifier and supersedes none. The cross-check on the owner's test repository after rename and transfer (P1-003b) remains a completion condition of P1-003c, not of this decision. The sentence of point 7 about version 1 readers is replaced by ADR-031. ADR-034 refines it with stored bundles and the attestation lookup after a transfer.  
**Date:** 2026-10-22.

## Context

ADR-005 and ADR-027 define two GitHub trust levels. Strict needs a verified release attestation of an immutable release; Attested needs a verified artifact attestation bound to the pinned repository ID and the exact bytes. ADR-017 point 9 made the GitHub CLI only the reference oracle for R-003 and left the production verifier to R-003. ADR-023 point 3 waits for it before unsigned RPMs can use the Attested exception.

R-003 established what the verifier has to do and why `gh` cannot be it:

- **Release attestations.** A release attestation of github.com is signed by GitHub's own certificate authority. Its certificate carries only the SAN `https://dotcom.releases.github.com`: no Fulcio claims, issuer, SCT or transparency-log entry, and one RFC 3161 timestamp. That SAN is the same for every repository, so the only binding is inside the signed predicate `https://in-toto.io/attestation/release/v0.2`: `repositoryId`, `packageId`, `ownerId`, `databaseId` (the release ID), `tag`, a `sha1` subject for the tag commit, and one named `sha256` subject per asset.
- **Artifact attestations.** Attestations of public repositories are signed by public-good Sigstore (Fulcio, SCT, Rekor). The certificate claims `1.3.6.1.4.1.57264.1.15` and `.1.17` carry the immutable repository and owner IDs.
- **Why not `gh`.** `gh attestation verify` binds by repository name, reports one error for different causes, and has no offline path for release attestations. `gh release verify` (v2.103.0) checks the tag and the digest but not `repositoryId`. Three matcher advisories fixed after 2.95.0 (GHSA-mm27-mwq9-fr5g, GHSA-wjmr-j3rp-mh2g, GHSA-4mq3-hpgx-9cx8) show how easily name and pattern matching goes wrong.

## Decision

1. **Library.** Pakomichi verifies attestations with `sigstore-verify` from `sigstore/sigstore-rust`. It depends on the published crates, never on a Git source (`deny.toml`: `allow-git = []`): `sigstore-verify`, `sigstore-crypto`, `sigstore-trust-root` and `sigstore-types`, each pinned to `=0.15.0` with `default-features = false`. The transitive `sigstore-bundle`, `sigstore-merkle`, `sigstore-rekor` and `sigstore-tsa` come in at the same version, also without their default features. The library is Apache-2.0 and pre-1.0, a known risk the owner accepted on 2026-10-22.
   - An upgrade is a deliberate change. It reruns the probe cases of point 9 and records the result in the evidence log.
   - Versions below 0.12 are never acceptable: the Trail of Bits audit findings TOB-SIGSTORE-6/9/11 were fixed only in 0.12.
   - No `aws-lc-rs` or `aws-lc-sys` may appear in the graph, and the gate checks this with `cargo tree -i`.
   - A defect found in the library is fixed upstream: the owner sends the pull request, and candidates are tracked locally. Pakomichi never carries a patched fork.
2. **Cryptography provider.** Pakomichi installs its own verification-only `sigstore_crypto::CryptoProvider` on `ring` (the `ring` version of ADR-017's TLS stack) once at process start, before any verification.
   - A process that cannot install it refuses to start. Without a provider, `sigstore-crypto` panics on first use (probe case N42).
   - Prehashed ECDSA and ML-DSA are not available in `ring` and fail closed. Neither is used for DSSE bundles.
3. **Boundary.** The library sits behind a Pakomichi verifier interface that takes bundle bytes, the trusted root and the expected identity, and returns either a verified result with its evidence flags or one sub-reason (point 7). A replacement, such as an in-house verifier, is a superseding ADR behind the same interface. Verification runs in an unprivileged process, never in the administrative applier. Bundles are network input and are size-checked before parsing.
4. **Two verifiers with separate trusted roots, never merged.**
   - **Strict:** GitHub's root (certificate authorities and timestamp authorities). The policy requires:
     - the certificate chain to that root;
     - the SAN exactly `URI:https://dotcom.releases.github.com`;
     - at least one verified RFC 3161 timestamp.

     The transparency log and SCTs are skipped, because GitHub's instance has neither. The predicate must be release v0.2.
   - **Attested:** the public-good root. The policy requires the full chain, a verified SCT, a Rekor inclusion proof with a signed checkpoint, and the issuer exactly `https://token.actions.githubusercontent.com`. The predicate must be `https://slsa.dev/provenance/v1`.
   - A bundle that is valid only under the other root is rejected (probe cases N8, N9).
   - Attested accepts only public-good attestations. GitHub-instance artifact attestations without a transparency log, which private repositories use, are rejected (owner decision D3).
5. **Binding by immutable IDs; names never bind.** All comparisons are exact and case-sensitive, with no prefix or pattern matching.
   - **Strict** (owner decision D4). These must all hold, or verification fails closed:
     - `repositoryId == packageId ==` the pinned repository ID;
     - `ownerId ==` the pinned owner ID;
     - `databaseId ==` the release ID from the API;
     - `tag ==` the release tag;
     - the `sha1` subject `==` the object SHA of the tag reference (`/repositories/{id}/git/ref/tags/<tag>`) as returned, never peeled: the commit for a lightweight tag, the tag object for an annotated tag (refined on 2026-10-22 with the owner's approval after `github/github-mcp-server` v2.0.2 showed the tag object; `gh` compares the same value);
     - a subject with the asset's name has the asset's SHA-256.

     The API's `immutable` flag is still required by ADR-005 but is never evidence by itself. After a transfer the owner ID changes, so the source needs confirmation again.
   - **Attested.** These must all hold:
     - `.1.15 ==` the pinned repository ID and `.1.17 ==` the pinned owner ID;
     - the signer workflow (`.1.9` after the source repository URI) `==` the configured workflow path, and its ref `==` the configured ref;
     - `.1.14 ==` the release ref and `.1.13 ==` the release commit (the commit the tag points to, peeled);
     - `.1.11 == github-hosted`.

     The signer must be the source repository itself, so in 0.1 a reusable workflow from another repository (for example a separate SLSA generator) is rejected. Support for such a signer, pinned by its own repository ID, needs a separate ADR.
   - A changed repository name with unchanged IDs is not a failure. It is reported as a notice (probe cases O1, O2).
6. **What is read, and when.**
   - The in-toto statement is read from the same in-memory bundle that was verified. It is interpreted only after the envelope signature over it has been verified: before that it only chooses which bundles to try (probe case N39).
   - Pre-checks before cryptography: at most 256 KiB per bundle and 16 bundles per digest; bundle media type v0.3 only; DSSE only, with exactly one signature and payload type `application/vnd.in-toto+json`.
   - A set of bundles passes when one bundle passes every check. Otherwise the first failure is reported.
7. **Reasons (owner decision D5).** A failed verification is `E_ATTESTATION_INVALID` with a typed sub-reason. Missing evidence stays `E_EVIDENCE_DOWNGRADE`: no bundle, no release attestation under Strict, or no provenance under Attested. The reason wire contract gains an optional `subcode` field that only `E_ATTESTATION_INVALID` carries, in reason event `schema_version` 2; version 1 readers keep working with the code alone. The sub-reasons are:

   | Sub-reason | Covers |
   |---|---|
   | `bundle_too_large`, `too_many_bundles` | size limits of point 6 |
   | `bundle_malformed`, `bundle_unsupported` | parse failure; media type, content type, signature count, payload type; structural rules of the library |
   | `signature_invalid` | DSSE signature over the statement |
   | `artifact_digest_mismatch` | the bytes are not a subject of the statement |
   | `certificate_untrusted`, `certificate_time`, `sct_invalid` | chain or certificate profile; no authority or certificate valid at the verified time; SCT |
   | `tlog_inclusion`, `tlog_checkpoint`, `tlog_promise`, `tlog_entry` | inclusion proof; checkpoint; inclusion promise or integrated time; entry does not describe the bundle, malformed or unknown log |
   | `timestamp_invalid`, `no_verified_time` | RFC 3161 token; no verified time at all |
   | `identity_mismatch` | SAN or OIDC issuer |
   | `repository_id_mismatch`, `owner_id_mismatch` | point 5 |
   | `release_mismatch`, `subject_mismatch` | release ID, package ID, tag or tag reference object; asset name and digest |
   | `workflow_mismatch`, `ref_mismatch`, `commit_mismatch`, `runner_not_hosted` | point 5 |
   | `statement_invalid` | statement type or malformed statement after verification |
   | `trust_root_invalid` | a defect of the trusted root itself, for example no CT log keys; reported for diagnosis by `pchi doctor` |

8. **Trusted roots are refreshed through TUF (owner decision D2).**
   - Both roots are updated from their TUF repositories with `sigstore-tuf` (`default-features = false`) over Pakomichi's own HTTP stack. They are never taken through the `tuf` feature of `sigstore-trust-root`, which enables `sigstore-tuf`'s default features and with them `aws-lc-rs`.
   - If the TUF metadata has expired and cannot be refreshed, verification fails closed with a reason that names the root. Pakomichi never keeps verifying silently against a root it can no longer refresh.
   - The TUF client is probed with its transport in P2-003; this probe did not exercise it.
9. **Evidence and oracle.**
   - The cases of `research/r-003/verifier-probe-cases.sh` are the acceptance set for any upgrade or replacement of the verifier. Their results are in `research/r-003/results/verifier-probe-cases.tsv`.
   - The reference oracle for R-003 cross-checks is `gh` 2.103.0 or newer, pinned by SHA-256. `cosign` is not added as a second oracle unless `gh` and Pakomichi disagree.

## Alternatives and reasons for rejection

- **The `sigstore` crate 0.14 (sigstore-rs):** marked experimental, `aws-lc-rs` mandatory, and no RFC 3161 support, so no Strict.
- **`gh`, `cosign` or `sigstore-go` at run time:** a Go runtime dependency, binding by name, one untyped error, and no offline Strict in `gh`.
- **`jdx/sigstore-verification` 0.2.8:** a wrapper over the old `sigstore` 0.13 with `reqwest` and `tokio`. It fetches attestations online, binds by owner and repository name, and has no RFC 3161 support. No published crate depends on it; mise itself moved to `sigstore-verify`.
- **An in-house verifier:** 3–5 thousand lines of security-critical code without external review. It stays the fallback behind the interface of point 3.
- **Waiting for 1.0:** no date, and Strict and Attested would stay blocked.
- **Small crates (`sigstore-verifier`, `attestation-verify`, `airgap-verify`):** not mature enough, or built on the same library.

## Consequences

- P2-003 (Strict) and P2-004 (Attested) implement points 2–8 behind the interface of point 3. The probe is research tooling, not product code.
- `specifications/errors.md` gets reason event `schema_version` 2 with `subcode` when P2-003 implements it. Until then the wire contract stays v1.
- ADR-023 point 3 may use the Attested result once P2-004 is implemented. The probe alone does not enable it.
- The dependency set grows by 56 crates in the probe's normal graph. The only duplicate is the build-time `syn` 2 and 3.
- Risks:
  - Pre-1.0 churn and one main maintainer.
  - The library has no published audit beyond the findings fixed in 0.12.
  - Strict rests on GitHub's certificate authority and timestamp authority alone.
  - The predicate IDs are GitHub extensions beyond in-toto release v0.2: if GitHub drops them, Strict fails closed everywhere.

## Evidence

- `research/r-003/verifier-probe/` (probe crate), `verifier-probe.sh` (build and dependency gates), `verifier-probe-inputs.py` (tampered inputs), `verifier-probe-cases.sh` (cases), `verifier-probe-oracle.sh` (cross-check with `gh`).
- Results: `research/r-003/results/verifier-probe-cases.tsv` and `verifier-probe-oracle.tsv`. Raw logs are in `.research-local/p1-003c/`.
- Cross-check on the owner's test repository after rename, reuse of the old name, transfer and fork (`verifier-probe-owner.sh`, `research/r-003/results/verifier-probe-owner.tsv`): 10 of 10 as expected. A new repository that took the old name is rejected by repository ID, while `gh` accepts it offline by name. After a transfer, attestations made before it carry the previous owner ID, so confirming the new owner must not invalidate releases attested under the old one (P2-003, P2-004).
- Desk research: crate sources of 0.15.0, the R-003 report, and the R-003 runs of 2026-10-20 and 2026-10-22.
