# ADR-025 — Astra Linux protected security levels

**English** · [Русский](../../ru/decisions/ADR-025.md)

**Status:** accepted by the project owner on 2026-10-20. ADR-009 and ADR-014 remain in force; this decision refines them and supersedes none.  
**Date:** 2026-10-20.

## Context

R-006 tested Astra Linux 1.8.6 at `base(orel)`, `advanced(voronezh)`, and `maximum(smolensk)` with the closed software environment, mandatory integrity control, and mandatory access control ([R-006 report](../research/R-006-report.md)):

- with the closed software environment on, `dpkg -i` and `apt-get install` install a package with an unsigned ELF with exit 0, but the program is killed with `SIGSEGV` (exit 139) and the reason (`DIGSIG ... NOT_SIGNED`) appears only in the kernel log (cells 2–4);
- a key not signed by the Astra Linux root key cannot be trusted; laboratory RSA and GOST keys were refused;
- with integrity control on, a process at integrity level 0 cannot install packages or write `/etc/apt/sources.list.d/` or `/var/lib/dpkg`, but can run `apt-get update` and write `/var/lib/apt/lists` and `/var/cache/apt/archives` (cell 5); the administrator's SSH session and systemd services, including `DynamicUser=yes`, run at level 63;
- the level is detectable without root; the `digsig` configuration file shows the state for the next boot, not necessarily the running state;
- the protected levels do not change APT's selection (cell 6).

Not covered: Astra Linux 1.7 (excluded by the owner on 2026-10-20), the `external_sig` and xattr signature modes, the interpreter, `chmod +x`, and `bash` locks, and shared libraries (only a static executable was tested).

## Decision

1. **Detection without root.** On Astra Linux, Pakomichi records the security level (`astra-modeswitch get`/`getname`), the closed-environment configuration (`DIGSIG_ELF_MODE` in `/etc/digsig/digsig_initramfs.conf`), and integrity control (`/sys/module/parsec/parameters/max_ilev`, `/proc/cmdline`). A mismatch between configured and running state, or an indicator that cannot be read, counts as "closed environment on".
2. **Out of the 0.1 matrix.** Astra Linux with the closed software environment on (or treated as on) is not supported in 0.1, because Pakomichi's own executables would not run there unless signed through the Astra Linux key chain. In 0.1 Pakomichi refuses to activate sources while the closed environment is on and reports the reason. Astra Linux 1.7 at any protected level is not claimed. Integrity control or access control without the closed environment was not tested and is not claimed.
3. **Hold rule.** While the closed environment is on, Pakomichi holds every artifact with `E_EXECUTION_POLICY` instead of offering it as an ordinary update. The inspector does not read package payloads to look for ELF files (it never reads the payload; `architecture/privileges.md`), so the hold does not depend on what an artifact contains.
4. **No workaround.** Pakomichi never signs, re-signs, or modifies third-party files, never adds keys to `/etc/digsig/keys`, and never changes the security level.
5. **Diagnosis.** When the closed environment is on, an installed program that exits with `SIGSEGV` is reported as a probable closed-environment refusal of an unsigned executable, not as a defect of the package.
6. **Integrity level of the applier.** The administrative applier runs as a systemd service or from the administrator's session (level 63). A failed apply from a lower integrity level is reported as an integrity-level problem (`E_SECURITY_CONTEXT`), not as a package error. Integrity control does not lower Pakomichi's other services (systemd starts them at 63), so ADR-009 privilege separation remains the boundary.
7. **APT lists and cache are untrusted input on every distribution.** Pakomichi does not take package bytes or metadata from `/var/lib/apt/lists` or `/var/cache/apt/archives` as trusted input on any distribution, not only on Astra Linux at a protected level; it relies on APT's own signature and hash verification and on its CAS digests.
8. **Selection rules unchanged.** The R-001 conclusions and the ADR-004 hold apply to Astra Linux 1.8.6 at every level.

## Alternatives and reasons for rejection

- **Sign Pakomichi or third-party binaries with a self-made key:** refused by the kernel; trusting another key requires the Astra Linux root key, and signing third-party files is prohibited by `AGENTS.md`.
- **Offer such artifacts and let the user discover the crash:** installation succeeds with exit 0, so the failure would be silent.
- **Claim the protected levels from the `base(orel)` results:** the installation outcome differs.

## Consequences

- Supporting the protected levels later requires signing Pakomichi's binaries through the Astra Linux key chain and a new run of R-006 cells 2–5 with Pakomichi itself; this is outside 0.1.
- `architecture/families-compatibility.md`, `architecture/privileges.md`, `specifications/apt.md`, `testing/matrix.md`, and `testing/negative.md` are updated in both languages. The owner decided on 2026-10-21 that the reason codes name the class of problem rather than Astra Linux: `E_EXECUTION_POLICY` (an OS execution-control policy would refuse to run the package's executables) and `E_SECURITY_CONTEXT` (the operation runs in a security context, such as an integrity level or a mandatory access label, that cannot perform it). Both are defined in `specifications/errors.md` and `ReasonCode`; no other Astra-specific work is planned.

## Verification

- Evidence: R-006 report, "Results", "Not covered", "Conclusions and required decision changes" 1–8.
- Required tests in the implementation: detection as an unprivileged user at each level, including the configured-but-not-running case and an unreadable indicator; refusal to activate with the closed environment on (N-035); an apply from integrity level 0 reported as an integrity-level problem (`E_SECURITY_CONTEXT`) (N-036).
