# ADR-024 — Local delivery after R-004: generations, freshness, and service robustness

**English** · [Русский](../../ru/decisions/ADR-024.md)

**Status:** accepted by the project owner on 2026-10-20. ADR-007, ADR-008, ADR-010, and ADR-013 remain in force; this decision refines them and supersedes none. ADR-021 already covers `skip_if_unavailable` and socket recovery; point 3 answers the interaction that ADR-021 left to this ADR. ADR-036 makes the port a setting until the test of point 6 is run.  
**Date:** 2026-10-20.

## Context

R-004 tested socket activation, immutable generations, lazy fetch, crashes, and removal on Debian 12 (APT 2.6), AlmaLinux 9 (DNF 4.14), and Fedora 44 (DNF5 5.4) with systemd as PID 1, plus three guest power cuts on Astra Linux 1.8.6 ([R-004 report](../research/R-004-report.md)). ADR-007 and ADR-013 held, and ADR-008 held with two mandatory details. The conclusions that change or sharpen decisions:

- without content-addressed index names a generation switch produces hash mismatches (G3); without retained old generations APT falls back to the mutable path and mixes generations (G4) (conclusion 5);
- `repomd.xml` has no signed expiry, and DNF accepted older signed metadata served again after newer metadata and offered the older version; APT ignored the replay and enforces `Valid-Until` (G7, G8, conclusion 6);
- the detached `repomd.xml.asc` and `repomd.xml` are separate mutable paths: on Fedora 44, 1–3 of 640 parallel updates failed with `Bad PGP signature` when generations switched every few seconds; per-connection pinning did not help (G6, G6p, conclusion 7);
- a crash loop disables the socket (S7); while it is down the loopback port is free for any local user (conclusion 3, an untested analysis);
- `systemctl restart` broke 10–13 of 20,000 in-flight requests (S3); 70 slow local clients against the 64-connection limit delayed others by about 10 s (S8b) (conclusion 4);
- signing-key loss stops publication honestly; APT clients fail after `Valid-Until` (G9, conclusion 13).

## Decision

1. **Content-addressed indexes are mandatory.** APT `Release` declares `Acquire-By-Hash: yes` and every index is served under its `by-hash` path; RPM `repodata` files have unique, digest-bearing names (never `--simple-md-filenames`); package paths are content-addressed. Only `InRelease`, `Release`, `Release.gpg`, `repomd.xml`, `repomd.xml.asc`, and the plain compatibility index paths are mutable, and they are served only from the current generation.
2. **Retention and garbage collection.** A retired generation stays reachable at least until no client can still hold metadata that references it: the retention window is at least the maximum freshness (DNF) or the `Valid-Until` of its `InRelease` (APT), plus a safety margin. Garbage collection is by reachability plus this time window, never by generation count alone. The exact window is a configuration value that the implementation must test against G4/G5.
3. **Server-side freshness and no rollback for DNF.** Generation IDs are monotonic and never reused; `current` never moves back to an older generation. When the last confirmed synchronization of a DNF source is older than the maximum freshness of `delivery-recovery.md` (7 days by default), Pakomichi does not answer 503 and does not keep serving the stale generation: it publishes a new signed generation of that source's DNF repository that contains no packages (an empty generation). Installed packages stay installed; DNF keeps working for the rest of the system, because the Pakomichi repository stays available (compatible with ADR-021); the source's packages are not offered for installation or upgrade until a successful synchronization publishes a fresh generation; `pchi doctor` and `pchi status` show the reason (`E_SOURCE_STALE`). The empty generation asserts only that nothing is currently offered, so it does not re-sign stale data as fresh (ADR-010). This behaviour must be verified by a test on every supported DNF build before release. APT relies on `Valid-Until`, which must equal the confirmed freshness. Signing keys and `Valid-Until` settings are chosen so that the staleness warning (24 h) fires well before clients are blocked.
4. **Infrequent RPM generation switches.** RPM generations are switched at most once every 6 hours (the regular check interval), except on an explicit `sync --force` and for the empty generation of point 3, which is published when the maximum freshness is reached. Pakomichi's own post-publication check treats a metadata-signature failure immediately after a switch as retryable, not as corruption. Generations are never switched faster than clients update.
5. **Service robustness.** The reader never exits with an error status on recoverable conditions, so that it does not consume the systemd start limit. On `SIGTERM` it stops accepting, completes in-flight responses within a bounded deadline, and then exits; upgrades use this drain. Slow clients get a request-header deadline shorter than the 10 s used in R-004 and a limit that prevents one local client from occupying all connections; how a client is identified on loopback is an implementation question. The concrete values are fixed and tested by the implementation.
6. **Port takeover (test required).** A test is to be run of binding the socket on a privileged port (below 1024) through systemd, so that an unprivileged user cannot take the port over while the socket is down. The port choice follows that test and is recorded separately; until then ADR-021's health check is the only mitigation, and APT is bounded by `Valid-Until` while DNF is not.
7. **Out of scope.** Lazy-fetch SSRF rules with HTTPS (conclusion 11) and GitHub conditional requests (conclusion 14) belong to the GitHub and HTTP client decisions of P2-001. Verification of objects before sending (conclusion 10) is already part of `delivery-recovery.md`.

## Alternatives and reasons for rejection

- **Mutable index paths only:** fail during switches (G3).
- **Retention by generation count:** cannot bound how long a client holds old lists (G4, G5).
- **Rely on client-side expiry for DNF:** `repomd.xml` has none, and DNF accepts a replay (G8).
- **Per-connection generation pinning:** did not help DNF, because librepo uses several connections (G6p).
- **Switch RPM generations on every poll:** increases the `repomd.xml.asc` mismatch rate without benefit.

## Consequences

- Combined with ADR-021, point 3 means that a DNF source past its maximum freshness stops offering its packages but does not block DNF for the rest of the system: the empty generation keeps the Pakomichi repository available. A Pakomichi DNF repository that is unreachable (service or socket down) still blocks DNF metadata operations, as ADR-021 states. Re-signing stale data as fresh remains prohibited (ADR-010).
- `architecture/delivery-recovery.md`, `specifications/apt.md`, `specifications/dnf.md`, `architecture/states.md` (snapshot retention), and `testing/negative.md` (replay of an older generation, freshness expiry on DNF, drain on restart, port takeover) are updated in both languages.

## Verification

- Evidence: R-004 report, "Socket activation", "Generations and native clients", "Conclusions and required decision changes" 2–7, 10, 13.
- Required tests in the implementation: G3/G4 controls stay failing and G2/G5/G6 pass with the production publisher; a replayed older generation is never served as `current`; restart under load loses no in-flight response; the slow-client limits; garbage collection never removes a generation inside its window.
- Verification items before release: on every supported DNF build, DNF freshness expiry publishes a signed empty generation, installed packages stay installed, DNF operations on the distribution repositories succeed, the source's packages are no longer offered, and a successful `sync` restores them (N-032); the privileged-port test of point 6 (N-034).
