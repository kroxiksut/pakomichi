# ADR-022 — Native source selection: system namespace and publisher protection

**English** · [Русский](../../ru/decisions/ADR-022.md)

**Status:** accepted by the project owner on 2026-10-20. ADR-003, ADR-004, and ADR-012 remain in force; this decision refines them and supersedes none.  
**Date:** 2026-10-20.

## Context

ADR-004 assigns each Git source its own logical repository with APT `Origin`/`Label`/`Suite`, a targeted pin, and DNF repository ID, priority, and `includepkgs`, and holds an equal native version with different bytes. R-001 ran the selection matrix on APT 1.8 (Astra Linux 1.7), 2.6 (Debian 12, Astra Linux 1.8), 2.8, 3.0, 3.2, DNF4 (AlmaLinux 9 and 10, RED OS 7.3 and 8), and DNF5 (Fedora 44) ([R-001 report](../research/R-001-report.md)); R-006 repeated the APT matrix at Astra Linux 1.8.6 `maximum(smolensk)` with the same decisions in all 26 cells ([R-006 report](../research/R-006-report.md), cell 6). The findings that need a decision:

- No manager keeps an *equal* version bound to one instance over the package's life: APT 2.6 merges equal versions and source order decides; APT 2.8+ binds only a fresh install; DNF `distro-sync` and `reinstall` move to the currently preferred instance; on RED OS 7.3 and 8 `reinstall` takes the instance from the repository with the *worst* priority (R-001 conclusions 1, 2, 8).
- An ordinary upgrade changes the publisher on every tested manager when another enabled source offers a higher version of the same name. A 990 pin on the original source (APT) and repository priority or `excludepkgs` (DNF) prevent it; `allow_vendor_change=False` also does, but DNF 4.2 on RED OS 7.3 does not have the option (conclusion 3, RED OS table).
- Family dependencies are resolved across sources silently (APT and DNF tables).
- Every tested manager accepts a third-party `Provides` of the C library and uses it to satisfy a versioned C-library requirement (N-008 + N-009, conclusion 4).
- `apt-get update` exits 0 when a source is offline (conclusion 5; R-004 conclusion 9).
- Astra Linux 1.7 and 1.8 refuse `apt upgrade` and `apt-get upgrade`; their ordinary path is `apt-get dist-upgrade`, which also changes the publisher without a pin (conclusion 7).

## Decision

1. **Equal versions.** ADR-004 stays as accepted on every platform: an equal native version with different bytes is `E_SOURCE_AMBIGUOUS` (observing/hold), and the conflicting package is never published in an active repository. Neither APT 2.8+ pins nor DNF priority are accepted as a substitute.
2. **System namespace.** The system namespace is the set of package names and `Provides` (package names and virtual capabilities, file provides, soname provides) of the packages from the distribution's own sources. An artifact is held with `E_SYSTEM_PACKAGE_CONFLICT` when any of its `Provides` names a member of the system namespace. The rule is conservative for replacement relationships: an artifact whose `Obsoletes` or `Replaces` names a member of the system namespace is also held, whatever the version constraint of that relationship. Ordinary capabilities provided only by the admitted family itself stay allowed (`families-compatibility.md`). The check runs in Pakomichi's admission, because the native managers do not perform it. Which configured sources count as the distribution's own sources on each supported build is fixed by the system-namespace specification.
3. **No implicit publisher change.** For every activated name, including every member of the activated family:
   - **APT:** a targeted preference with `Pin-Priority: 990` for the activated names, matched by the `Origin`/`Label` of the source's logical repository (`Pin: release o=…,l=…`). `Pin: origin` (host name) is not used, because ADR-007 serves all logical repositories from one loopback host. A priority of 1000 or higher is never written, because it allows downgrades (R-001, "Installed 1.0, lower version pinned 1001").
   - **DNF:** the source's repository has a priority better than the distribution repositories, and `includepkgs` lists only the activated names, so the priority affects no other name. `allow_vendor_change` is read and reported, never written (it is global) and never relied upon (absent in DNF 4.2). `excludepkgs` in other repositories is not written, because it changes third-party repository configuration.
   - **Activation:** a name that is installed from, or available in, another enabled source is not activated implicitly; it stays `observing` until an explicit migration (ADR-012, E2E-04).
   - **Later updates from another source:** an activated name keeps its publisher even when another source, including a distribution security update, later offers a newer version of it. Pakomichi shows a prominent notice of such an update (in `pchi status`, `pchi doctor`, and the status API), naming the other source and its version; switching the publisher remains an explicit user decision (ADR-012).
4. **Ordinary update command per distribution.** The supported update commands are: `apt upgrade` and `apt full-upgrade` on Debian and Ubuntu; `apt-get dist-upgrade` on Astra Linux; `dnf upgrade` on DNF platforms. The protection of point 3 must be shown under each listed command. Pakomichi never requires `APT::Get::EnableUpgrade` or any other change of the distribution's APT or DNF policy. The first vertical slice ("GitHub connection → verification → APT → ordinary `apt upgrade`") uses this per-distribution command.
5. **Per-build adapters.** DNF4 and DNF5 are separate adapters (see also ADR-023), and every selection rule is verified on every supported distribution build, not inferred from the manager's version number: RED OS 7.3 and 8 differ from upstream DNF 4.14/4.20 in `reinstall`, defaults, and options. APT 2.6-based builds (Debian 12, Astra Linux 1.7 and 1.8) and APT 2.8+ differ in how equal versions are merged.
6. **Health diagnosis.** Offline and stale-source diagnosis uses Pakomichi's own state (last confirmed synchronization, age of the served generation, service and socket health) and per-source fetch results, never the exit status of `apt-get update`.

## Alternatives and reasons for rejection

- **Rely on DNF priority alone for equal versions:** fails on RED OS `reinstall` and on `distro-sync` everywhere.
- **Write `allow_vendor_change=False`:** a global DNF setting that changes the behaviour of distribution packages, and is ignored by DNF 4.2.
- **`excludepkgs` in third-party repositories:** effective on every tested DNF, but it edits third-party configuration, which `AGENTS.md` prohibits.
- **Pin 1000 or higher:** would also force downgrades.
- **Enable `APT::Get::EnableUpgrade` on Astra Linux:** changes the distribution's policy.
- **Rewrite versions or epochs to win selection:** already rejected by ADR-004 and ADR-012.

## Consequences

- An activated Pakomichi package keeps its publisher even when a distribution later offers a newer version of the same name; distribution security updates of that name then need an explicit migration. Users are told this at activation, and the notice of point 3 makes every such update visible.
- `architecture/families-compatibility.md`, `architecture/policy-engine.md`, `specifications/apt.md`, `specifications/dnf.md`, `testing/negative.md`, and `testing/e2e.md` are updated in both languages. The definition of the system namespace still needs a specification with tests before admission is implemented.
- `Pin: release` by `Origin`/`Label` on one loopback host was not part of R-001 (R-001 served each source under its own host name). It must be verified before point 3 is implemented.
