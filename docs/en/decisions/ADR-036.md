# ADR-036 — Source settings confirmed by the administrator: Attested signer, loopback port, family approval

**English** · [Русский](../../ru/decisions/ADR-036.md)

**Status:** accepted by the project owner on 2026-10-24. It refines ADR-030 point 5 (where the configured workflow and ref come from), ADR-024 point 6 (the port until N-034 is run), and the family admission of `architecture/families-compatibility.md` (which command confirms a family). It supersedes nothing. The default port of point 2 was chosen by the owner on 2026-10-24 after N-034: 879 (`architecture/delivery-recovery.md`).  
**Date:** 2026-10-24.

## Context

Three questions blocked the synchronization pipeline of P4-001a:

- ADR-030 point 5 requires the signer workflow and its ref of an Attested provenance to equal "the configured" workflow and ref, but no document says where a source's workflow and ref are configured.
- ADR-024 point 6 postpones the choice of the loopback port until the privileged-port test N-034, while the APT configuration (P4-003a) and the reader's socket unit already need a port.
- `architecture/families-compatibility.md` says the administrator confirms a family's names at a revision, but no command does it.

## Decision

1. **The Attested signer is part of the source and is confirmed when the source is added.**
   - A source has at most one Attested signer: a workflow path inside the source repository (`.github/workflows/<file>.yml|yaml`) and a ref rule. The rule is either "the release tag" (the provenance ref is `refs/tags/<tag of the release being verified>`) or one branch (`refs/heads/<name>`).
   - `pchi source add` looks for the signer itself. It takes the latest release, asks GitHub for the attestations of each asset by the pinned repository ID (ADR-034), and verifies every SLSA provenance under all checks of ADR-030 points 4–6 except two: the workflow and the ref are read from the verified certificate instead of being compared. The signer must still be a workflow of the source repository itself, built on a GitHub-hosted runner, from the commit the release tag points to.
   - The plan shows the signer found, or says that none was found and why. The administrator's `yes` confirms it together with the source; nothing is stored before that.
   - `--workflow <path>` and `--ref tag|refs/heads/<name>` set the signer explicitly. When they are given and discovery finds a different signer, the plan is refused and shows both. Explicit values let a source be added before its first attested release.
   - Two different signers in the latest release make the plan refuse and ask for `--workflow` and `--ref`. Discovery never picks one of them.
   - Without a signer, the source is added and works at Strict and Pinned. A release that has only Attested evidence is held with `E_EVIDENCE_DOWNGRADE`, and the status names the missing signer.
   - The signer changes only through a separate interactive administrative command that shows the old and the new signer. Its name is approved by the owner when it is implemented. A provenance from another workflow or ref is `workflow_mismatch` or `ref_mismatch` (ADR-030 point 7), never a reason to change the signer automatically.
2. **The loopback port is a setting until N-034 decides its default.**
   - The port is a start argument of the state owner (`--loopback-port`, default 18080) and the `ListenStream=` of the reader's socket unit. P5-004a ships both with the same value, and the administrator changes both together with a drop-in.
   - The state owner renders the APT sources with its port, so the port reaches APT only through the root applier (ADR-035, P4-003a). `pchi doctor` reports when the socket listens on a different port.
   - N-034 is run before the alpha on a test bed: a privileged port (below 1024) bound by a systemd socket unit, the socket stopped and then in `failed`, an unprivileged user trying to bind the same address. Its result chooses the default, which is recorded in the evidence log and in `architecture/delivery-recovery.md`; a privileged default does not change this decision.
3. **`pchi source activate` confirms the family.**
   - The plan of `pchi source activate <id> --packages a,b` shows the family revision the server holds, every name and architecture seen in the source at that revision, and the names to be activated.
   - The `yes` approves the next revision of the family: the names approved before plus the listed names, with the architectures shown. It also activates the listed names. The plan digest covers the revision, so a confirmation of an older revision is refused (`families-compatibility.md`).
   - A name that the source has never offered is refused at planning. A source that has not been synchronized yet has no family; its activation is refused with a message to run `pchi sync <id>` first.
   - A name seen but not listed stays outside the family and is held with `E_FAMILY_UNAPPROVED`. A new name in a later release is held the same way until it is activated with the same command.
   - No separate `approve-family` command exists.

## Alternatives and reasons for rejection

- **A required `--workflow` for every source:** an administrator copies a path from the repository and makes typing mistakes. A source without `--workflow` would work only at Strict and Pinned, even when its releases are attested. Right for forges or instances where discovery cannot verify what it finds.
- **Taking the signer from the first provenance seen at every synchronization:** a compromised workflow of the same repository would become the signer by publishing first. The signer is fixed by the administrator and changed only by the administrator.
- **Choosing the port now:** ADR-024 point 6 makes the choice depend on N-034. A setting with a default keeps test beds and packages consistent until then.
- **A separate `approve-family` command:** one more confirmation for the same decision. Activation already shows the names and needs the administrator. Right if a family ever needs approval without activating anything, for example a source that is only observed.

## Consequences

- Migration 0004 stores the signer of a source. The plan of `source add` gains a change of kind `set_signer`, and `SourceAdd` gains the optional `workflow` and `ref` arguments. The protocol is not released yet, so `schema_version` stays 1.
- The state owner needs the trusted roots and the verifier for planning `source add`, as it does for synchronization.
- `specifications/cli-api.md`, `architecture/families-compatibility.md`, `architecture/trust.md`, and `architecture/delivery-recovery.md` describe the rules in both languages.
- The plan of an activation names the family revision, and the run refuses when the revision moved.

## Verification

- Tests in P4-001a: discovery returns the signer of a verified provenance only; a provenance of another repository, a self-hosted runner, or another commit is not a signer; two different signers refuse the plan; explicit values that disagree with discovery refuse the plan; a release with only Attested evidence and no signer is held with `E_EVIDENCE_DOWNGRADE`; an activation of a name the source never offered is refused; a confirmation of an older family revision is refused; a new name after activation is held with `E_FAMILY_UNAPPROVED`.
- N-034 on a test bed with real units, recorded in the evidence log.
