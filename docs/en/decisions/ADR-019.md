# ADR-019 — serde and serde_json as the serialization layer

**English** · [Русский](../../ru/decisions/ADR-019.md)

**Status:** accepted by the project owner.  
**Date:** 2026-10-20.

## Context

P0-003 implemented the versioned reason contract (JSON envelope v1) with `serde =1.0.229` (feature `derive`) and `serde_json =1.0.154`. The decision log deferred approval of these crates to P0-004, and ADR-017 does not name them. Upcoming work needs a serialization layer for versioned JSON: the IPC between the unprivileged core and the applier, the read-only status API, evidence and decision records, and parsing of GitHub API responses (P2-001).

`rust-engineering.md` requires that IPC, storage, and serialized-decision formats have an explicit version and one normative type, and that `Debug`/`Display` are never a stable format.

The locked graph of the two crates is: `serde`, `serde_core`, `serde_derive` (with `proc-macro2`, `quote`, `syn`, `unicode-ident` at build time), `serde_json`, `itoa`, `memchr`, and `zmij`. All are MIT and/or Apache-2.0 (with Unicode-3.0 for `unicode-ident`), come from crates.io, and pass the current `cargo deny` policy.

## Decision

1. Approve `serde` (features `derive` and the default `std`) and `serde_json` (default features only) with exact version pins in `[workspace.dependencies]`. Updates follow the normal dependency review and `cargo deny`.
2. **Formats owned by Pakomichi** (reason events, IPC messages, status API, evidence and decision records): every top-level message carries an explicit `schema_version`; its wire type uses `#[serde(deny_unknown_fields)]`; it is converted into validated domain types through `TryFrom`, as P0-003 already does. A message with an unknown field or an unsupported version is rejected with a stable reason code, never partially accepted.
3. **Formats owned by others** (GitHub REST responses and similar): do not use `deny_unknown_fields`, because the provider adds fields. Deserialize only the fields that are used into dedicated wire types, validate them, and treat a missing or mistyped required field as an error. Never derive trust from a field that is not explicitly validated.
4. **Limits:** the input size is bounded before parsing; keep the `serde_json` default recursion limit (do not enable `unbounded_depth`); do not enable `arbitrary_precision`, `preserve_order`, or `raw_value` without a separate decision. Numbers that are identities or sizes are parsed into explicit integer types, never through `f64`.
5. **Out of scope:** SQLite rows (handled by `rusqlite` directly), DEB/RPM metadata (process boundaries of ADR-017), APT/RPM repository files (written by dedicated generators), and the configuration file format, which needs its own decision when a configuration file is introduced.

## Alternatives and reasons for rejection

- Hand-written JSON encoding and decoding: more code on security-relevant parsing paths and no gain in auditability for this size of format.
- `miniserde` or `nanoserde`: smaller, but with weaker support for strict field handling and validated conversion, and less review and use in the ecosystem.
- SIMD JSON parsers: performance is not a constraint for these message sizes, and they add `unsafe` code and dependencies.

## Consequences

`Cargo.toml` already matches points 1 and 4 (no extra features). `src/error.rs` follows point 2 and limits a reason event to `MAX_REASON_EVENT_JSON_BYTES` before parsing. The GitHub API client (P2-001) must follow point 3, with a test that unknown provider fields are tolerated and that a missing required field fails. `rust-engineering.md` references this ADR.

## Verification

`scripts/quality.ps1`: the reason-contract tests reject an unknown field and an unsupported `schema_version` (`unknown_schema_versions_and_fields_are_rejected`) and reject input over the size limit before parsing (`oversized_input_is_rejected_before_parsing`); `cargo deny` checks the graph. Every new owned message type must add the same two tests.
