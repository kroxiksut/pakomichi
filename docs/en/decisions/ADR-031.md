# ADR-031 — Reason events v2 with an attestation sub-reason

**English** · [Русский](../../ru/decisions/ADR-031.md)

**Status:** accepted by the project owner on 2026-10-22. It supersedes the last sentence of ADR-029 point 5 ("Reason events inside responses keep the wire contract v1") and replaces the sentence of ADR-030 point 7 about version 1 readers; nothing else in either changes.  
**Date:** 2026-10-22.

## Context

ADR-030 point 7 (owner decision D5) gives every failed attestation verification a typed sub-reason under `E_ATTESTATION_INVALID`, carried in an optional `subcode` field of the reason event with `schema_version` 2. It also says that version 1 readers keep working with the code alone. That is not true: the version 1 contract in `specifications/errors.md` rejects an unknown `schema_version` and unknown fields, so a version 1 reader rejects every version 2 event.

ADR-029 point 5, accepted earlier, says that reason events inside IPC responses keep the wire contract v1. Taken together, the two decisions cannot both hold for an attestation failure that crosses IPC.

## Decision

1. **Two versions.** Version 1 is unchanged. Version 2 is version 1 plus `reason.subcode`, whose value is one of the sub-reasons of ADR-030 point 7 (`specifications/errors.md`, "Wire contract v2").
2. **Version 2 only when needed.** A writer uses version 2 only for `E_ATTESTATION_INVALID` with a sub-reason. Every other event, including `E_ATTESTATION_INVALID` without one, stays version 1. A version 1 reader therefore keeps reading every other event and rejects only the version 2 ones, as its contract requires.
3. **Readers.** Pakomichi's readers (the CLI, the IPC client, and the service) accept both versions. A version 2 event without `subcode`, a version 1 event with one, a `subcode` with another code, and an unknown `subcode` are rejected. The CLI and the service ship together, so no deployed reader is older than the writer.
4. **IPC.** Reason events inside IPC responses use this contract, versions 1 and 2. The IPC message envelope of ADR-029 (its own `schema_version` 1) does not change.
5. **Message.** The `message` of an attestation failure is fixed text for its sub-reason. The verifier's detail can quote certificate or bundle values from the network and is kept only for local diagnostics.

## Alternatives and reasons for rejection

- **Keep only version 1 and put the sub-reason in the message text:** simple, but not machine-readable, which reverses owner decision D5.
- **Keep the reason event at version 1 and add the sub-reason as a separate field of the IPC response:** keeps the reason contract, but stores the cause in two places, and the CLI's own output would have no sub-reason.
- **Make every event version 2:** every version 1 reader would reject everything, including events that have no sub-reason.

## Consequences

- `src/error.rs`: `REASON_SCHEMA_VERSION` (1), `REASON_SCHEMA_VERSION_SUBCODE` (2), `ATTESTATION_SUBCODES`, `ReasonSubcode`, `Reason::attestation_invalid`. `ReasonEvent::new` chooses the version from the presence of a sub-reason.
- `AttestationFailure::reason` builds the event: version 2 for an invalid attestation, version 1 `E_EVIDENCE_DOWNGRADE` for missing evidence.
- The contract tests check both versions, every rejection above, and that the sub-reasons in `specifications/errors.md` equal `ATTESTATION_SUBCODES` and the verifier's `SubReason` list.
