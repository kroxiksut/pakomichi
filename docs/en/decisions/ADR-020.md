# ADR-020 — System SQLite 3.34.1 without STRICT tables

**English** · [Русский](../../ru/decisions/ADR-020.md)

**Status:** accepted by the project owner on 2026-10-20; supersedes point 2 of ADR-017 only. All other points of ADR-017 remain in force.  
**Date:** 2026-10-20.

## Context

ADR-017 point 2 selects `rusqlite 0.40.2` with the distribution SQLite library and requires SQLite 3.37 or newer, because migration 0001 declared every table `STRICT`. R-004 found that AlmaLinux 9.8 ships `sqlite-libs-3.34.1-11.el9_8` ([R-004 report](../research/R-004-report.md), conclusion 15). SQLite 3.34.1 cannot parse `STRICT`: on that system the previous migration 0001 fails with `near "STRICT": syntax error`. The EL9 family therefore needed one of three changes: a bundled SQLite for EL9, no `STRICT` tables, or no EL9 in 0.1.

`STRICT` was used only to enforce column storage types. The same rule can be written as `CHECK (typeof(column) = ...)` constraints, which every SQLite version that Pakomichi can target understands. `rusqlite 0.40.2` itself supports SQLite 3.34.1 or newer: its default bindings are `min_sqlite_version_3_34_1`.

Migration 0001 has never been applied to an installation: no package or release has shipped it. It can therefore still be edited in place, as was done for the P0-002 review fix; its version stays 1 and its name stays `initial`.

## Decision

1. Keep `rusqlite 0.40.2` with default features disabled and the **distribution SQLite library** on every supported distribution, including EL9. Bundled SQLite is not used by default; enabling it anywhere requires a new owner decision.
2. Do not use `STRICT` tables. Every column of every table carries a type check as its first constraint: `CHECK (typeof(c) = 'text')` or `CHECK (typeof(c) = 'integer')` for a `NOT NULL` column, and `CHECK (typeof(c) IN ('text', 'null'))` for a nullable column. Declared types keep their affinity, so the result matches a `STRICT` table: a value that converts losslessly (the integer 5 into `TEXT`, the text `'5'` into `INTEGER`) is stored in the declared type, and any other value (a BLOB in `TEXT`, `'abc'` or 1.5 in `INTEGER`) is rejected. An `INTEGER PRIMARY KEY` is the rowid and is rejected by SQLite itself for a non-integer value. All foreign keys, `UNIQUE` constraints, triggers, and existing checks are unchanged.
3. The minimum supported SQLite version is **3.34.1**. It is the oldest version on which the schema and its tests have been run (AlmaLinux 9.8), and it is the floor of `rusqlite 0.40.2`. The schema and the application must not use SQLite features newer than 3.34.1, among them `RETURNING` and `ALTER TABLE ... DROP COLUMN` (3.35.0), `STRICT` (3.37.0), `unixepoch()` and the `->`/`->>` operators (3.38.0). SQL must not rely on compile-time options that a distribution may omit, such as the JSON functions before 3.38.0; JSON columns are stored as text and parsed in Rust.
4. Migration 0001 is changed in place to the form described in point 2. Later migrations follow the same rule and are checked on the oldest supported SQLite.
5. The state owner checks the runtime SQLite version (`sqlite3_libversion_number()`) before it opens the state database and refuses to start below 3.34.1 with a clear diagnostic. The reason code and message are fixed by the task that adds `rusqlite` to the main crate.

A platform whose system SQLite is older than 3.34.1 is not supported by this decision. Adding it requires evidence on that platform and a separate owner decision (for example, bundled SQLite for that platform only).

## Alternatives considered

- **Bundled SQLite for EL9 only:** keeps `STRICT`, but ships a second SQLite in one package family, makes Pakomichi responsible for SQLite security updates on EL9, and splits the build matrix. Rejected by the project owner.
- **Bundled SQLite everywhere:** one SQLite version on every platform, but the same servicing cost on every distribution and a duplicate of a library that every target already ships. ADR-017 already rejected it as the default. Rejected by the project owner.
- **No EL9 in 0.1:** keeps the schema unchanged, but drops the EL9 family, the DNF4 platform on which R-001, R-002, and R-004 all ran, although nothing in the schema needs a feature newer than 3.34.1. Rejected by the project owner.
- **No type enforcement:** plain SQLite affinity would accept a BLOB or arbitrary text in any column. Rejected, because type errors in identity and digest columns must fail in the database, not only in application code.

## Consequences

The schema enforces the same storage types as before on SQLite 3.34.1 and newer, and EL9 keeps using the distribution SQLite with its distribution security updates. Each table definition is longer; a column added without a type check is caught by the migration tests, which try a wrong-typed value in every column of every table.

Every SQL statement in Pakomichi is limited to SQLite 3.34.1 features. `RETURNING` is not available, and removing a column needs a table rebuild in a forward-only migration.

Supported platforms whose SQLite version has not been checked against 3.34.1 remain unverified until it is checked. This includes RED OS 7.3. Such a platform must not be declared supported until its SQLite version has been recorded and the migration tests have passed there. Astra Linux 1.7.6 was checked on 2026-10-20: it ships `libsqlite3-0 3.34.1-3+ci202402082153+astra2` (an Astra backport above the Debian 10 version), migration 0001 applies, and the 13 migration tests pass with its Python 3.7.3.

`prototypes/p0-004/tests/stack.rs` keeps its assertion of SQLite 3.37 or newer: it is recorded P0-004 evidence for ADR-017, not a product requirement.

## Verification

- `python3 -m unittest discover -s tests -p "test_*.py" -v` on AlmaLinux 9.8 (`sqlite-libs-3.34.1-11.el9_8`, Python 3.9.25, `_sqlite3` linked to `/lib64/libsqlite3.so.0`, `sqlite3.sqlite_version` = 3.34.1): 13 tests passed. The same tests pass on the Windows host (SQLite 3.45.3) through `scripts/quality.ps1`.
- Control on the same system: the previous `STRICT` migration 0001 fails with `near "STRICT": syntax error`.
- Negative tests in `tests/test_schema_migrations.py`: a wrong-typed value is rejected by the type check in every column of all 16 tables (a BLOB in `TEXT`; `'not-an-integer'`, 1.5, and a BLOB in `INTEGER`); every nullable column accepts NULL; lossless values are stored in the declared type. Removing a single type check from the migration makes the per-column test fail.
