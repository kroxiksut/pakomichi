# ADR-021 — DNF repositories of Pakomichi fail closed (`skip_if_unavailable=False`)

**English** · [Русский](../../ru/decisions/ADR-021.md)

**Status:** accepted by the project owner on 2026-10-20; supersedes ADR-010 in part (the availability of system DNF operations while a Pakomichi repository is unavailable). All other parts of ADR-010 remain in force.  
**Date:** 2026-10-20.

## Context

R-001 showed that the behaviour of DNF when a repository disappears depends on `skip_if_unavailable` ([R-001 report](../research/R-001-report.md), "Results: DNF" and conclusion 2). With `True`, a package installed from a repository that is removed (404) or offline is silently replaced by another publisher's file of the same NEVRA on `dnf reinstall`, with exit status 0. The default is `False` on AlmaLinux 9 and 10, but `True` on Fedora 44 (DNF5) and on RED OS 7.3 and 8. A per-repository `skip_if_unavailable=False` made every tested DNF fail with exit 1 and keep the installed instance.

R-004 measured the cost of `False` ([R-004 report](../research/R-004-report.md), "Third-party repositories and removal", conclusion 8). While the Pakomichi repository refuses connections (T1) or answers 503 (T2), every `makecache` fails and so does the installation of a distribution package. If the service and its data are removed but the repository file is left behind (T3a), DNF keeps failing; with the file removed too (T3), DNF works and the installed application still runs. R-004 also showed that a crash loop puts the systemd socket into `failed` (`service-start-limit-hit`), after which it stops listening until `systemctl reset-failed` and a socket start (S7, conclusion 2). A crash loop therefore turns into a system-wide DNF outage under `False`.

ADR-010 is titled "Failure must not affect applications or system sources". With `False`, an unavailable Pakomichi repository does not change any third-party repository file or installed application, but it does stop DNF operations on the other sources until the Pakomichi repository is available again or removed. This ADR records that limit explicitly.

APT is not affected: an unreachable source or a 503 answer gives `apt-get update` exit 0 with a warning, and distribution sources keep working (R-001 conclusion 5, R-004 T1 and T2, conclusion 9).

## Decision

1. Every DNF repository section written by Pakomichi sets `skip_if_unavailable=False` explicitly, on DNF4 and DNF5, regardless of the distribution default. The distribution default is never relied upon.
2. While a Pakomichi DNF repository is unavailable, DNF operations that load the metadata of all enabled repositories fail. This is accepted as a fail-closed outcome in preference to a silent switch to another package instance. It is a documented limitation of the DNF integration, not a defect to be hidden.
3. Protections that are mandatory with this setting:
   1. **Health check and socket recovery.** The diagnostic command `pchi doctor` checks the socket and service units and reports a socket in `failed` or `service-start-limit-hit` as a Pakomichi repository outage. The documented recovery is `systemctl reset-failed` for the units followed by starting the socket. Performing the recovery is an administrative action that needs administrator privileges; it is never offered through the read-only status API or the loopback HTTP endpoint (ADR-009).
   2. **Removal.** Uninstalling Pakomichi and removing a source delete the Pakomichi `.repo` files of that source, so that no repository file points at a service that no longer exists (R-004 T3a versus T3).
   3. **Error message.** The failure names the Pakomichi repository. Repository IDs and `name` values of Pakomichi repositories identify Pakomichi and the source, so that DNF's own error message points at the Pakomichi repository; the exact format is fixed by the DNF adapter specification. Pakomichi diagnostics name the failing repository and the recovery command.
4. No automatic fallback: Pakomichi never switches its repositories to `skip_if_unavailable=True`, never disables them, and never edits third-party repository files to restore availability. Disabling or removing a source remains an explicit administrator action.

## Alternatives and reasons for rejection

- **`skip_if_unavailable=True`:** keeps DNF usable during an outage, but R-001 showed that `reinstall` then silently installs another publisher's file on every tested DNF. Rejected by the project owner.
- **Leave the distribution default:** the behaviour would differ between AlmaLinux (`False`) and Fedora or RED OS (`True`) for the same Pakomichi configuration. Rejected.
- **Switch to `True` automatically while the service is down:** reintroduces the silent switch exactly when it matters. Rejected.

## Consequences

ADR-010 remains in force for applications, third-party repository files, staleness, and corruption. For DNF availability it is superseded by point 2: a Pakomichi outage blocks DNF metadata operations on the system until recovery or removal. The release documentation and troubleshooting guide must state this limitation and the recovery command.

The server-side freshness limit for DNF interacts with this decision. ADR-024 point 3 resolves it: after the maximum freshness Pakomichi publishes a signed empty generation instead of answering 503, so an expired source stops offering its packages without blocking DNF for the rest of the system.

## Verification

- Evidence for the decision: R-001 report, DNF tables (`skip_if_unavailable` rows on AlmaLinux 9 and 10, Fedora 44, RED OS 7.3 and 8); R-004 report, T1, T2, T3a, T3, and S7.
- Required before a supported DNF platform is claimed: on each supported distribution build, an E2E test that the generated repository has the effective value `False`; with the Pakomichi repository down, the DNF error names the Pakomichi repository and the installed instance is kept; `pchi doctor` detects a socket in `service-start-limit-hit` and the documented recovery restores it; after uninstalling Pakomichi no Pakomichi `.repo` file remains and distribution DNF operations succeed (N-022). None of these Pakomichi-level tests has been run yet, because the code does not exist.
