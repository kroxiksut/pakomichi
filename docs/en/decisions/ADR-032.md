# ADR-032 — Source model: any source kind, honest evidence levels, configurable policy

**English** · [Русский](../../ru/decisions/ADR-032.md)

**Status:** proposed, draft. The project owner agreed with the approach in principle on 2026-10-22 and expects to revise it more than once. Nothing here is implemented, and nothing changes the 0.1 scope (ADR-014: GitHub Releases only).

If accepted, it would amend:

- ADR-027 point 4 (pre-authorized consent, point 7 below);
- the AGENTS.md rule "never replace an explicit user confirmation for a risky transition with an automatic yes", for the transitions listed in point 7 only.

**Date:** 2026-10-22.

## Context

The R-008 phase A survey ([report](../research/R-008-report.md), [matrix](../../../research/r-008/sources-matrix.tsv)) showed what the current design assumes. It assumes that a source is a GitHub repository, with a numeric repository ID and owner ID, release and asset IDs, a SHA-256 digest from the API, one API host, and GitHub's rate-limit and pagination rules.

The places where developers publish differ on every one of these points:

- other forges;
- vendor and organization APT/DNF repositories;
- PPA, COPR, and OBS;
- catalogs such as WinGet, Scoop, Chocolatey, and Homebrew.

Strict exists only on GitHub, and Attested beyond GitHub only on gitlab.com.

The phase A report recommended keeping hosted APT/DNF repositories and pointer catalogs out of the source model. The project owner rejected that on 2026-10-22.

- **Sources are not restricted.** Vendor repositories (Zabbix, ClickHouse, PostgreSQL), an organization's own repositories, and catalogs such as WinGet are sources too.
- **The user configures the behaviour.** The project ships the most balanced defaults.
- **Repositories already configured on a system are left alone** by default.
- The repository-key level and the behaviour on certified editions are settings, not fixed rules.

The value Pakomichi adds to a vendor repository is not stronger cryptography: the same key that APT/DNF already checks protects it. The value lies elsewhere:

- control over which packages from it are admitted, with system packages protected (R-001, ADR-022);
- a confirmed key change instead of a silent key import;
- detection of rollback and freeze, which upstream metadata does not prevent (no `Valid-Until` in 17 of 17 `InRelease` files; DNF accepts an older signed `repomd.xml`, R-004);
- snapshots and rollback, the same state on every machine, and a recorded origin for every installed package.

## Decision (draft)

1. **Source kinds.** Any of the following may be a source. Each kind has its own adapter, identity, evidence, and network rules. Only GitHub is implemented in 0.1.

   | Group | Kinds |
   |---|---|
   | Forge releases | GitHub, GitLab (gitlab.com and self-managed), Forgejo and Gitea, Bitbucket Cloud, SourceForge, GitFlic, GitVerse, Launchpad downloads |
   | Native repositories | Vendor and organization APT and DNF repositories, PPA, COPR, OBS, hosted repositories |
   | Catalogs | WinGet sources, Scoop buckets, Chocolatey, Homebrew taps |

2. **Identity.** A source is identified by `(kind, instance origin, stable identity)`. Identifiers are unique only within an instance.
   - Forges: repository or project ID and owner ID, with the owner confirmations of migration 0002.
   - Native repositories: URL template and suites or `$releasever`, plus the allowed key fingerprints. A key change is confirmed like an owner transfer.
   - Catalogs: the catalog plus the exact package identifier. Never a name search.

   A kind with a name-only identity is marked as such and can never reach Attested.
3. **Artifacts.** An artifact is `(source, release key or none, source artifact key, digest algorithm, digest)`. The digest algorithm is recorded (SHA-256, SHA-512, SHA3-384); MD5 is never more than a hint.
   - A pin is never rebound.
   - A replaced file and a file added to a pinned release are both mutations (`E_ASSET_MUTATED`).
   - "Same version, new bytes, valid signature from a confirmed key" (a vendor re-signing after a key rotation, a COPR rebuild) is held for an explicit decision. The setting in point 6 controls this.
4. **Levels.** The order is `pinned < signed < attested < strict`, and the ratchet of ADR-027 point 3 applies to it.
   - `signed` means a valid signature by a pinned key, either a publisher key (OpenPGP over the file or its checksums, Authenticode, an embedded RPM signature under ADR-023) or a repository key. The label always says which.
   - Strict stays GitHub-only. Attested is defined by an issuer and its claim template (GitHub Actions; gitlab.com).
   - Claims made by stores, packagers, and catalogs are recorded as evidence, but never raise a level: Snap assertions, the Flathub repository key, Homebrew bottle attestations, and WinGet manifest hashes. A catalog hash that disagrees with a forge digest is a finding (point 6).
   - **Per-release approval** is a separate flag that combines with any level. It is mandatory for `pinned`, as in ADR-027.
5. **Configuration classes.**
   1. **Invariants, not configurable.**
      - The invariants of ADR-027 point 2.
      - A pin is never rebound.
      - Maintainer scripts and MSI custom actions never run during inspection.
      - The control API is never exposed on an external interface.
      - A level never drops silently, and its label is always visible.
   2. **Loosening.** Allowed only by an explicit administrator setting. The setting is shown in `pchi status` and `pchi doctor` and recorded in the decision log, and it is never a default.
   3. **Tightening.** Allowed freely.

   Settings are layered: global defaults, then a profile, then per-source settings (`source_policy`).
6. **Defaults (draft).**

   | Area | Default | Configurable |
   |---|---|---|
   | Packages admitted from a native repository | Only the families chosen when the source is added; system packages are never displaced | Allowlist; the whole repository; displacement only through an explicit decision |
   | Key change of a native repository | Hold until confirmed | Accept automatically when the new key is certified by the old one |
   | Metadata rollback or staleness | Rollback is held; staleness gives a warning | Staleness threshold per source; warn only; hold |
   | Same version, new bytes, valid confirmed key | Hold for a decision | Accept with a log entry |
   | Repositories already configured on the system | Shown, not touched | Offer to move them under Pakomichi; move automatically |
   | Certified editions (RED OS certified, Astra with the closed software environment) | Detected; warning; separate administrator consent | Forbid; pre-authorized consent (point 7) |
   | Catalog hash that disagrees with the forge digest | Warning | Hold |
   | Per-release approval | Only for `pinned` | For any level or source |

7. **Pre-authorized consent.** A transition that needs interactive consent may instead be pre-authorized, but only under all of these conditions:
   - the consent is written in a configuration file owned by root and not writable by others;
   - it names the exact source and transition;
   - it is applied with a decision-log entry, and `pchi status` shows it.

   The eligible transitions (draft):
   - consent to `pinned` for a source;
   - approval of the releases of a source;
   - acceptance of a key change;
   - consent on a certified edition.

   Pre-authorized consent is never available through the status API, the loopback HTTP endpoint, or `--yes`.
8. **Network per source kind.**
   - An allowlist of the API host and the declared download hosts, with DNS vetting on every hop. Integrity comes only from the pinned digest or signature, never from the host.
   - A validated paginator, a rate-limit dialect, and optional validators, with a path for sources that send no validators.
   - Credentials per source instance.
   - The 16 MiB response cap stays.

## Consequences

- **Schema.** The next migrations need a source kind and an instance origin, a nullable or composite release key, an opaque artifact key with a digest algorithm, new evidence types, an identity and a key-change confirmation for native repositories, and the policy settings. None of this is written before acceptance.
- **Code.** The `github` module stays as it is. A source abstraction is introduced only when a second kind is implemented.
  - `src/attest` knows only Strict and Attested (ADR-030, ADR-031). The `signed` level needs its own verifier path and probably its own sub-reasons; it is not assumed to fit under `E_ATTESTATION_INVALID`.
  - This draft does not change the Strict or Attested rules of ADR-030.
- **R-008.** The report's recommendations "not a source kind" and "cross-check only" are withdrawn. Phase B experiments decide the open details.
- **Documents to change on acceptance:**
  - `architecture/trust.md` and `architecture/policy-engine.md`;
  - `specifications/github.md`, which would become one adapter among several;
  - ADR-027 point 4;
  - AGENTS.md.

## Open questions

- The format and location of the configuration, and the names and contents of the profiles.
- Whether a publisher key and a repository key should be two levels instead of one `signed` level with a label.
- The final list of transitions that can be pre-authorized.
- The meaning of "certified edition" detection on each distribution, and the exact wording of the warning.
