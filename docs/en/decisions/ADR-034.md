# ADR-034 — Attestation evidence after R-003: stored bundles and lookup after a transfer

**English** · [Русский](../../ru/decisions/ADR-034.md)

**Status:** accepted by the project owner on 2026-10-23. It refines ADR-030 and the data model (`architecture/data-model.md`) and supersedes nothing. Point 4 records that the condition of ADR-023 point 3 is met.  
**Date:** 2026-10-23.

## Context

R-003 ([report](../research/R-003-report.md)) ended with three facts that ADR-030 does not settle:

- **Attestations do not follow a repository transfer** (finding 6). After the transfer of the owner's test repository to an organization, `attestations/…` returned HTTP 404 for the repository, by name and by ID, and for the new owner, while the previous owner's endpoint `users/{login}/attestations/…` still returned them. The behaviour did not change for about 19 hours. It is undocumented and has been reported (GitHub Community discussion 211055).
- **Only a verification record is kept.** `trust_evidence` stores the result of a verification (`record_json`), not the bundle that was verified. An admitted artifact therefore cannot be verified again: not for an audit, not with a newer verifier, not after a trusted root rotates, and not after a transfer, when the forge no longer serves the bundle.
- **A digest does not identify a source** (finding 4, step 5). The same bytes were attested by two repositories: the fork and the repository that took the old name both published a byte-identical asset with their own valid provenance.

ADR-023 point 3 allowed the Attested exception for unsigned RPMs only after R-003. R-003 completed with PASS on 2026-10-22, and ADR-030 chose the production verifier.

## Decision

1. **Every verified bundle is stored.** The bundles that produced a `TrustEvidence` entry are kept in the blob store by their SHA-256, byte for byte as received, within the limits of ADR-030 (at most 256 KiB each and 16 per digest). The evidence names the digests of its bundles and the trusted root versions it used.
   - Evidence can be verified again from stored data alone. A later check (an audit, `pchi doctor`, a new verifier version, a root rotation) verifies the stored bundles again and never fetches them again for an artifact that is already admitted.
   - The blob store never collects a bundle that evidence references; evidence is append-only, and so are its bundles.
   - A stored bundle that is missing or whose bytes no longer match its digest fails the check with a store integrity reason and is never treated as a pass. The recorded evidence stays as an audit fact, but nothing is admitted again from it.
   - Whether the reference is a column (a new migration) or part of `record_json` is decided by the implementation task; the blob store's collector must see it either way.
2. **Attestation lookup after a transfer.** For a release that has not been admitted yet, the verifier looks for its attestations in this order:
   1. the repository by ID (`/repositories/{id}/attestations/{digest}`);
   2. each owner ID confirmed earlier for the source (migration 0002), newest first: its current login is resolved by ID (`GET /user/{id}` for a user, `GET /organizations/{id}` for an organization), then `users/{login}/attestations/{digest}` or `orgs/{login}/attestations/{digest}` is queried. A stored login is never used, because logins change.
   - The location adds no trust: a bundle from any of these places passes only the full ADR-030 verification, with the pinned repository ID compared first and an owner ID that has been confirmed for the source. An owner that was never confirmed is never queried.
   - If nothing is found, the release is held with `E_EVIDENCE_DOWNGRADE`, not `E_ATTESTATION_INVALID`, and the status explains that attestations are unreachable after a transfer.
   - The extra requests are bounded: one login lookup and one attestation request per confirmed earlier owner, inside the rate limits of `specifications/github.md`.
3. **A digest never identifies a source.** The blob store may keep one copy of bytes that two sources share. Evidence, admission, pins and approvals belong to one source: an artifact of source B whose bytes equal an admitted artifact of source A is admitted for B only with evidence of B's own.
4. **ADR-023 point 3 is unblocked.** Its condition "after R-003" is met (R-003 PASS on 2026-10-22, verifier ADR-030). The other conditions of the Attested exception do not change: verification by the production verifier, binding to the exact SHA-256 of the package, the user's explicit consent for that source, and an effective OS signature policy that permits it. It is implemented in P3-004c.

## Alternatives and reasons for rejection

- **Keep only the verification record:** less storage, but "we once verified it" cannot be checked again by anyone, and a transfer leaves nothing to verify with.
- **Fetch the bundles again at every synchronization:** after a transfer the forge does not return them, and the requests multiply without adding trust.
- **Query the previous owner by its stored login:** a login can be renamed or taken by another account; resolving it by owner ID avoids binding by name, as for repositories.
- **Ask GitHub for nothing and hold every pre-transfer release:** honest, but it drops releases whose evidence is still available from the previous owner and verifies fully.

## Consequences

- `specifications/github.md` gains the lookup order of point 2; `architecture/trust.md` and `architecture/data-model.md` describe stored bundles and per-source evidence.
- P2-004b implements points 1–3 (stored bundles, the collector's references, the lookup order, per-source admission); P3-004c implements the Attested exception for RPM.
- Storage grows by at most 4 MiB per admitted digest in the worst case (16 bundles of 256 KiB); in R-003 a digest had one or two bundles of a few kilobytes.

## Verification

Tests start from a failure and assert the promise to the user (AGENTS.md):

- after the forge stops serving an attestation (HTTP 404 everywhere), an admitted artifact still verifies again offline from its stored bundle;
- a stored bundle changed by one byte, truncated, or missing fails the check again and is reported; it never passes;
- the collector never removes a bundle that evidence references, including under disk pressure;
- after a transfer, a release published before it and not admitted yet is verified from a confirmed earlier owner's endpoint; a bundle found there that names another repository ID or an owner ID that was never confirmed is rejected;
- an earlier owner that renamed its account is still found through its ID; an owner that was never confirmed is never queried;
- nothing found anywhere gives `E_EVIDENCE_DOWNGRADE`, never `E_ATTESTATION_INVALID`, and nothing is admitted;
- a fork or a repository that took the old name, offering bytes identical to an admitted artifact of the original, is not admitted through the original's evidence (R-003 F1, C1).
