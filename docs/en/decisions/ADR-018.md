# ADR-018 — Graded provenance levels below Attested

**English** · [Русский](../../ru/decisions/ADR-018.md)

**Status:** proposed; not binding until the project owner accepts it. ADR-005 remains in force. Accepted in reduced form by ADR-027 (points 4, 5, and 8, the mode limits of point 7, and Pinned behind manual approval of every release); Signed and the quarantine are deferred to 0.2.  
**Date:** 2026-10-19.

## Context

ADR-005 admits a source automatically only in the Strict or Attested mode and rejects pure TOFU for the 0.1 automatic mode. Its context assumes that a significant share of releases carry attestations; this has not been measured. If most repositories that publish `.deb`/`.rpm` files in Releases provide no attestations, Pakomichi cannot connect most of the projects it exists for.

Most protections do not depend on attestations: repository-ID pinning, freezing of accepted digests, family and system-package protection, CAS verification, and signed local indexes. Attestations add two things: protection against a new release uploaded outside the repository's CI (for example, with a stolen token), and proof that the file was built from that repository. Without them, the main new risk is automation itself: a malicious release would reach every connected machine without a human looking at it, which a manual download does not do.

## Proposed decision

1. Strict and Attested stay unchanged.
2. Add the **Signed** level: a publisher signature with a pinned identity. Accepted forms are a Sigstore/cosign signature over the checksum file with a pinned certificate identity (the workflow of that repository), an OpenPGP or minisign signature over `SHA256SUMS` with a key fingerprint confirmed by the user when the source is connected, and the native RPM signature with a pinned key. An unsigned checksum file in the same release is not evidence: it travels through the same channel as the files.
3. Add the **Pinned** level: no cryptographic provenance, only repository-ID pinning and digest freezing. It is enabled per source only after explicit consent that names the risk.
4. These invariants do not depend on the level and are never relaxed: repository-ID pinning; immutability of accepted bytes; family and system-package protection; CAS verification before serving; signed local indexes; the system RPM signature policy (ADR-006, R-002); no re-signing of third-party packages; no disabling of global signature checks; no automatic `yes` for a risky transition.
5. **Ratchet.** The level of a source is a floor. It may rise automatically. A release with weaker evidence than the floor (for example, no attestation after attested releases, or a different signing key) is `held` until the user decides. The level never drops silently.
6. **Quarantine for Pinned.** A new release is published only after a quarantine period (proposed default: 7 days, configurable) during which its assets must not change. A change during the period is `E_ASSET_MUTATED`; a release removed during the period is not published. As an alternative to quarantine, the user approves each release explicitly.
7. **Mode limits.** A Pinned source works only in `supplemental` mode, never in `preferred`, and never displaces a distribution package. Future multi-machine distribution excludes Pinned sources by default.
8. **Visibility.** Each level is served from its own logical repository (ADR-007) with a distinct `Label`/`Origin`, so `apt policy` and `dnf repolist` show the level without `pchi`. The status API and the CLI show the level and the reason for every hold.
9. **Proposed scope.** Signed in 0.1 if the extended R-003 confirms its verification. Pinned in 0.2, or in 0.1 behind explicit opt-in only if R-005 shows that 0.1 is otherwise of little use. The project owner decides.

## Alternatives

- Keep ADR-005 unchanged: the strongest guarantees, but most target repositories may stay `observing`. This remains the right choice if R-005 shows high attestation coverage.
- TOFU with automatic updates and no quarantine: rejected, because it turns a stolen token into silent automatic distribution.
- Treating an unsigned `SHA256SUMS` as evidence: rejected, because it comes through the same channel as the files.
- A project-curated allowlist of trusted repositories: rejected, because it conflicts with having no catalog and with the user's own choice of source (ADR-001).

## Consequences

If accepted, a separate accepted ADR supersedes ADR-005 in part; ADR-005 itself is not rewritten. Both language trees then need updates to `architecture/trust.md`, `architecture/policy-engine.md`, `architecture/states.md`, `architecture/data-model.md` (trust level), `specifications/errors.md` and `ReasonCode` (new codes for an evidence downgrade, a key change, and a pending quarantine or approval; names are fixed in the specification), `specifications/cli-api.md` (consent and approval), `product/scope-0.1.md`, `testing/negative.md`, `testing/release-gate.md`, and core rule 5 in both READMEs. Migration 0002 changes the `trust_evidence.evidence_type` check. R-003 is extended to cosign and OpenPGP checksum signatures.

An opt-in Pinned source can deliver a malicious update. Consent, quarantine, the ratchet, and visible labels reduce that risk; they do not remove it, and the documentation must say so.

## Verification

- R-005 measures which evidence real repositories publish.
- The extended R-003 verifies each Signed form.
- Negative tests: a Pinned source never reaches `preferred`; a release with weaker evidence than the floor is held; an asset change during quarantine produces `E_ASSET_MUTATED`; a signing-key change is held.
