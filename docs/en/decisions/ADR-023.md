# ADR-023 — RPM package trust and signed repository metadata

**English** · [Русский](../../ru/decisions/ADR-023.md)

**Status:** accepted by the project owner on 2026-10-20. ADR-006 and ADR-011 remain in force; this decision refines them and supersedes none. The Attested exception of point 3 waited for R-003; R-003 completed with PASS on 2026-10-22 and ADR-030 chose the verifier, so that condition is met (ADR-034 point 4); the other conditions of point 3 still apply.  
**Date:** 2026-10-20.

## Context

ADR-006 separates metadata signing by the local key from native RPM signature verification, and allows an unsigned attested RPM only where the repository policy permits it and a mandatory system check does not prohibit it. R-002 tested this on AlmaLinux 9.8 (DNF 4.14, RPM 4.16) and Fedora 44 (DNF5 5.4, RPM 6.0) with the same verdict in all 12 cells on both platforms ([R-002 report](../research/R-002-report.md)):

- signed `repomd.xml` and the embedded RPM signature are independent controls: valid metadata does not rescue an unsigned or corrupted package under mandatory policy, and a valid package signature does not rescue invalid metadata;
- an unsigned package was installable only in the explicit modeled-Attested cell, after exact-byte verification, with package checking disabled for that test repository; the same bytes were blocked when `%_pkgverify_level=signature` required a signature;
- DNF 4.14 has neither `pkg_gpgcheck` nor `gpgcheck_policy`; DNF5 uses `pkg_gpgcheck` and `repo_gpgcheck`, and `gpgcheck_policy=legacy` makes `gpgcheck=1` expand only to `pkg_gpgcheck=1`; RPM 6 enforces transaction verification by default;
- a new metadata key is rejected until it is explicitly trusted; losing the metadata private key leaves the signed snapshot valid and stops new signatures until an authenticated backup is restored.

R-005 found no embedded signature in any of the 10 RPMs of its verified subset, including RPMs with verified Strict GitHub evidence ([R-005 report](../research/R-005-report.md), conclusion 5). Without the Attested exception most GitHub RPMs could only be held.

The production attestation verifier is not chosen yet (ADR-017 point 9); R-003 is complete only for its read-only part (`research/r-003/README.md`).

## Decision

1. **Two gates.** Every Pakomichi DNF repository has `repo_gpgcheck=1` with signed `repomd.xml` (ADR-011 key), and package trust is decided separately. Each gate fails closed with its own diagnostic: a metadata failure is never reported as a package problem and the reverse.
2. **Native mode.** A package in Native mode must carry an embedded RPM signature that verifies against the publisher key pinned for the source. Package checking stays on for its repository (`gpgcheck=1` on DNF4, `pkg_gpgcheck=1` on DNF5). Adding a publisher key to the system RPM keyring is allowed only after explicit consent to that key's fingerprint, together with a warning that the key applies system-wide: RPM verifies against one keyring that is not scoped to one repository, so the key is also accepted for packages from any other source. The removal procedure for an imported key is fixed by the DNF adapter specification before Native mode is implemented.
3. **Attested exception (waits for R-003).** An unsigned RPM is published only if all of the following hold: the production attestation verifier has verified it (R-003); the exception is bound to the exact SHA-256 of the package; the user consented explicitly for that source; and the effective OS policy permits unsigned packages. The OS policy permits unsigned packages only when the effective `%_pkgverify_level` (as RPM evaluates it on that system) is neither `signature` nor `all`. The package is served from a separate logical repository of that source that contains only such digest-bound packages; package checking (`gpgcheck`/`pkg_gpgcheck`) is disabled only for that Pakomichi repository, never globally and never for any other repository, so that it does not affect the source's signed packages. If any condition fails, the package is held with `E_SIGNATURE_POLICY`. An attestation never turns an RPM into a natively signed one.
4. **Never global.** Pakomichi never writes a global `gpgcheck=0`, `pkg_gpgcheck=0`, `localpkg_gpgcheck` change, or `%_pkgverify_level` change. A requested global disable is refused before DNF is invoked.
5. **Separate adapters.** DNF4 and DNF5 are separate adapters. DNF4 writes per-repository `gpgcheck` and `repo_gpgcheck` and treats `%_pkgverify_level` as the superior policy; DNF5 writes `pkg_gpgcheck` and `repo_gpgcheck` explicitly and records `gpgcheck_policy`. An adapter never emits a setting that its DNF does not support. After writing, the applier reads back the effective values; a mismatch is `E_ADMIN_APPLY_FAILED`. RPM 6 is a separate supported stack. Each supported distribution build is tested, not inferred from the DNF major version.
6. **Keys.** Publisher keys and the local metadata key are separate and never interchangeable. Metadata key rotation is two-phase: the new key is trusted first (overlap), metadata is then signed with it, and the old key is removed afterwards. Loss of the metadata key never silently creates a new trust root (N-023); recovery uses an authenticated backup or an explicit re-trust by the administrator. Production key custody is not decided by this ADR.
7. **Byte preservation.** Repository metadata is generated only from the final verified RPM bytes, their digest is checked again before publication, and signing never rewrites an RPM.

## Alternatives and reasons for rejection

- **Treat signed metadata as sufficient for unsigned RPMs everywhere:** contradicts mandatory policies and ADR-006.
- **Global `gpgcheck=0` or a lower `%_pkgverify_level`:** weakens the whole system; prohibited by `AGENTS.md`.
- **Re-sign third-party RPMs with a local key:** prohibited by `AGENTS.md` and ADR-006.
- **One adapter for DNF4 and DNF5:** DNF 4.14 does not know the DNF5 settings, and `gpgcheck` has a different meaning under DNF5.
- **Hold every unsigned RPM:** safest, but per R-005 it would hold practically every RPM from GitHub Releases; it remains the behaviour until R-003 completes.

## Consequences

- Until R-003 completes and the production verifier is selected, an unsigned RPM can only be held; only Native-mode RPMs can be published.
- `specifications/dnf.md`, `architecture/trust.md`, `architecture/data-model.md` (package trust mode per artifact), and `testing/negative.md` are updated in both languages. The metadata gate needs no reason code of its own (decided on 2026-10-21 under the owner's delegation): a failure of Pakomichi's own check of the signed metadata is `E_SNAPSHOT_INCONSISTENT` and a package-trust failure is `E_SIGNATURE_POLICY`, so the two gates already report different codes; on the client a metadata failure is the native manager's own error (N-012).
- The owner answered which effective settings count as "OS policy permits unsigned packages" (point 3) on 2026-10-20.
