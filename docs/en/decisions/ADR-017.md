# ADR-017 — Initial Rust operational and packaging model

**English** · [Русский](../../ru/decisions/ADR-017.md)

**Status:** accepted by the project owner. Point 2 superseded by ADR-020. Point 4 superseded in part by ADR-028. Point 7 refined by ADR-035.  
**Date:** 2026-10-19.

## Context

ADR-015 selects Rust but explicitly does not approve a dependency stack, runtime, packaging path, or process model. P0-004 exercised the required mechanisms in an isolated Ubuntu 24.04 WSL2 VM. The evidence is in `docs/en/prototypes/P0-004-stack.md`.

The choice here must preserve ADR-007 socket activation, ADR-009 privilege separation, ADR-011 metadata-only local signing, and ADR-013 SQLite plus CAS. It must not claim that the broader R-001 through R-004 hypotheses have passed.

## Decision

1. Keep Rust 1.94.1 as the initial pinned toolchain. Use Tokio 1.53.3 as the mandatory async runtime for the long-lived network process: GitHub I/O, lazy loopback HTTP, socket activation, timers, cancellation, and bounded coordination. Tokio is not a cross-process contract and is not required in the inspector, signer, migration, or privileged applier. Blocking work uses bounded `spawn_blocking` only when it must remain in-process; hostile package parsing and privileged operations keep their process boundaries. Never hold a lock or SQLite transaction across `.await`.
2. Use `rusqlite 0.40.2` with default features disabled and the distribution SQLite library. Require SQLite 3.37 or newer for `STRICT` tables. Keep a single state owner and use SQLite's online backup API; do not pretend SQLite and the filesystem form one transaction.
3. Use `rpm 0.30.2` with default features disabled for RPM header inspection. Enable payload/compression only in the unprivileged fixture/package builder, not in the production metadata reader.
4. Use `dpkg-deb --field/--info` for DEB metadata behind an unprivileged, resource-limited inspector process. Never invoke install, unpack, or maintainer scripts during inspection.
5. Use `gpgv` for APT `InRelease` and RPM `repomd.xml.asc` verification. A separate signer invokes `gpg` with access only to the local metadata key; downloader, inspector, HTTP reader, and root applier do not receive that key.
6. Use `listenfd 1.0.2` for systemd socket activation. The repository reader accepts only inherited loopback sockets, implements read-only routes, and has no fallback external bind. ADR-007's ordinary-service fallback retains the same loopback listener and protocol.
7. Separate the deployed responsibilities into unprivileged core/state owner, disposable unprivileged package inspector, read-only repository reader, metadata signer, and narrowly privileged administrative applier. IPC messages and filesystem ownership are the authority boundary; network-facing parsing never runs as root.
8. Build the Rust binary once, then assemble native DEB with `dpkg-deb` and RPM with the pinned Rust `rpm` builder. Packages contain the binary and hardened systemd units, but no maintainer script that performs package-manager operations. Installation and removal behavior is verified later in clean VMs.
9. Treat GitHub CLI attestation verification as the independent reference oracle for R-003. Do not make `gh` or the experimental Rust `sigstore` crate a production runtime dependency yet. R-003 must select and cross-check the production verifier before P2-003/P2-004.

## Rejected alternatives

- A root network/parser daemon: conflicts with ADR-009 and was unnecessary in the prototype.
- Bundled SQLite by default: duplicates a system library and complicates security servicing without evidence that the supported distributions need it.
- Executing DEB/RPM scripts to discover metadata: unsafe and unnecessary.
- Tokio in every process, including inspectors and the privileged applier: async adds no benefit to these short-lived or deliberately isolated operations and would blur their authority boundaries.
- Re-signing upstream packages: conflicts with ADR-006 and ADR-011.
- Making GitHub CLI mandatory in the product merely because it passed the reference test: the prototype proves the protocol path, not distribution availability or the final library boundary.

## Consequences

The accepted model is sufficient to begin isolated research and small implementation slices. Exact HTTP, GitHub API, and production attestation crates remain decisions of their dependent tasks, with R-003 as a hard gate for provenance verification. Network concurrency must be bounded and expose backpressure; synchronous SQLite ownership and helper processes must not block Tokio worker threads. Any failure in R-001 through R-004 uses its documented fallback or a superseding ADR; it does not silently weaken this model.

The packages produced by P0-004 are disposable fixtures and are not supported releases. No distro, DNF variant, boot lifecycle, or alpha readiness is asserted.
