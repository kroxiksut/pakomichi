# APT contract

**English** · [Русский](../../ru/specifications/apt.md)

## Adapter outputs

- For each active logical source: a Pakomichi-owned `.sources`/`.list` file (modern deb822 where possible), unique `Origin`, `Label`, `Suite` fields, and `Signed-By` set to *our* keyring; do not use the global `apt-key`/`trusted=yes`. Each provenance level of a source has its own logical repository with a distinct `Label`/`Origin`, so that `apt policy` shows the level (ADR-027).
- A signed `InRelease` (and `Release.gpg` when needed), `Packages`/`Packages.gz`, correct checksums/architectures fields, and time-bounded `Valid-Until` validity equal to the confirmed freshness.
- `Acquire-By-Hash: yes` is mandatory, and every index is served under its `by-hash` path. Only `InRelease`, `Release`, `Release.gpg`, and the plain compatibility index paths are mutable, and they are served only from the current generation (ADR-024).
- An **initially low priority** for the Git source: its `Release` says `NotAutomatic: yes` and `ButAutomaticUpgrades: yes`, so APT gives every version from it priority 100 (as for backports). It never displaces a version from another source, and a package installed from it still gets its upgrades; the protection does not depend on a preferences file. For every activated name, including every member of the activated family, a targeted preference with `Pin-Priority: 990` matched by `Pin: release o=…,l=…` of the source's logical repository (ADR-022 point 3), verified with `apt-cache policy`. `Pin: origin` is not used, because one loopback host serves all logical repositories; a priority of 1000 or higher is never written, because it allows downgrades.

### Index publisher

The publisher (`src/publish/apt.rs`, `apt_store.rs`, `sign.rs`, P3-001) builds one generation of one logical repository at a time.

- **Layout:** `dists/<label>/InRelease`, `dists/<label>/main/binary-<arch>/Packages` with its `by-hash/SHA256/<digest>` alias, and `pool/<sha256>/<package>_<version>_<arch>.deb`. The label is the logical repository's `Label` (`pakomichi-<source>-<level>`); `Suite` and `Codename` equal it, `Origin` is `Pakomichi`, the only component is `main`, and `NotAutomatic: yes` with `ButAutomaticUpgrades: yes` give the repository priority 100. Packages for `all` are listed in the index of every served architecture. The pool name comes from the control fields without the epoch, never from the asset's file name; the digest directory makes it unique.
- **Exact bytes:** each stanza is the package's own control paragraph, field for field, followed by `Filename`, `Size`, and `SHA256` of the stored object. A control paragraph that already carries `Filename`, `Size`, `MD5sum`, `SHA1`, `SHA256`, or `SHA512` is refused (`E_ARTIFACT_MALFORMED`): otherwise a package could point APT at another file. Two different files with one package, version (compared as dpkg compares, so `1.0` equals `1.0-0` and `0:1.0`), and architecture are `E_SOURCE_AMBIGUOUS`; the same bytes offered twice are one entry.
- **Release:** `Date` is the signing time, `Valid-Until` is the last confirmed synchronization plus the maximum freshness, never the signing time plus the maximum freshness. When that moment has passed, nothing is signed (`E_SOURCE_STALE`), and a last confirmation in the future is refused as well. `Acquire-By-Hash: yes` and the `SHA256` list of every index; dates in the form `Fri, 23 Oct 2026 10:00:00 UTC`.
- **Only `InRelease`:** no unsigned `Release` and no `Release.gpg` are published, so APT has no unsigned or detached path to fall back to. `Packages` is published uncompressed; APT fetches exactly the variants `Release` lists.
- **Signing:** the metadata signer runs `gpg --clearsign` with SHA-512 in its own child process with the signer's home directory; the publisher never reads the key (ADR-011, ADR-017 point 5). The check runs `gpgv` against the keyring APT is configured with (`Signed-By`): exactly one valid signature, by the expected primary key, with SHA-256, SHA-384, or SHA-512 (APT on Debian 13 verifies with `sqv`, which refuses SHA-1), and nothing outside the clear-signed message. The text the signature covers must be byte for byte the `Release` that was built.
- **Check before publication:** a separate reader re-reads the signed text and every index: `Origin`, `Label`, `Suite`, `Codename`, `Components`, `Architectures`, `NotAutomatic`, `ButAutomaticUpgrades`, `Acquire-By-Hash`, the dates against the confirmed freshness, every listed index served with its digest and size and every served index listed, every stanza naming a served pool file with its digest and size, and every pool file listed. Every logical repository is signed with the same local key, so APT would accept the `InRelease` of another level of the same source; this check does not.
- **Order:** indexes into the CAS, sign, check, `InRelease` into the CAS, then the generation store writes the manifest and replaces `current` (`delivery-recovery.md`). Any failure before that leaves `current` unchanged, and clients keep the previous generation until its `Valid-Until` (R-004 G9).

### Adapter

The adapter (`src/apt/`, P3-002) writes and reads back the configuration of the sources. The root applier (`pakomichi-applier`, P4-003a) runs it: it receives the desired configuration over `apply.sock`, renders the files itself, and restores the previous configuration when a write fails or APT refuses the result (`architecture/delivery-recovery.md`, "Coordinating the DB and OS files").

- **Files:** the local keyring `/etc/apt/keyrings/pakomichi.gpg`; per source `/etc/apt/sources.list.d/pakomichi-<source>.sources` (deb822, a stanza per logical repository: `URIs: http://127.0.0.1:<port>/<label>`, `Suites: <label>`, `Components: main`, `Signed-By` the local keyring) and `/etc/apt/preferences.d/pakomichi-<source>.pref`: per logical repository with activated names one stanza `Package: <names>`, `Pin: release o=Pakomichi,l=<label>`, `Pin-Priority: 990`. A source without activated names has no preferences file. Package names follow Debian Policy and labels are `[a-z0-9-]`, so no value can add a field (`*` or a line break is refused). One name activated in two logical repositories or in two sources is refused: two 990 pins let the higher version decide. A name is pinned to the level repository that serves its newest published version; for the same version at two levels the stronger one serves it. An older version left in a weaker repository is not pinned. A source added with `--observe`, or a suspended one, gets its repositories but no pins.
- **When a pin is written:** only for a family whose every member APT already lists in the family's repository and whose versions no other source offers in an equal version (compared as dpkg compares). Otherwise the family is held whole: `E_SOURCE_AMBIGUOUS` for an equal version (merged by APT 2.6, listed twice by 2.8+), or pending until the next `apt update` lists the repository. So activation runs in two steps: the source (safe on its own at priority 100), `apt update`, then the pins.
- **Changes:** only the paths above, and only when they hold the bytes Pakomichi last wrote (recorded by the caller). A file someone changed, removed, or created under our name, or a symlink there, is drift: it is reported and neither overwritten nor deleted, and nothing is applied while there is drift. A file that already holds the desired bytes is adopted, which finishes an apply interrupted after its rename. Writes go keyring, preferences, sources; removals go sources, preferences, keyring, so a source never exists without the pins of its activated names. Each write is staged in the target's directory as `.<name>.pakomichi-new~` (a name APT ignores silently), synced, renamed into place, and the directory is synced; a target that changed between planning and applying is not touched.
- **Read-back:** `apt-cache policy <names>` with `LC_ALL=C`. Unsafe, and shown: an activated name whose candidate is not its repository's version at 990 (a lost pin, a foreign preference, a missing source); an equal version in another source; a published, not activated name that would replace another source's version. A higher version of an activated name in another source, including a distribution security update, is a notice naming that source and version; the publisher stays (ADR-022 point 3).

## Constraints

- `apt_preferences` selects a **version**, not an instance of the same version among several URLs. APT 2.6 merges equal versions and source order decides; APT 2.8+ binds the instance only for a fresh install. An equal version with different bytes is `E_SOURCE_AMBIGUOUS` on every APT version, and no pin is claimed to ensure origin safety (R-001, ADR-022 point 1).
- An activated name keeps its publisher when another source, including a distribution security update, later offers a higher version; Pakomichi shows a notice and the switch is an explicit user decision (ADR-022).
- An artifact whose `Provides` or `Replaces` names a member of the system namespace is held in admission (`E_SYSTEM_PACKAGE_CONFLICT`, ADR-022 point 2); APT itself accepts a third-party `Provides` of the C library (R-001 N-008/N-009).
- Do not rename or modify other parties' packages; do not change files of other APT repositories or the global policy. Never require `APT::Get::EnableUpgrade`.
- A binary SHA match of two *available files* may indicate content equivalence; an actually proven SHA is required, not just a name/version.
- Activation happens after reading the `dpkg` inventory and the repositories and after a verified `apt-get -s` transaction simulation, with an understanding of that simulation's limitations.
- If the preferred mode cannot be carried out, remain in `observing`/`held`. Do not change the package's original version for the sake of a pin.
- `apt-get update` exits 0 when a source is offline; source health comes from Pakomichi's own state, never from that exit status (ADR-022 point 6).
- `/var/lib/apt/lists` and `/var/cache/apt/archives` are never trusted input (ADR-025 point 7).

## Ordinary update command

`apt upgrade` and `apt full-upgrade` on Debian and Ubuntu; `apt-get dist-upgrade` on Astra Linux, which refuses `apt upgrade` and `apt-get upgrade` (R-001). The protection above must be shown under each listed command (ADR-022 point 4).

## Astra Linux

The supported level in 0.1 is `base(orel)` on Astra Linux 1.8.6 (ADR-026). The security level, the closed software environment, and integrity control are detected without root; while the closed environment is on, or cannot be ruled out, activation is refused and every artifact is held with `E_EXECUTION_POLICY` (ADR-025). The applier runs at integrity level 63 (a systemd service or the administrator's session); a failed apply from a lower level is reported as an integrity-level problem (`E_SECURITY_CONTEXT`).

## Tests

Only on builds admitted by ADR-026; the first APT targets are Debian 12 and Astra Linux 1.8.6 at `base(orel)`. Two `.deb` files with the same version and different sha, permutation of order and Pin-Priority, a selected package family (main/service), a higher version of an activated name from another source under each ordinary update command, the `Pin: release` match on one loopback host, a system dependency update, loss of the local server, Valid-Until, a replayed older generation.
