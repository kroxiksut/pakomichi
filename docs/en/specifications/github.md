# GitHub Releases adapter contract

**English** · [Русский](../../ru/specifications/github.md)

1. On `source add`, obtain the repo canonical URL, the numerical repository ID, and the owner ID from the API. Reconcile them on every synchronization. A Git rename with unchanged IDs is allowed; owner transfer -> suspend.
   - The first resolution of `owner/name` pins the repository ID and owner ID. The canonical URL is built from the validated owner and name, not copied from `html_url`.
   - Synchronization reconciles through `GET /repositories/{id}`, never through the name. Outcomes: unchanged; **rename** (same repository ID and owner ID, new owner login or repository name) → allowed, the previous address is recorded; **owner transfer** (same repository ID, new owner ID) → suspend with `E_OWNER_TRANSFER`; **replacement** (a different repository ID, for example a new repository created under the old name) → refuse with `E_REPO_ID_CHANGED`, never follow.
   - The pin keeps every owner ID the administrator has confirmed. Confirming a transfer is an explicit administrator action that adds the new owner ID and keeps the earlier ones, because attestations made before the transfer carry the owner ID of their time (R-003, probe case T3). Any owner ID other than the current one is a transfer again, including a move back to an earlier owner. An attestation's owner ID must be one of the confirmed IDs; its repository ID is still compared first. The confirmations are stored append-only (migration 0002, `repository_owner_confirmation`). Recording a transfer confirmation is the only way the stored current owner changes.
   - A lookup by name follows only GitHub's redirect to `https://api.github.com/repositories/{id}`; any other redirect is refused.
   - `gh attestation verify` binds attestations by repository name only, case-insensitively (R-003), so this ID check is always Pakomichi's own.
2. Request only the Releases of the selected repo ID (`/repositories/{id}/releases`, `.../releases/latest`, `.../releases/tags/{tag}`). No Search API for neighboring repos, forks, or alternative owners. Do not use HTML scraping.
3. Release ID/tag/target_commitish are different fields. A verified link to the commit and the release is required wherever the trust mode claims it; `target_commitish` is not a sufficient cryptographic SHA check.
4. First examine the list of assets (name, size, digest, ID) and filter by format/architecture; when necessary, download *only* the candidates and inspect the native metadata. The API may omit an asset `digest` (R-005: 23% of latest releases) or the release `immutable` field; a missing value stays unknown and is never invented.
   - Before any download (`src/inventory`, P2-002): `.deb`/`.rpm` names of the target ecosystem are candidates; source, delta, and debug packages, installer components, archives (including Linux `.tar.gz`), checksums, signatures, SBOMs, and packages for other systems are skipped with a recorded reason; any other name needs review and is never downloaded or published. An empty package-like asset is `E_ARTIFACT_MALFORMED`; an incomplete upload or one over the size limit is skipped.
   - An architecture in the name (`amd64`, `x86_64`, `x64`, Go's `linux_386` and `linux_armv6`, `all`/`noarch`, ...) only skips assets that clearly name another CPU; it never admits one. The native metadata read by the inspector decides: only the target's native architecture or the universal one is admitted, otherwise `E_PLATFORM_UNSUPPORTED`. Foreign architectures (multiarch, multilib) are not targets in 0.1.
   - After download, bytes whose SHA-256 differs from the API `digest` are rejected (`E_ASSET_MUTATED`); without an API digest the CAS digest of the downloaded bytes is the only one. Two different files of one release with the same native name and architecture are both held (`E_SOURCE_AMBIGUOUS`); the same bytes under two names keep the first. An SRPM named like a binary RPM is rejected.
   - An admitted asset is pinned as `(release ID, asset ID, SHA-256)` with its name. A mutable release keeps its release ID, tag, and asset name when an asset is replaced, so a new asset ID or digest under the pinned name, or a changed digest or name under the pinned asset ID, is `E_ASSET_MUTATED`, and the pin is never rebound (R-003 step 3). A pinned asset that is gone admits nothing new; an asset without an API digest is compared after download.
5. Reconcile the digest of the received content; do not treat the API `digest` as an independent signature. Verify the cryptographic attestation, predicate, verified source repo ID, workflow, and exact digest.
   - An attestation outlives the asset it was made for: a replaced file still verifies by its digest (R-003 step 3). An attested digest is accepted only when it equals the API digest of the uploaded asset with that exact name in the release now.
   - Attestations are looked up by repository ID first, then under each owner ID confirmed earlier for the source, newest first, with its current login resolved by ID through `GET /user/{id}`, which answers for users and organizations alike and gives the `type` that chooses `users/{login}/attestations/…` or `orgs/{login}/attestations/…` (checked live on 2026-10-25), never by a stored login: after a transfer GitHub keeps them under the previous owner (R-003 finding 6). The lookup stops at the first place with bundles of the pinned repository ID; an owner that was never confirmed is never asked. A bundle found anywhere passes only the full verification; nothing found is `E_EVIDENCE_DOWNGRADE` (ADR-034 point 2). Every verified bundle is stored and an admitted artifact is never fetched again (ADR-034 point 1).
   - A release attestation found through the tag commit may belong to another release on the same commit (R-003 step 2). Its predicate must name the pinned repository ID as `repositoryId` and `packageId`, a confirmed owner ID, the release ID being checked as `databaseId`, its tag, the tag reference object as a `sha1` subject, and the asset's name with its SHA-256 as the only digest for that name (ADR-030 point 5).
   - The tag reference object is `object.sha` of `GET /repositories/{id}/git/ref/tags/{tag}` exactly as returned, never peeled: the commit for a lightweight tag, the tag object for an annotated tag. For an annotated tag the release attestation does not name the peeled commit, and a lookup by that commit finds nothing (HTTP 404); the lookup goes through the tag reference object (`github/github-mcp-server` v2.0.2, `research/r-003/results/annotated-tag-reference.tsv`). The Attested commit (`.1.13`) is the peeled commit.
6. Stable/beta/alpha channels are an explicit policy and the native version; the `prerelease` flag is mutable and is not the sole criterion.
   - A release is on the stable channel only when the flag is `false` and neither the tag nor any native version names a pre-release (`~`, or a word `alpha`, `beta`, `rc`, `pre`, `preview`, `dev`, `nightly`, `snapshot`, `canary`, `unstable` as a whole run of letters). A stable flag next to such a tag or version is unclear (`E_CHANNEL_UNCLEAR`) and is not offered on the stable channel (example: Win32-OpenSSH `10.4.0.0p1-Preview` with `prerelease: false`, R-007). Following pre-releases is an explicit per-source choice. Drafts are never offered.
7. Record ETag/Last-Modified, use conditional requests, back off according to `Retry-After` and limits; on error, do not substitute the reliable date of the last successful synchronization.
   - Conditional requests use only the `ETag`; `If-Modified-Since` is not sent. `If-None-Match` carries the ETag stored from an earlier **validated** 200 for the same URL and the same credential identity (a one-way token fingerprint, never the token). A 304 confirms "unchanged" only as the answer to such a request and never confirms asset bytes; any other 304 is an error (R-004 conclusion 14). Anonymous 304 responses still consume the rate limit.
   - `x-ratelimit-remaining: 0` stops requests until `x-ratelimit-reset`, even after a successful response. A 403 or 429 with `Retry-After` waits that long; with `x-ratelimit-remaining: 0` it waits until the reset; another 429, or a 403 whose message names a rate limit, waits one minute, doubling on each consecutive refusal. Every wait is capped at 61 minutes. The client never retries by itself; requests during a wait fail locally without a network request.
   - Pagination follows `rel="next"` only to the same origin and path, with the same `per_page` and exactly the next page number, up to a page cap (default 10 pages of 100). A listing that reaches the cap is marked truncated. GitHub's links for `/repositories/{id}/releases` have the form `https://api.github.com/repositories/{id}/releases?per_page={n}&page={m}` (checked live on 2026-10-20), which this rule accepts.
8. HTTP redirect validation on every hop; do not access private IPs/metadata endpoints based on parameters of an untrusted source; limit the sizes/number of assets.
   - The API client talks only to `https://api.github.com`. It resolves the host once per request, refuses the whole answer if any address is loopback, private, link-local (including metadata), shared, benchmarking, documentation, multicast, or reserved, and connects to a vetted address (R-004 conclusion 11).
   - The connection uses TLS 1.2 or 1.3 with SNI `api.github.com` and always verifies the certificate chain and host name against the operating system CA store; there is no option to disable verification. ALPN offers only `http/1.1`. An empty or unusable CA store is a setup error, and a rejected certificate is reported separately from other TLS failures.
   - A response body is limited to 16 MiB before parsing, a page to 100 releases, and a release to 1000 assets. The client requests `Accept-Encoding: identity` and refuses compressed bodies. The token is optional, comes from the caller (a file or an environment variable), and never appears in logs, `Debug` output, URLs, or cache keys.
   - Responses follow ADR-019 point 3: only used fields are deserialized, unknown fields are tolerated, a missing or mistyped required field is an error, and IDs and sizes are integers.
9. No attestation/repo ID problem/file changed → `held`/`rejected`, a log event, no publication.
