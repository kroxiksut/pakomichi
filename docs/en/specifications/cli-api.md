# Proposed CLI and read-only API

**English** · [Русский](../../ru/specifications/cli-api.md)

**Command names approved by the project owner:** the primary short command is `pchi`, the full command is `pakomichi`. Both entry points provide the same CLI, set of arguments, exit codes, and output semantics. Documentation and interactive examples use `pchi` by default. The conflicting name `gitbridge` must not be used.

```text
pchi source add <https-git-url> [--observe] [--workflow <path> --ref tag|refs/heads/<name>]
pchi source list
pchi source inspect <id>
pchi source activate <id> --packages <comma-list> [--policy supplemental|preferred]
pchi source suspend <id>
pchi source remove <id>  # does not remove programs
pchi sync [<id>] [--force]
pchi source allow-pinned <id>  # Pinned consent for one source (ADR-027)
pchi release approve <source-id> <release-id>  # Pinned: approve one release
pchi status [--json]
pchi doctor [--json] [--repair]
pchi cache status
```

The full form replaces only the entry-point name: `pakomichi source list` is equivalent to `pchi source list`. The way the two entry points are delivered (for example, an alias, a symlink, or a separate launcher) is chosen when the package is implemented, but it must not create two diverging CLI implementations.

`add` by itself does not activate a package. Do not use `--yes` to confirm a repo owner transfer, a publisher change, an ambiguity, Pinned consent, or the approval of a Pinned release. Activation requires administrator privileges and prints the original and resulting plan of files/sources.

**Attested signer** (ADR-036 point 1): `source add` looks for the workflow that signs the provenance of the latest release and shows it in the plan; the confirmation stores it with the source. `--workflow` and `--ref` (`tag` for the release tag, or `refs/heads/<name>`) set it explicitly and must agree with what discovery finds. Two different signers refuse the plan. A source without a signer works at Strict and Pinned.

**Family** (ADR-036 point 3): the plan of `source activate` shows the family revision, every name and architecture the source offers, and the names to activate; the confirmation approves the listed names into the next revision. A name the source never offered is refused; a source that was never synchronized is refused with a message to run `pchi sync <id>` first.

**`pchi doctor`** (ADR-021, ADR-022, ADR-024, ADR-025) diagnoses without changing anything: the health of the socket and service units (a socket in `failed` or `service-start-limit-hit` is reported as an outage of the Pakomichi repositories, with the recovery command), the last confirmed synchronization and the age of the served generation per source (`E_SOURCE_STALE`), updates of an activated name offered by another source, the Astra Linux security level, and the name of every failing Pakomichi repository. The exit status of `apt-get update` is never used as a health signal. `--repair` performs only the documented socket recovery (`systemctl reset-failed` for the units, then starting the socket); it requires administrator privileges and an explicit interactive confirmation, does not accept `--yes`, and is never offered through the status API or the loopback HTTP endpoint.

**What `pchi doctor` checks in this build** (P4-001, 2026-10-25). It runs without root and changes nothing; the service not answering is one of its findings, not a reason to stop. Every unit of the installation (the seven sockets and `pakomichi-state.service`): not installed, a socket in `failed` (for the reader socket: the Pakomichi repositories are down, with the `systemctl reset-failed … && systemctl start …` recovery), a socket not listening, a failed state owner. The reader socket's port: 1024 or above is unprotected, and `net.ipv4.ip_unprivileged_port_start` at or below it, or unreadable, is a risk (N-034); a port other than the one the APT sources name (`loopback_port` in the status) is a problem. Every source of the status: never synchronized (a notice), last confirmed longer ago than the maximum freshness of 7 days (`E_SOURCE_STALE`), updates of activated names offered elsewhere (notices), and promises APT does not keep (`apt_problems`). The operating system's execution policy on or not ruled out (`E_EXECUTION_POLICY`). Each finding is printed as `PROBLEM`, `RISK`, or `notice` with its code and a `fix:` line. Exit status: `0` when only notices remain, `1` when a problem or risk is found. Not in this build yet: the age of the served generation, the Astra Linux security level beyond the execution policy, the non-public range of an asset host, and the name of each failing repository.

**`pchi doctor --repair`** (P4-001, owner decision of 2026-10-25) runs in the CLI process itself, never through the state owner: the service runs as an unprivileged user and cannot call systemctl, and the recovery is needed most when the service itself is down. The status and administrative channels have no request for it. Unless the effective user is root it is refused with exit status `1` before anything is read or changed. It then diagnoses as `pchi doctor` does and plans the documented recovery of every installed unit in `failed`: the sockets in a fixed order, then `pakomichi-state.service`, which requires its sockets. For a socket the recovery is `systemctl reset-failed <service> <socket>`, then `systemctl start <socket>`, where `<service>` is what the socket starts: `pakomichi-reader.service` for the reader socket, `pakomichi-state.service` for the status, admin, and fetch sockets, and the instances `pakomichi-<name>@*.service` for the accepting sign, inspect, and apply sockets. For the state owner it is `systemctl reset-failed pakomichi-state.service`, then `systemctl start pakomichi-state.service`. The `fix:` line of `pchi doctor` names the same commands. A socket that is only stopped and a unit that is not installed are reported but not repaired: the documented recovery is for `failed` (ADR-021 point 3.1). With nothing failed it prints `nothing to repair` and exits `0`. Otherwise it prints the commands and runs them only after the administrator types `yes` at a terminal; without a terminal, or with any other answer, it exits `3` and nothing is changed. It runs each command as `/usr/bin/systemctl` with `LC_ALL=C`, stops at the first failure and reports it, then diagnoses again and prints the result. Exit status: `0` when no repaired unit has a problem afterwards, `1` otherwise.

**Pinned level** (ADR-027): `source allow-pinned` names the risk (a compromised publisher account, token, or CI can publish a malicious release that Pakomichi cannot detect) and records consent for that source only; `release approve` shows the release and the exact digests of its artifacts and approves only those digests. Both are administrative, interactive, and refuse `--yes`. A Pinned source can be activated only with `--policy supplemental`. The command names were approved by the project owner on 2026-10-21. `<release-id>` is the forge's release ID: a synchronization whose release waits for approval (`E_RELEASE_APPROVAL_REQUIRED`) prints the exact `pchi release approve <source-id> <release-id>` line. The approval plan lists every artifact of the release not approved yet by file name and SHA-256; the run recomputes it and refuses when the release changed since the plan, then approves exactly those digests and synchronizes the source, so the release is published at the Pinned level and pinned like any other.

**Status API (read-only):** list of sources, identity, mode, provenance level and trust floor, last_successful_sync, trusted snapshot age, list of installed/admissible versions, held reasons (including `E_EVIDENCE_DOWNGRADE` and `E_RELEASE_APPROVAL_REQUIRED`), updates of activated names offered by another source, build variant/confidence, app/package statuses. The JSON response contains `schema_version`, machine-readable `state`, `reason_code`. The status API never accepts consent, approval, or recovery.

**What APT will choose** (ADR-022 point 3, N-027): every source in the status carries `updates_elsewhere` — a newer version of one of its activated names that another source offers, including a distribution security update (`name`, `version`, `offered_by` as APT names that source: URI and suite); the publisher stays until the user switches it — and `apt_problems` — a promise APT does not keep now: an activated name APT would take from elsewhere or does not list yet (`E_ADMIN_APPLY_FAILED`), a version another source also offers (`E_SOURCE_AMBIGUOUS`), a published name that is not activated but would replace a copy installed from another source (`E_ADMIN_APPLY_FAILED`). When APT cannot be asked, every source carries one problem without a name or code that says so: not known is never reported as kept. The state owner reads `apt-cache policy` for the names it answers for when it starts and after every operation, so a status request never starts a process; after `apt update` the view is current again with the next operation (for example `pchi sync`). `pchi status` prints a `notice:` line for each update elsewhere and a `PROBLEM` line for each problem.

The API must not provide `install`, `upgrade`, `change source`, `add repo`, `import key` commands. Applications may show the user an available update, but installation is performed by the native package manager.

**Errors:** for details see `errors.md`. Output contains no secrets/tokens. Do not introduce a false "package is protected" message if only a SHA match has been verified.

## Implementation (P4-001a)

One implementation serves both entry points: `src/cli`, called by the `pchi` and `pakomichi` binaries. Read-only commands (`status`, `source list`, `source inspect`) use `status.sock`; administrative ones (`source add`, `source activate`, `sync`) use `admin.sock` and therefore need root. `doctor --repair` needs root too, but runs `systemctl` itself instead of asking the service (see above).

- **Confirmation:** the CLI asks the server for the plan, prints its summary and every change (kind, target, digest before and after, and the reason codes of the risks), and applies it only after the administrator types `yes` at a terminal. Without a terminal it changes nothing. No command accepts `--yes` or any other way to confirm from its arguments; the plan digest binds the action and its arguments (ADR-029 point 8, ADR-033 point 5).
- **Exit status:** `0` done; `1` refused (by the server, or `doctor --repair` without root), or the operation failed; `2` a usage error; `3` not confirmed, or no terminal to confirm at (nothing was changed); `4` the service did not answer.
- **Defaults:** `source activate` without `--policy` asks for `supplemental`, never `preferred`.
- `PAKOMICHI_RUNTIME_DIR` points the CLI at another socket directory for a test bed; packages never set it.
- **Signer discovery:** `source add` asks GitHub for the latest release, the commit of its tag, and the attestations of at most 20 uploaded assets that carry an API digest, each by the pinned repository ID. An asset without a digest is skipped, because its attestations cannot be looked up without downloading it. The state owner verifies with trusted roots refreshed through TUF at start (`pakomichi-state --tuf-cache DIR`); without them the plan says that nothing was checked and the source gets no signer unless one is named.
- **Synchronization** (`sync`, and every activation): identity by repository ID; every listed release, oldest first, so the trust floor rises as the releases did; assets for the target fetched into the CAS and inspected by the isolated inspector; Strict or Attested evidence of the exact bytes, reused for bytes verified before until the daily full check (`--force` asks the forge about every release now, ADR-037 point 1); the family (proposed on the first synchronization, a name outside it recorded as seen and held with `E_FAMILY_UNAPPROVED`); system namespace, compatibility, and the decision core, each decision logged; a signed generation per level for the activated names; then the APT configuration of every source through the root applier, with a pin only where APT already lists the family and no other source offers an equal version (`apt.md`; a held family is named in the outcome, with `E_SOURCE_AMBIGUOUS` or "run apt update, then pchi sync"). The activation journal follows only a verified apply, and so does the source state: `active` while the verified configuration pins at least one of its names, back to `registered` when none is left; an observed or suspended source keeps its state. An error talking to GitHub, the inspector, or the publisher stops that source's pass and fails the operation; what was published before stays, and the other sources still run.
- `source activate` and `sync` need `pakomichi-state` started with the pipeline arguments (`--publish-root`, `--sign-socket`, `--inspect-socket`, `--apply-socket`, `--keyring`, `--key-fingerprint`, and `--loopback-port`); without them they are refused.
