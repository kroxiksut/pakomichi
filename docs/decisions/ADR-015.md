# ADR-015 — Rust as the implementation language and Rust 1.94.1 as the initial toolchain

**Status:** accepted by the project owner; ecosystem and operational properties remain subject to prototype verification.
**Date:** 2026-10-18.

## Context

Pakomichi needs a language suitable for a long-running Linux service, hostile package-metadata parsing, local IPC, SQLite state, cryptographic verification, and native DEB/RPM packaging. The initial architecture work considered Rust, Go, and other options before implementation. The repository already has a verified local Rust 1.94.1 toolchain and a candidate engineering baseline, but no package-manager or library prototype has yet proved the complete operational design.

The project owner selected Rust as the implementation language. This direct product decision settles the language while preserving the requirement to verify dependencies, packaging, privilege boundaries, and the process model before those operational choices are approved.

## Decision

- Implement Pakomichi in Rust.
- Pin Rust 1.94.1 as the initial compiler and tooling baseline in `rust-toolchain.toml`; update it deliberately through a documented change and a complete quality-gate run.
- Apply `docs/process/rust-engineering.md` as the project engineering baseline.
- Require prototypes to establish the dependency stack, runtime choices, packaging path, and process model before those choices are approved.
- Do not treat language selection as evidence that R-001 through R-004, package-manager behavior, or the proposed Rust libraries have passed verification.

## Alternatives and reasons for rejection

- **Continue treating Rust and Go as equally open choices.** Rejected because the owner has made the product-level language decision and maintaining two hypothetical implementation tracks would create documentation and prototype work without a second intended implementation.
- **Treat language selection as approval of the whole implementation stack.** Rejected because selecting a language does not prove that its OpenPGP, attestation, DEB/RPM inspection, SQLite, systemd, sandboxing, or packaging path satisfies the project constraints.
- **Use an unpinned stable toolchain.** Rejected because builds and lint behavior would change without a reviewed repository change. The pin may be upgraded; it is not a promise to remain on 1.94.1 indefinitely.

## Consequences and limitations

Rust-specific repository scaffolding may be designed against the pinned baseline, but dependent implementation remains blocked by the unfinished prototype criteria and required research. If a required capability cannot be implemented safely in the selected ecosystem, record the prototype result and propose a superseding ADR rather than silently weakening an architectural requirement.

This ADR records a design choice, not a claim that Pakomichi builds, runs, or supports any Linux distribution today.
