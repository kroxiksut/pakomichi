# R-001 — APT/DNF: версия, экземпляр файла и поставщик

Результат этого протокола обязателен до реализации или обещания поведения `preferred` для APT/DNF.

## Гипотеза

При несовпадающих версиях можно адресно задать приоритет. При *одинаковой версии с разными байтами* APT не гарантирует выбор заданного экземпляра через `apt_preferences`. В DNF потребуются независимые тесты `priority`, `includepkgs`, `excludepkgs`, исходного repo и разных вариантов сборки.

## Среды

APT на Debian 12 и 13, Ubuntu 24.04; DNF4 и DNF5 на соответствующих изолированных поддержанных образах. Версии apt, rpm, dnf фиксировать. Ни один сценарий не выполнять на рабочей машине.

## Fixtures

Собрать **синтетические** маленькие DEB/RPM `sampleapp` для версии `1.0-1` в двух вариантах `A`, `B` с различными SHA; дополнительные версии `0.9`, `1.1`; `sampleapp-helper (=1.1)`; фиктивный `Provides` и безопасный тест «зависимость требует недоступную библиотеку». Два подписанных собственными лабораторными ключами репозитория, отдельные pin/repo ID.

## Протокол

1. Провести без Pakomichi обычный `apt-cache policy sampleapp`, `apt-get -s install sampleapp`, фактический download-only и сверить SHA при двух источниках, меняя порядок и pin.
2. Проверить explicit apt source preference при разных версиях и что меняется при равной версии; подтвердить документацию, не заявлять то, чего не показал опыт.
3. Для DNF4/DNF5: `repolist`, candidate info, package download, cache hash при приоритетах 10/90, при фильтрах и --disableexcludes; сначала не устанавливать на host.
4. Повторить для установленной версии и `upgrade`, для удаления первого репозитория и при последующем появлении системной версии.
5. Проверить зависимости двух пакетов семейства, удаление базового пакета и upgrade системной зависимости; убедиться, что Pakomichi policy не позволяет неявную смену издателя (или формально обозначить предел).
6. Записать, какие native config primitives поддерживают именно заданное поведение; приложить файлы и hash артефактов.

## Приёмка / решение

PASS если механизмы выбора для поддерживаемых конфликтов известны, а для равных версий безопасное `observing/hold` детерминировано и подтверждено испытаниями. Не требуем гарантировать невыразимую привязку к другому экземпляру.

**Fallback:** при конфликте, который native manager не может безопасно разрешить, не публиковать конфликтующий пакет в active repo. Остальные семейства обслуживать.
