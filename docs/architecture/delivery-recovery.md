# Доставка, снимки, доступность и восстановление

## Основной путь

Служба на loopback с активацией через systemd socket (где поддерживается). Один процесс обслуживает *логические* APT/RPM-репозитории каждого Git-источника. Отдельный административный IPC. Не считать локальный HTTP защищённым без криптографически подписанных индексов.

## Неизменяемые поколения

1. Создать staging снимок из проверенных `eligible` артефактов.
2. Записать все пакеты/хеши/индексы; генерация APT `Packages`, `Release`, `InRelease` и RPM `repodata` из тех же файлов.
3. Подписать метаданные *после* полного построения.
4. Выполнить самопроверку: пути, digest, даты, ссылки и подписи.
5. `fsync` содержимого/каталогов, атомарно переключить активное поколение на том же FS.
6. Удерживать старые поколения, пока возможны запросы и ссылки; сборка мусора по достижимости, а не по возрасту одного файла.

Для APT включить `Acquire-By-Hash`; для RPM сохранить `repomd.xml` и связанные по уникальным URL версии metadata. Пути файлов пакетов неизменяемы и content-addressed.

## Ленивое скачивание

Если пакет ещё не в CAS: получить **зафиксированный asset** по API/проверенному маршруту, с ограничением размера, протокола и DNS/редиректов; на каждый переход перепроверять адрес, исключить localhost/private/metadata endpoints; писать во временный файл; проверить хеш и attestation против принятого evidence; только потом отдавать байты. При невозможности буферизации целиком — не стримить непроверенные данные как готовый доверенный файл.

## Freshness (начальные предложенные настройки)

Обычная проверка: раз в 6 ч; ручное `sync --force`; предупреждение об устаревании после 24 ч; максимальная свежесть 7 суток после последней успешной подтверждённой синхронизации. `304`/условный ответ может подтверждать отсутствие изменений, если проверено согласно API/политике. **Никакого обновления срока при сетевой ошибке.** `Valid-Until` должен соответствовать реально подтверждённой свежести. Настройки изменяемы, значения проверить R-004.

## Сбой сервиса

Чужие системные источники и установленные приложения не трогаем. APT/DNF может получить ошибку нашего источника; не скрывать отказ. Если GitHub недоступен, уже сохранённые пакеты могут быть доступны при действительном снимке. Если ключ/DB/индекс повреждены — fail closed для нашего источника.

## Координация БД и файлов ОС

SQLite transaction + запись intent в `AdminOperation` + staging файлов конфигурации + атомарные rename + проверка + commit outcome. После сбоя сравнить фактические хеши и применить безопасный rollback/finish. SQLite и `/etc/apt` **не** являются общей атомарной транзакцией.

## Удаление

Удаляем только принадлежащие Pakomichi system config files и локальные ключи/кеш в соответствии с режимом удаления; приложения и файлы третьих сторон остаются. При purge source не оставляем dangling репозиторных файлов.
