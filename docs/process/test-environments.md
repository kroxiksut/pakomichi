# Изолированные среды, VM и секреты исследований

## Граница

APT/DNF, systemd, установка пакетов, изменение репозиториев, root-сценарии и сетевые интеграции Pakomichi проверяются только в контейнере или VM. Windows-хост разработки не является испытательной Linux-системой и не должен изменяться ради прохождения R-исследования.

## Воспроизводимость среды

Для каждого прогона фиксировать:

- R/task ID и точную цель;
- provider, образ, digest/версию и архитектуру;
- версии ядра, APT/DNF/RPM/systemd и проверяющих инструментов;
- команды создания, подготовки, запуска и восстановления;
- исходное состояние репозиториев и snapshot;
- ожидаемый и фактический результат, включая отрицательный сценарий;
- SHA-256 синтетических пакетов, индексов и проверяемых файлов.

Образ или snapshot не является доказательством сам по себе. Доказательство — воспроизводимый протокол и сохранённый обезличенный вывод.

## Локальные каталоги

- `.vm-local/` — диски VM, snapshots, SSH state, cloud-init с локальными значениями и provider metadata.
- `.research-local/` — сырые логи, временные пакеты, ключевые кольца и промежуточные результаты.
- `.env` — локальные пути и credentials; публичный перечень имён переменных находится в `.env.example`.

Эти пути исключены из Git. Долговечное доказательство переносится в связанный R-отчёт или специально созданный каталог результатов только после удаления секретов, персональных данных, внутренних адресов и лишних сведений о хосте.

## Credentials и ключи

- Использовать минимально необходимые права и отдельные учётные данные лаборатории.
- GitHub token не должен попадать в URL, командную строку, shell history, журнал агента или сохранённый HTTP trace.
- SSH-ключи для VM не использовать как release/signing keys.
- Для APT/RPM создавать отдельные тестовые ключи с явной маркировкой `TEST ONLY`; private key остаётся локальным.
- Публичный ключ или синтетический fixture можно коммитить только когда его тестовое назначение очевидно и private counterpart не используется вне лаборатории.
- Перед публикацией логов проверять заголовки HTTP, окружение, абсолютные пути, имена пользователей, адреса и содержимое конфигурации.

## Жизненный цикл прогона

1. Создать или восстановить известную чистую среду.
2. Проверить baseline до изменения.
3. Сохранить snapshot перед рискованным переходом.
4. Выполнить только сценарий связанного R/task; не чинить образ системными миграциями ради зелёного результата.
5. Провести отрицательный сценарий и проверить отсутствие изменений чужих источников.
6. Экспортировать обезличенные команды, версии, hashes и вывод.
7. Восстановить или уничтожить лабораторную среду после сохранения доказательств.

Если VM не поддерживает требуемую возможность правдоподобно, результат `INCONCLUSIVE` и используется предусмотренный fallback; требование не ослабляется.
