# Отчёт R-006 — Защищённые уровни Astra Linux

[English](../../en/research/R-006-report.md) · **Русский**

- **Дата / исполнитель:** 19.10.2026 и 20.10.2026, программный агент по поручению владельца проекта; протокол: [R-006](R-006-astra-protected-modes.md).
- **Итог:** **PASS** для Astra Linux 1.8.6: все уровни матрицы протокола, установка с низкого и высокого уровня целостности, матрица APT из R-001 на `maximum(smolensk)` и определение уровня без root. Astra Linux 1.7, режимы подписи `external_sig` и xattr, блокировки интерпретаторов и `chmod +x` не покрыты (см. «Не покрыто»).
- **Главный факт:** при включённой замкнутой программной среде APT и dpkg без ошибок ставят пакет с неподписанным ELF, но программа не запускается. Собственный ключ в Astra Linux 1.8 сделать доверенным нельзя: дополнительный ключ принимается, только если он подписан корневым ключом Astra Linux.

## Окружение

Astra Linux 1.8.6, ядро 6.12.77-1-generic, `digsig_verif` и `parsec` 6.12.77-1.astra1+ci11, gnupg 2.2.40-1.1.astra7b1, bsign 1.5.11. Работа шла на существующей установленной ВМ в отдельном снимке VirtualBox, сделанном перед экспериментом (вместо клона, с одобрения владельца проекта). После эксперимента ВМ возвращена к этому снимку, а сам снимок удалён; другие снимки ВМ не затрагивались. Второй сеанс (20.10.2026) повторил это с новым снимком; `strace` 6.1 был установлен из репозитория Astra Linux только внутри этого снимка, и там же `apt-get update` обновил собственные списки пакетов ВМ; и то и другое отброшено вместе со снимком. Доступ только по SSH; адреса и учётные данные здесь не записаны.

## Фикстуры и команды

`research/r-006/build-deb.sh` собирает в Debian 12-сборщике из R-001 два пакета TEST ONLY: `sampleapp-elf` (статический ELF из нескольких строк ассемблера, печатает одну строку, не подписан для Astra Linux) и `sampleapp-script` (без исполняемых файлов, `postinst` пишет маркер). `research/r-006/run-level.sh LABEL` копирует на цель `level-check.sh` и пакеты и запускает его через sudo; скрипт записывает уровень от имени обычного пользователя и от root, ставит пакеты через `dpkg -i` и `apt-get install ./…`, запускает ELF от пользователя и от root, проверяет маркер `postinst` и удаляет оба пакета. `research/r-006/low-ilev-check.sh` собирает команды ячейки с низким уровнем целостности; сама ячейка выполнялась 20.10.2026 равнозначным разовым root-фрагментом, а файл скрипта написан по нему после прогона и как файл не запускался. Матрица APT из R-001 прогонялась без изменений командой `research/r-001/run-remote.sh astra186-smolensk apt` (изолированный режим, см. [отчёт R-001](R-001-report.md)). Сырые журналы: `.research-local/r-006/` и `.research-local/r-001/runs/astra186-smolensk/`; ячейки матрицы — в `research/r-006/results/astra186-smolensk-apt.tsv`.

Уровни переключались командами `astra-modeswitch set`, `astra-digsig-control enable`, `astra-mic-control enable` и `astra-mac-control enable`, каждый раз с перезагрузкой.

## Результаты

| Ячейка | Уровень / настройки | `dpkg -i` / `apt-get install` | Запуск неподписанного ELF (пользователь, root) | `postinst` |
|---|---|---|---|---|
| 1 | `base(orel)`, всё выключено | exit 0 | запускается, exit 0 | выполнен |
| 2 | `advanced(voronezh)`, замкнутая среда включена | exit 0, статус `install ok installed` | **`Segmentation fault`, exit 139**; в ядре `DIGSIG:[ERROR] type=NOT_SIGNED` | выполнен |
| 3 | `advanced(voronezh)`, замкнутая среда + контроль целостности | exit 0 | exit 139, `NOT_SIGNED` | выполнен |
| 4 | `maximum(smolensk)`, замкнутая среда + контроль целостности + управление доступом | exit 0 | exit 139, `NOT_SIGNED` | выполнен |
| 5 | `advanced(voronezh)`, замкнутая среда + контроль целостности; команда выполняется на уровне целостности 0 | **отказ**: `dpkg -i` exit 2, `apt-get install` exit 100, ничего не установлено | — | не выполнялся |
| 6 | `maximum(smolensk)`, все три защиты; матрица APT из R-001, 26 ячеек | во всех ячейках те же решения, что на `base(orel)` | — | — |

Ячейка 6 сравнивалась с прогоном R-001 на той же системе на уровне `base(orel)`: кандидат, скачанный экземпляр, установленный вариант и загруженные URL совпадают во всех 26 ячейках, включая равные версии, pin, `dist-upgrade`, удалённый и недоступный источник, отсутствующую зависимость и негативные случаи N-008 и N-009. Единственное отличие — порядок двух параллельных загрузок в одной ячейке. APT 2.6.1.astra3, dpkg 1.21.22.astra.se7, parsec-base 3.11+ci183.

Другие наблюдения:

- На уровне `base(orel)` команда `astra-digsig-control enable` отказывает: `This function can't be enabled in current astra mode`. Само переключение уровня ничего не включает; каждая защита включается отдельно и действует после перезагрузки.
- Отказ не выглядит как понятная ошибка: процесс убивается сигналом `SIGSEGV` (exit 139), а причина есть только в журнале ядра.
- ELF, подписанный `bsign` лабораторным ключом RSA-4096: `BAD_SIGNATURE`, `Unknown algo type 0`. Подписанный лабораторным ключом ГОСТ Р 34.10-2012, который положен в `/etc/digsig/keys` (initramfs пересобран, перезагрузка): ядро отказалось загрузить ключ (`verify_key_signature: ERROR, Key signature was not found`, `LOADKEY ... res=fail`), а программа получила `BAD_SIGNATURE`, `signer key was not found`. Ключи Astra Linux в `/etc/digsig/` — ГОСТ Р 34.10-2012 (алгоритм OpenPGP 35).
- После включения контроля целостности SSH-сеанс администратора работает с `ILevel=63(High)`, поэтому `dpkg` и APT работают как прежде. Службы systemd, включая службу с `DynamicUser=yes`, тоже запускаются с `ILevel=63`.
- Установка с низкого уровня целостности (ячейка 5, `advanced(voronezh)` с включёнными замкнутой средой и контролем целостности; 20.10.2026). Процесс, запущенный от root командой `pdp-exec -l 0:0`, работает с `ILevel=0(Low)`. С этого уровня `dpkg -i` завершается ошибкой `dpkg: error: required read/write access to the dpkg database directory /var/lib/dpkg` (exit 2), а `apt-get install ./…` разрешает транзакцию и затем падает с `E: Sub-process /usr/bin/dpkg returned an error code (2)` (exit 100); ничего не устанавливается. Запись в `/etc/apt/sources.list.d/` и `/var/lib/` отклоняется с `Permission denied`. `apt-get update` проходит, запись в `/var/cache/apt/archives/` тоже, потому что `/var/lib/apt/lists`, `/var/cache/apt/archives`, `/var/log` и `/tmp` имеют метку целостности `Low`, а `/etc`, `/etc/apt`, `/usr/bin` и `/var/lib/dpkg` — `High`. Тот же `dpkg -i` из сеанса администратора на уровне 63 проходит.
- `sumic` для этой проверки не подходит: он всегда запускает команду через `/usr/bin/fly-xephyr.sh` и `xinit` в изолированном дисплее Xephyr, поэтому без графического сеанса завершается с кодом 1, а его вывод об ошибке до вызывающего не доходит. Это и было причиной неопределённого результата первой попытки 19.10.2026 (прослежено `strace` из репозитория Astra Linux, установленным только внутри снимка эксперимента). На базовом уровне `sumic` отказывает с сообщением, что работает только на усиленном и максимальном уровнях.
- Определение без root: читаются `astra-modeswitch get`/`getname`, `/etc/digsig/digsig_initramfs.conf` (`DIGSIG_ELF_MODE`), `/proc/cmdline` (`parsec.max_ilev`, `parsec.mac`), `pdp-id` и `/sys/module/parsec/parameters/max_ilev`. Файл `digsig` показывает настройку для следующей загрузки, а не обязательно текущее состояние. `astra-*-control is-enabled|status` и `/sys/module/digsig_verif/parameters/*` требуют root.

## Не покрыто

- Astra Linux 1.7 — исключена из R-006 решением владельца проекта от 20.10.2026. Её защищённые уровни могут вести себя иначе, и выводить их поведение из 1.8.6 нельзя; поэтому Astra Linux 1.7 на защищённом уровне не входит ни в какое заявление о поддержке.
- Режимы подписи `external_sig` и xattr. Они меняют место хранения подписи, а не то, кто может подписывать, поэтому снятия требования к корневому ключу от них не ожидается; это не показано.
- Блокировки интерпретаторов, `chmod +x` и `bash`, которые могут ломать maintainer scripts. Во всех ячейках они были выключены.
- Матрица APT из R-001 на `advanced(voronezh)`; она прогонялась только на `maximum(smolensk)`, который включает все защиты `voronezh`.

## Выводы и требуемые изменения решений

1. В Astra Linux с включённой замкнутой программной средой пакет из GitHub-релиза с исполняемыми файлами доставляется и ставится без единой ошибки, но так и не запускается. Pakomichi должен определять замкнутую среду и удерживать такие артефакты с понятной причиной, а не предлагать их как обычные обновления.
2. Pakomichi не может это исправить и не должен пытаться: чтобы сделать доверенным дополнительный ключ, нужен ключ, подписанный корневым ключом Astra Linux, а подпись или правка сторонних файлов запрещена `AGENTS.md`.
3. Собственные исполняемые файлы Pakomichi на такой системе не запустятся, пока они не подписаны через цепочку ключей Astra Linux. До тех пор защищённые уровни с замкнутой средой — вне матрицы поддержки 0.1.
4. Определение должно опираться на непривилегированные признаки: уровень — из `astra-modeswitch`, замкнутая среда — из `/etc/digsig/digsig_initramfs.conf`, контроль целостности — из `/sys/module/parsec/parameters/max_ilev`. Поскольку файл `digsig` до перезагрузки может расходиться с текущим состоянием, расхождение нужно считать как «замкнутая среда включена».
5. Падение с `SIGSEGV` после установки при включённой замкнутой среде нельзя диагностировать как дефект пакета.
6. При включённом контроле целостности ставить пакеты может только процесс с высоким уровнем целостности. Административный applier Pakomichi должен работать как служба systemd или из сеанса администратора (оба работают на уровне 63), а неудачную установку с более низкого уровня должен сообщать как проблему уровня целостности, а не как ошибку пакета. Компонент с низким уровнем целостности, например сетевой загрузчик, не может ставить пакеты и менять источники APT, что соответствует разделению привилегий ADR-009.
7. На уровне целостности 0 процесс всё ещё может писать в `/var/lib/apt/lists` и `/var/cache/apt/archives`. Pakomichi не должен считать списки или кеш APT в Astra Linux доверенным входом и должен опираться на проверку подписей и хешей APT и на собственные digest CAS.
8. Защищённые уровни не меняют выбор версии и экземпляра в APT. Выводы R-001 и hold по ADR-004 применимы к Astra Linux 1.8.6 на всех уровнях без изменений.
