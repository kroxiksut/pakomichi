# R-007 — Windows: MSI-пакеты из GitHub Releases через локальный источник WinGet

[English](../../en/research/R-007-windows-msi-winget.md) · **Русский**

Этот протокол не блокирует 0.1. ADR-014 оставляет WinGet вне alpha и требует исследовать его параллельно; этот документ — вход для такого исследования и для будущего ADR. Ничто здесь не является заявлением о поддержке или реализованной возможностью.

## Пример, с которого всё началось

Типичный сегодняшний способ поставить OpenSSH для Windows на Windows 10 — так его 21.10.2026 предложил владельцу проекта ассистент:

```powershell
Invoke-WebRequest https://github.com/PowerShell/Win32-OpenSSH/releases/download/10.4.0.0p1-Preview/OpenSSH-Win64-v10.4.0.0.msi -OutFile C:\temp\OpenSSH-Win64.msi -UseBasicParsing
Start-Process msiexec -ArgumentList '/i C:\temp\OpenSSH-Win64.msi /qn' -Wait
```

Факты о релизе из GitHub API (только чтение), наблюдались 21.10.2026:

| Факт | Значение | Следствие для рецепта |
|---|---|---|
| Repository ID / owner ID | `42125787` / `11524380` | Рецепт опирается на имя в URL; переименование, передача или пересоздание репозитория не обнаруживаются |
| Релиз `10.4.0.0p1-Preview` | опубликован 20.10.2026, `immutable=false`, `prerelease=false` | Файлы можно подменить; в теге «Preview», а флаг релиза говорит «стабильный», поэтому канал нельзя определять только по флагу |
| Digest файла | `sha256:788d8643…6ac9` для `OpenSSH-Win64-v10.4.0.0.msi` | GitHub его публикует, но рецепт его не сверяет |
| Аттестации для этого digest | нет (`404`) | Нет доказательств ни Strict, ни Attested (ADR-005) |
| Другие файлы | `OpenSSH-{ARM,ARM64,Win32,Win64}.zip` и `*_Symbols.zip` | Архитектура и формат выбираются вручную |

Другие проблемы рецепта: подпись Authenticode у MSI не проверяется; `msiexec /qn` молча и с правами администратора выполняет custom actions пакета; версия, архитектура и путь зашиты в команду, поэтому для следующего релиза нужен новый URL, написанный вручную, и нигде не записано, откуда взялась установленная программа; в Windows 10 уже есть OpenSSH как дополнительный компонент (`OpenSSH.Client`, `OpenSSH.Server` в `System32`), и MSI ставит рядом вторую копию — два `ssh` в `PATH` и возможный конфликт службы `sshd`.

Та же задача с Pakomichi — как это могло бы выглядеть, если исследование подтвердится (гипотетически; таких команд нет):

```text
pchi source add https://github.com/PowerShell/Win32-OpenSSH
  → pinned: repository ID 42125787, owner ID 11524380
pchi source inspect <id>
  → MSI for x64, x86, ARM64 (zip and symbol archives ignored)
  → no attestations, release not immutable: Strict and Attested unavailable
  → Authenticode signature: <signer, status>         (analogue of Native mode, ADR-023)
  → custom actions: <list from the MSI tables>       (shown, not executed)
  → conflict: Windows capability OpenSSH.Client is installed → observing
pchi source activate <id> --packages openssh          (explicit decision about the built-in capability)
winget upgrade                                        (later releases arrive through the native manager)
```

Что это упростило бы: не нужно вручную писать URL, версию и архитектуру; digest файла и подпись издателя проверяются до того, как что-либо запустится; подменённый файл (`E_ASSET_MUTATED`), сменившийся repository ID или передача владельцу блокируются; custom actions и конфликт с системным компонентом видны до решения; следующие релизы приходят обычной командой обновления; у установленной программы записано происхождение.

Если пакет издателя уже есть в общем репозитории WinGet, правильный ответ — использовать его, как PPA или COPR в Linux. Pakomichi — для проектов, которые публикуют пакеты только в Releases.

## Гипотеза

Модель Pakomichi переносится на Windows со следующим соответствием; каждая часть требует доказательств:

| Linux (0.1) | Windows (гипотеза) |
|---|---|
| Локальный подписанный репозиторий APT/DNF на loopback | Локальный источник WinGet, который отдаёт Pakomichi |
| Штатный менеджер: `apt upgrade`, `dnf upgrade` | `winget upgrade` |
| Встроенная подпись RPM, режим Native (ADR-023) | Подпись Authenticode у MSI, проверяемая по закреплённой для источника идентичности издателя |
| Maintainer scripts, проверяемые без запуска (ADR-028) | Custom actions MSI, читаемые из таблиц MSI без установки |
| Системное пространство имён (ADR-022) | Дополнительные компоненты Windows и пакеты, установленные из других источников WinGet |
| Политика контроля исполнения (`E_EXECUTION_POLICY`) | Smart App Control, политики WDAC/AppLocker |

## Вопросы

1. Какие типы источников WinGet может предоставить локальная служба: REST-источник (требует ли он HTTPS и как тогда доверять сертификату на loopback) или заранее проиндексированный источник (нужен ли подписанный `source.msix` и каким ключом)? Может ли `winget source add` зарегистрировать его без ослабления собственных проверок WinGet и нужны ли для этого права администратора?
2. Сохраняет ли `winget upgrade` источник установленного пакета, или более высокая версия из другого источника (общий репозиторий, Microsoft Store) может его перехватить — как R-001 показал для APT и DNF?
3. Authenticode: какие поля достаточно надёжно идентифицируют издателя для закрепления (subject, цепочка издателя, отпечаток сертификата при продлении), как ведут себя метка времени и отзыв без сети и какой подписью на самом деле подписан MSI Win32-OpenSSH.
4. Можно ли прочитать таблицы MSI (`Property`, `CustomAction`, `InstallExecuteSequence`, `File`) без установки и без запуска чего-либо — ограниченным парсером в непривилегированном процессе?
5. Как без прав администратора определить, что ту же программу уже даёт компонент Windows или пакет из другого источника.
6. Как быть с MSIX и переносимыми zip-файлами — или они остаются вне рамок.

## Окружение

Отдельная ВМ `pakomichi-win-*` в `V:\VMs\pakomichi-*`, никогда не ВМ владельца или NetRuleRouter, по правилам аренды ВМ; только NAT; снимок перед каждым экспериментом; версии WinGet и Windows записываются. Используются только тестовые сертификаты подписи, и они никогда не добавляются на хост. Ни один эксперимент не выполняется на машине разработчика.

## Фикстуры

Собираются вне цели, TEST ONLY, никогда не публикуются: MSI, подписанный лабораторным сертификатом; тот же MSI без подписи; MSI с изменённым после подписи байтом; MSI с custom action; более высокая версия того же продукта из второго тестового источника. Сторонние MSI (например, Win32-OpenSSH) проверяются только на чтение и ставятся только в ВМ.

## Негативные случаи

- MSI, digest которого отличается от принятого, никогда не предлагается.
- MSI без подписи или с неверной подписью не предлагается как Native.
- Во время проверки не выполняется ни одна custom action.
- Сторонние источники WinGet, глобальные настройки WinGet и политика безопасности Windows не меняются; нет инструкций отключить проверку.
- Встроенный компонент Windows никогда не вытесняется автоматически.

## Результат

PASS: задокументированные ответы на вопросы 1–5 с командами и журналами из ВМ и предложенный ADR для соответствия Windows. **Fallback:** если WinGet не может использовать локальный источник без ослабления своих проверок, Windows остаётся вне рамок, а часть «только чтение» (закрепление, проверка digest и Authenticode, проверка MSI) рассматривается только как отдельная команда проверки `pchi`, которая ничего не устанавливает.
