# R-008 — Источники пакетов: где публикуют разработчики и что это значит для архитектуры

[English](../../en/research/R-008-package-sources.md) · **Русский**

Протокол обследует места, где разработчики публикуют устанавливаемые программы и откуда Pakomichi могла бы брать пакеты. GitHub Releases — первый и единственный источник 0.1 (ADR-014). Обзор проверяет, какие допущения текущего устройства выдерживают выход за пределы GitHub, чтобы модель источника можно было зафиксировать до того, как от неё будет зависеть больше кода. Это входные данные для ADR о модели источника. Протокол не меняет рамки 0.1 и не решает, какие источники будут реализованы и когда.

## Вопросы

1. **Идентичность.** Какой устойчивый идентификатор есть у проекта и его владельца: числовой ID, UUID или только путь? Что происходит при переименовании, передаче, удалении и повторном использовании имени? Можно ли разрешить имя в устойчивый идентификатор до первого использования, и следуют ли перенаправления за переносом?
2. **Модель выпуска.** Какой объект публикует источник? Выпуск с тегом и файлами, версионированный пакет, манифест-указатель (URL производителя и хеш) или подписанные метаданные репозитория (репозиторий APT или RPM)? Какие поля есть (ID, digest, размер, время)? Может ли содержимое под той же версией или тем же именем измениться, и фиксирует ли это что-нибудь?
3. **Доказательства.** Что потребитель может проверить?
   - аттестации: издатель и claims идентичности;
   - отдельные подписи: OpenPGP, minisign, cosign;
   - ключи метаданных репозитория;
   - подписи платформы: Authenticode, утверждения магазина;
   - только контрольные суммы.

   Как каждое из них соотносится с уровнями доверия Strict и Attested (ADR-005), Pinned (ADR-027) и Native (ADR-023)?
4. **Форматы.** Какие форматы артефактов несёт источник (`.deb`, `.rpm`, MSI, MSIX, AppImage, Flatpak, архивы), и какие из них доходят до APT или DNF без преобразования (AGENTS.md запрещает превращать `.tar.gz` в `.deb`)?
5. **API.** Требования к аутентификации, анонимные лимиты, условные запросы, постраничная выдача, перенаправления между хостами и ограничения размера — в сравнении с правилами клиента из `specifications/github.md`, пункты 7–8, и ADR-019.
6. **Граница обнаружения.** Можно ли пользоваться источником, не сканируя соседние проекты, форки или одноимённые проекты (AGENTS.md)?
7. **Влияние на архитектуру.** Какие части текущего устройства привязаны к GitHub и потребуют общей формы? Кандидаты:
   - `forge_repository` (`repository_id`, `owner_id`, `canonical_url`) и подтверждения владельцев миграции 0002;
   - `release_record.forge_release_id` и ID файла в `artifact`;
   - типы доказательств в `trust_evidence`;
   - `github::PinnedRepository` и закрепление файла;
   - кэш ETag и список разрешённых сетевых хостов;
   - сами уровни доверия.

## Источники в рамках

| Группа | Источники |
|---|---|
| Площадки с выпусками | GitHub; GitLab (gitlab.com и self-managed); Bitbucket Cloud и Data Center; Gitea и Forgejo (Codeberg); Azure DevOps; SourceForge, включая проекты на SVN; Launchpad (хостинг кода); GitFlic и GitVerse (российские площадки) |
| Репозитории пакетов от разработчиков | Репозитории APT и YUM/DNF производителей; Launchpad PPA; Fedora COPR; openSUSE Build Service; хостинги репозиториев (packagecloud, Cloudsmith, Gemfury); публичные экземпляры Artifactory и Nexus |
| Пакеты приложений и магазины | Flathub; Snap Store; AppImage в выпусках и каталогах |
| Каталоги Windows и macOS | Общий репозиторий WinGet и REST-источники; Chocolatey; Scoop; Microsoft Store; формулы, bottle, cask и tap Homebrew |
| Реестры | GitHub Packages; GitLab Package Registry; OCI-реестры с артефактами, отличными от контейнеров; языковые реестры (crates.io, PyPI, npm) для сравнения, включая инструменты, которые ставят из них бинарные файлы выпусков |
| Российские дистрибутивы | Репозитории Astra Linux и РЕД ОС и программы производителей для стороннего ПО на них — как цели, потребляющие перечисленные источники |

Во время обзора список может расти. Каждый добавленный источник записывается вместе с причиной добавления.

## Метод

Выполнять по `docs/ru/process/test-environments.md`. Обзор от начала до конца только читает: учётные записи не создаются, ничего не публикуется, ни один запрос не пишет ни в один сервис.

1. **Фаза A, документы и анонимное чтение.**
   - Для каждого источника записать ответы на вопросы 1–6 по документации, со ссылкой и датой чтения. Утверждения из единственного вторичного источника отмечаются как неподтверждённые.
   - Если у источника есть публичный API, анонимно прочитать метаданные хотя бы одного реального публичного проекта и сохранить ответ в `.research-local/r-008/`.
   - Пакеты на машине разработки не скачиваются и не устанавливаются.
2. **Фаза B, эксперименты, для каждой платформы нужно одобрение владельца.**
   - Вопросы, которые фаза A оставила открытыми, становятся экспериментами в одноразовых тестовых проектах или локальных стендах.
   - Тестовый проект на публичном сервисе владелец создаёт со своей учётной записи, как для R-003.
   - Эксперименты на Windows идут по R-007 и выполняются в ВМ.
   - У каждого эксперимента свои команды, журналы и таблица результатов.
3. **Синтез.** Матрица «источники × вопросы 1–6», затем список мест устройства из вопроса 7 с изменением, которое нужно каждому.

## Результат и PASS

- Отчёт с матрицей и списком по архитектуре, EN и RU. Очищенный TSV матрицы лежит в `research/r-008/`, сырые ответы — в `.research-local/r-008/`.
- **PASS** (протокола, а не какой-либо возможности продукта), когда выполнено всё:
  - у каждого источника в рамках есть строка с ответами на вопросы 1–6 со ссылками либо явное «неизвестно» с запланированным экспериментом;
  - по каждому месту устройства из вопроса 7 есть решение: остаётся как есть, нуждается в общей форме (описанной) или ещё открыто (с экспериментом, который его решит);
  - набросан хотя бы один предлагаемый ADR о модели источника, либо отчёт объясняет, почему он не нужен.
- **INCONCLUSIVE**, если у какой-то группы источников нет строки или список по архитектуре не удаётся довести до конца.

## Ограничения и запасной вариант

Никаких issue, pull request, комментариев и отправки пакетов во внешние проекты. Вне одноразовой среды не меняются ни файлы репозиториев хоста, ни сторонние источники лабораторной системы. Ничто здесь не является заявлением о поддержке. Если обзор не дал результата, устройство 0.1 с привязкой к GitHub остаётся как есть, а каждый следующий источник начинается со своей исследовательской задачи.
