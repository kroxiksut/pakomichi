# R-005 — Доказательства происхождения, которые публикуют реальные репозитории

[English](../../en/research/R-005-provenance-survey.md) · **Русский**

Этот протокол измеряет, какие доказательства происхождения на самом деле публикуют репозитории, выкладывающие `.deb`/`.rpm` в GitHub Releases. Его результат — входные данные для решения по предложенному ADR-018; он не проверяет поведение Pakomichi и сам по себе не меняет ADR-005.

## Вопросы

1. Для последнего стабильного релиза с файлами `.deb` или `.rpm`: какая доля репозиториев предоставляет (а) доказательство Strict (immutable release с release attestation); (б) attestation конкретного файла (Attested); (в) подпись издателя с проверяемой идентичностью (подпись или bundle cosign над контрольными суммами, подпись OpenPGP или minisign над контрольными суммами, подписанный RPM); (г) только неподписанные контрольные суммы; (д) ничего?
2. Стабилен ли уровень на последних трёх стабильных релизах или он понижается?
3. Какую долю выборки 0.1 покроет со Strict + Attested, с добавлением Signed и с добавлением Pinned?

## Выборка

- Не меньше 100 репозиториев не меньше чем из двух независимых источников, у каждого записана дата отбора: (1) размещённые на GitHub позиции каталога `deb-get`, используемые только как список имён; (2) поиск репозиториев GitHub (например, по темам `linux`, `cli` или `desktop` с не менее чем 100 звёздами), отфильтрованный до репозиториев, в недавних релизах которых есть файлы `.deb` или `.rpm`. Можно добавить read-only примеры из `docs/ru/product/scenarios.md`.
- Исключить форки и архивные репозитории и записать каждое исключение. Список кандидатов — только артефакт исследования: не переходить к форкам и другим репозиториям того же владельца и не превращать список в функцию поиска.
- Записать известные смещения: каталог `deb-get` смещён к популярным desktop-приложениям, поиск — к проектам со звёздами.

## Метод

Выполнять в изолированной среде согласно `docs/ru/process/test-environments.md`. GitHub token, если используется, берётся только из переменной окружения или локального файла с минимальными правами, никогда из аргумента команды или журнала.

1. **Фаза A, только метаданные (GitHub REST API).** Для каждого репозитория записать ID репозитория, признаки fork и archived и последние три релиза без prerelease: `immutable`, имена и размеры файлов и поле `digest` файла, если оно есть. Для каждого digest `.deb`/`.rpm` выполнить запрос `GET /repos/{owner}/{repo}/attestations/sha256:{digest}`. Записать файлы подписей и контрольных сумм по имени: `*.sig`, `*.pem`, `*.bundle`, `*.sigstore.json`, `*.asc`, `*.minisig`, `SHA256SUMS*`, `checksums*.txt`. Фаза A фиксирует только заявленные доказательства.
2. **Фаза B, проверка подмножества (не меньше 20 репозиториев, в VM или контейнере).** Скачать файлы и проверить: attestations — через `gh attestation verify` (эталонный оракул ADR-017); подписи cosign, OpenPGP и minisign — по идентичности или ключу, опубликованным проектом; подписи RPM — через `rpm -K`. Не устанавливать пакеты, не распаковывать и не запускать maintainer scripts. Файл с именем `.sig` не является доказательством, пока подпись не проверена.
3. Отнести каждый репозиторий к наивысшему уровню, подтверждённому в фазе B или заявленному в фазе A, и раздельно показать заявленные и проверенные уровни.

## Результат и PASS

- Таблица по репозиториям: репозиторий, ID, источник отбора, проверенные релизы, уровень каждого релиза и заметки; итоги по уровням, отдельно для заявленных и проверенных; понижения уровня между релизами.
- Скрипт и список кандидатов сохраняются как воспроизводимые команды; сырой JSON остаётся в `.research-local/`.
- Отчёт пишется нейтрально: отсутствие attestations — наблюдение о доказательствах, а не оценка проекта.
- **PASS** (протокола, а не продукта): не меньше 100 репозиториев не меньше чем из двух источников, воспроизводимые список и команды и подмножество фазы B не меньше 20 репозиториев. **INCONCLUSIVE**, если выборка меньше или лимиты API не позволяют завершить.

## Ограничения и fallback

В рамках исследования не открывать issues и pull requests во внешних репозиториях, не форкать и не изменять их. При результате INCONCLUSIVE ADR-018 остаётся предложенным, а ADR-005 — в силе.
