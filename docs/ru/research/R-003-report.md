# Отчёт R-003 — GitHub Strict/Attested и идентичность репозитория

[English](../../en/research/R-003-report.md) · **Русский**

- **Дата / исполнитель:** 20.10.2026 (часть только для чтения) и 22.10.2026 (тестовый репозиторий владельца), перепроверка после передачи только чтением и захват имени 23.10.2026, программный агент по поручению владельца проекта; протокол: [R-003](R-003-github-provenance.md).
- **Итог:** **PASS**. Выполнены все семь шагов протокола, фактические JSON-результаты проверки и точные правила сопоставления сохранены. Промышленный верификатор выбран отдельно в [ADR-030](../decisions/ADR-030.md). Наблюдение после передачи репозитория (шаг 4, находка 6) не изменилось при перепроверке только чтением примерно через 19 часов.
- **Главный факт:** имя репозитория никогда не идентифицирует источник GitHub. После переименования проверка проходит со старым именем и не проходит с новым. После того как старое имя занимает другой репозиторий, артефакты оригинала по-прежнему проходят `--repo` с этим именем. Форк в том же аккаунте имеет owner ID оригинала. Все эти случаи различает только repository ID, и Pakomichi должен сравнивать его сам, потому что `gh attestation verify` связывает по имени.

Fine-grained токен с доступом на чтение публичных данных и без permissions получали только онлайн-кейсы `gh`, через окружение из файла с правами 0600 и никогда в командной строке. ## Подтверждённые правила сопоставления

- **Strict** требует проверенную release attestation, у предиката которой `repositoryId` и `ownerId` равны закреплённым ID, `databaseId` равен ID проверяемого релиза, `tag` равен его тегу, subject `sha1` равен объекту ссылки на тег, а subject с именем asset имеет SHA-256 этого asset. Флаг `immutable` из API обязателен, но сам по себе доказательством не является. Объект ссылки на тег — `object.sha` из `git/ref/tags/{tag}` как есть, без разыменования. Теги R-003 лёгкие, поэтому там это коммит тега. Последующая проверка аннотированного тега чтением (`github/github-mcp-server` v2.0.2, `research/r-003/results/annotated-tag-reference.tsv`) показала, что subject `sha1` — объект тега, а не коммит после разыменования, и что поиск по коммиту после разыменования возвращает HTTP 404.
- **Attested** требует проверенную build provenance, у сертификата которой claims `.1.15` (repository ID) и `.1.17` (owner ID) равны закреплённым ID, с точными workflow подписанта, ref, коммитом, issuer `https://token.actions.githubusercontent.com` и раннером GitHub. Кроме того, digest артефакта должен быть равен digest из API для asset, который лежит в релизе сейчас.
- **Закрепление (pin):** `(release ID, asset ID, SHA-256)`. По имени или одному release ID замену asset не обнаружить.
- **Поиск источника:** через `/repositories/{id}`, никогда по сохранённому имени.

## Находки

1. **Поиск release attestation по коммиту неоднозначен.** Для `v0.2.0-mutable` запрос `attestations/sha1:<коммит тега>` вернул release attestation `v0.1.0`, потому что оба тега указывают на один коммит. Наличие release attestation для коммита тега не делает релиз Strict: `databaseId` и `tag` должны совпадать с проверяемым релизом. `gh release verify` обрабатывает это правильно.
2. **Аттестация переживает свой asset.** После замены удалённый asset по-прежнему проходит проверку онлайн по digest и офлайн со своим bundle. Валидная аттестация не доказывает, что файл сейчас лежит в релизе.
3. **Переименование сохраняет ID и ломает привязку по имени.** В сертификатах остаётся старый URI репозитория. `--repo <новое имя>` не проходит, старое имя проходит; `gh release verify` следует за репозиторием и проходит под обоими именами.
4. **Занятие старого имени.** Когда старое имя принадлежит другому репозиторию, артефакты оригинала по-прежнему проходят `--repo` с этим именем. Только repository ID показывает, что имя теперь чужое. Верно и обратное (захват имени, 23.10.2026): новый `kroxiksut/pchi-test` выпустил собственный аттестованный `v0.3.0-mutable` (release `421346102`, asset `667564280`), и его принимают `--repo kroxiksut/pchi-test`, путь workflow подписанта оригинала и `--owner kroxiksut`. При сверке с закреплением оригинала совпадают owner ID, digest, ref, коммит, раннер и issuer; отличается только repository ID (`1429307950` ≠ `1429109739`, `results/owner-step4-capture-reconcile-vs-pin.tsv`). Его asset байт-в-байт совпадает с asset форка из шага 5 (`d3c6baed…`), так что и digest источник не определяет.
5. **Передача меняет owner ID**, поэтому owner ID в сертификатах больше не совпадает: источник приостанавливается до повторного подтверждения владельцем (ADR-030, пункт 5). Аттестации, сделанные до передачи, сохраняют старый owner ID, поэтому повторное подтверждение источника должно добавлять новый owner ID к старому, а не заменять его; иначе релизы, выпущенные до передачи, перестают проходить проверку (кейсы пробы T1–T3 ниже).
6. **Аттестации не последовали за передачей.** Через несколько минут после передачи и без изменений при перепроверках только чтением примерно через 40 минут, через 4 часа и через 19 часов `attestations/…` возвращал HTTP 404 для репозитория (по имени и по `/repositories/1429109739`) и для организации, а `users/kroxiksut/attestations/…` по-прежнему возвращал оба bundle с repository ID `1429109739`. `gh release verify` для immutable `v0.1.0` не проходил, хотя релиз остался `immutable=True`. Bundle, сохранённые до передачи, по-прежнему проходят офлайн. Поэтому Strict не должен зависеть от получения аттестаций после передачи: он опирается на bundle, сохранённые при допуске.
7. **Один owner ID форк не отсекает.** Форк лежит в аккаунте, где создавался оригинал, поэтому его owner ID совпадает с owner ID в прежних сертификатах оригинала, и `--owner kroxiksut` принимает asset форка. Различает их только repository ID.
8. **Ограничения эталона `gh` 2.95.0.** `gh attestation verify` не может проверить release attestation офлайн: политика по умолчанию ждёт идентичность workflow, а с `--cert-identity https://dotcom.releases.github.com` требует `SourceRepositoryOwnerURI`, которого в сертификате нет. `gh release verify*` работает только онлайн и требует авторизации даже для публичных репозиториев. Разные отказы выдаются одним и тем же `verifying with issuer "sigstore.dev"`.
9. **Provenance фиксирует ref запуска.** Workflow, запущенный на `main`, записывает `refs/heads/main`, а не тег релиза. Политика, закрепляющая source ref, должна использовать ref запуска.
10. **Воспроизводимость.** Сборка фикстуры без маркера варианта байт-в-байт одинакова на dpkg 1.21.23 (Debian 12) и в раннере CI, поэтому локальная пересборка точно предсказала digest замены в CI.

## Промышленный верификатор

В R-003 `gh` использовался только как эталон (ADR-017, пункт 9). Промышленный верификатор определён в [ADR-030](../decisions/ADR-030.md): `sigstore-verify` `=0.15.0` за интерфейсом Pakomichi. Strict использует корень GitHub, SAN `https://dotcom.releases.github.com` и метку времени RFC 3161 и связывает только по предикату `repositoryId`/`packageId`/`ownerId`/`databaseId`/`tag`. Attested использует корень public-good и связывает по Fulcio `.1.15`/`.1.17`. Его проба на записанных доказательствах R-003 — `research/r-003/results/verifier-probe-cases.tsv` (60 из 60 как ожидалось) и `research/r-003/results/verifier-probe-oracle.tsv` (`gh` 2.103.0 совпадает в 26 из 26 сравнимых кейсов Attested; для переименованного репозитория `gh` отказывает по имени, а ADR-030 пропускает по ID с уведомлением). Перекрёстная проверка этого верификатора на bundle шагов 4 и 5 (P1-003c, `research/r-003/verifier-probe-owner.sh`, результаты `research/r-003/results/verifier-probe-owner.tsv`) дала 13 из 13 как ожидалось, включая захват имени, добавленный 23.10.2026:

| Кейс | Вход и закрепление | Проба ADR-030 | `gh` 2.103.0 офлайн |
|---|---|---|---|
| R1, R2 | после переименования; закреплённые ID `1429109739`/`2264172`, ожидаемое имя `kroxiksut/pchi-test-renamed` | Strict и Attested PASS с уведомлением `name_changed` | отклоняет (связывает старое имя из сертификата) |

## Не покрыто

- Находка 6 держалась около 19 часов после передачи (`results/owner-step4-transfer-attestation-lookup.tsv`) и считается устойчивым поведением; GitHub его не документирует, а восстанавливает ли поиск обратная передача, не проверялось.
- Приватные репозитории, GitHub Enterprise, переиспользуемые workflow подписанта из другого репозитория и клиент TUF (P2-003) вне этого протокола.

## Вывод

Доказано: Strict и Attested можно решать офлайн по сохранённым bundle с точной привязкой по ID; флаг immutable, имя, owner ID или release ID по отдельности недостаточны, что показано реальными контрпримерами. Находка 6 держалась без изменений около 19 часов и считается устойчивой; Strict к этому уже готов, потому что опирается на bundle, сохранённые при допуске. Что она постоянна, не доказано.

**Затронутые ADR:** ADR-005 и ADR-027 (уровни доверия и Pinned), ADR-017, пункт 9 (только эталон), ADR-030 (промышленный верификатор, согласуется с этими результатами).

**Запасной вариант:** без изменений относительно протокола. Если режим нельзя проверить на данном хосте или в проекте, этот режим отключается, и источник остаётся в наблюдении.

**Необходимые доработки:** реализация Pinned и храповика (P2-011a) хранит `(release ID, asset ID, SHA-256)` и требует digest текущего asset; реализация Strict и Attested сверяет `databaseId`/`tag` с релизом и ищет источники только по repository ID; после передачи источник приостанавливается, повторное подтверждение добавляет новый owner ID к закреплённому набору, а проверка использует bundle, сохранённые при допуске.
