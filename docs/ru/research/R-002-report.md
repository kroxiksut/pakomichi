# Отчёт R-002 — подписи RPM, подписанный repodata и Attested

[English](../../en/research/R-002-report.md) · **Русский**

- **Дата / исполнитель:** 2026-10-20, программный агент по запросу владельца проекта; протокол: [R-002](R-002-rpm-signatures.md).
- **Результат:** **PASS** по критерию R-002 на проверенных версиях DNF4 и DNF5. Неподписанный RPM был принят только в явной моделируемой Attested-ячейке, после проверки точных байтов и при отключённой проверке пакетов для этого тестового репозитория. Те же байты были отклонены, когда нативная политика требовала встроенную подпись RPM.
- **Не доказано:** другие сборки дистрибутивов, production GitHub attestations, production-хранение ключей и восстановление на установленной системе. Проверяющий attestation и все ключи — лабораторные fixtures. Результаты задают ограничения для ADR-006 и P1-005, но не реализуют их.

## Окружения и изоляция

Каждая цель была свежим импортом WSL2 из уже закешированного R-001 образа с digest pin. Windows-host, его репозитории, личная Ubuntu владельца и окружения других исследований не изменялись.

| Платформа | Закреплённый образ | Стек пакетов | Исходная effective policy |
|---|---|---|---|
| AlmaLinux 9.8 | `almalinux:9`, manifest `sha256:dc973f4d…`, layer `sha256:b4183c2…` | DNF 4.14.0, RPM 4.16.1.3 | `gpgcheck=1`, `repo_gpgcheck=0`, `localpkg_gpgcheck=0`, `%_pkgverify_level=digest`; `pkg_gpgcheck` и `gpgcheck_policy` не поддерживаются |
| Fedora 44 | `fedora:44`, manifest `sha256:be9d65e2…`, layer `sha256:59259e16…` | DNF5 5.4.3.0, RPM 6.0.2 | `gpgcheck=1`, `pkg_gpgcheck=1`, `repo_gpgcheck=0`, `localpkg_gpgcheck=0`, `gpgcheck_policy=legacy`, `%_pkgverify_level=digest` |

Обе цели использовали ядро WSL2 `6.18.40.1-microsoft-standard-WSL2`. Метаданные репозитория раздавались только через loopback цели. Репозитории дистрибутива применялись только для установки тестовых инструментов; каждая операция матрицы использовала изолированный `reposdir` только с R-002. Сырые команды и вывод остались в игнорируемом `.research-local/r-002/runs/`; очищенные результаты находятся в `research/r-002/results/`.

**Ограничение:** цели разделяют ядро и сетевое пространство имён host. Этого достаточно для решений package manager о проверке, но это не доказательство поведения загрузки, systemd, SELinux, protected mode или потери питания.

## Fixtures

Builder AlmaLinux 9 из R-001 создал все fixtures из одной спецификации:

- `signed.rpm` и `unsigned.rpm` имеют одинаковый payload digest (`7c210c52…`), но разные хеши полного файла; первый содержит подпись заголовка RPM v4 RSA/SHA-256, второй не подписан;
- `corrupted.rpm` отличается байтом подписи и после импорта открытого ключа определяется как `BAD`;
- `attested.rpm` побайтно совпадает с `unsigned.rpm`; его моделируемый attestation привязан к точному SHA-256 `fe920655…`;
- `unconfirmed.rpm` имеет другие байты и payload, поэтому не может случайно использовать этот attestation;
- ни один fixture не содержит scriptlets.

Builder репозиториев создал корректные и некорректные detached-подписи `repomd.xml`, репозиторий с заменённым после генерации метаданных RPM и репозитории ротации ключей метаданных A/B. `metadata-signer-invariance.tsv` доказывает, что подписание и переподписание метаданных не изменило RPM: все четыре копии совпадают с `signed.rpm` по SHA-256 `dc7fa40b…`.

## Результаты

Обе платформы дали одинаковые вердикты во всех 12 ячейках:

| Ячейка | DNF4 | DNF5 | Подтверждённое свойство |
|---|---:|---:|---|
| Корректная подпись RPM + корректные подписанные метаданные, обязательная политика | allow | allow | Пакет с доверенной встроенной подписью устанавливается. |
| Неподписанный RPM + корректные подписанные метаданные, обязательная политика | block | block | Подписанные метаданные не заменяют подпись пакета. |
| Моделируемый Attested unsigned RPM, явно разрешённый режим | allow | allow | Исключение для точных байтов и одного source представимо там, где его разрешает политика ОС. |
| Тот же Attested RPM, обязательная политика | block | block | Attestation не ослабляет обязательную нативную политику подписи. |
| Другой неподтверждённый unsigned RPM | block до DNF | block до DNF | Adapter не создаёт исключение после несовпадения attestation. |
| Испорченная встроенная подпись | block | block | Повреждение подписи закрывает путь. |
| Некорректный `repomd.xml.asc` | block | block | Аутентификация метаданных независима и обязательна. |
| RPM заменён после генерации метаданных | block | block | Хеши репозитория привязывают байты пакета. |
| Запрос глобального `gpgcheck=0` | отказ, exit 64 | отказ, exit 64 | DNF не запускается для запроса глобального отключения. |
| Ключ метаданных A доверен | allow metadata | allow metadata | Исходный ключ работает. |
| Ключ метаданных B до добавления trust | block | block | Ротация не доверяет новый ключ молча. |
| Ключ метаданных B после явного trust | allow metadata | allow metadata | Явная ротация восстанавливает доступность. |

Полные записи command/exit/verdict находятся в `alma9.tsv` и `fedora44.tsv`. `rpmkeys` независимо определяет подписанный fixture как корректный, unsigned fixtures как содержащие только digest, а corrupted fixture как некорректный на обеих версиях RPM.

### Синтаксис политики зависит от версии

- **DNF4:** проверка пакетов репозитория задаётся `gpgcheck=1`; DNF 4.14 не предоставляет `pkg_gpgcheck` и `gpgcheck_policy`. В эксперименте обязательной политики `%_pkgverify_level=signature` служит backstop транзакции RPM и отклоняет unsigned-байты, даже если отдельный тестовый репозиторий запрашивает `gpgcheck=0`.
- **DNF5:** `pkg_gpgcheck` — однозначная настройка пакетов. При исходном `gpgcheck_policy=legacy` параметр `gpgcheck=1` разворачивается только в `pkg_gpgcheck=1`; он не подразумевает `repo_gpgcheck` или `localpkg_gpgcheck`. Поэтому стенд явно записывает `pkg_gpgcheck` и независимо сохраняет `repo_gpgcheck=1`. Это соответствует upstream [справочнику конфигурации DNF5](https://dnf5.readthedocs.io/en/latest/dnf5.conf.5.html#gpgcheck-label).
- **RPM 6:** RPM 6 по умолчанию требует проверку транзакции и поддерживает пакеты RPM v4, но владельцем проверки пакетов из репозитория остаётся DNF5. Переход на RPM 6 нужно считать отдельным поддерживаемым стеком; см. upstream [release notes RPM 6.0](https://rpm.org/releases/6.0.0).

Исходные значения — наблюдения, а не безопасные defaults для создаваемых репозиториев. Pakomichi должен записывать настройки пакета и метаданных, на которые опирается, а затем считывать effective-конфигурацию.

## Ротация и восстановление ключа метаданных

Ротация двухфазна: метаданные ключа B отклоняются, пока настроен только A, и принимаются лишь после явного добавления B в trust. Потеря закрытого ключа метаданных не делает уже подписанный snapshot некорректным (`exit 0`), не позволяет создать новую подпись (`exit 2`) и разрешает новую проверяемую подпись только после восстановления лабораторной резервной копии (`exit 0`). Это проверка механизма, а не утверждение production-дизайна хранения.

## Выводы

1. Гипотеза подтверждена на DNF 4.14/RPM 4.16 и DNF5 5.4/RPM 6.0: аутентификация метаданных репозитория и встроенная аутентификация RPM — отдельные контроли.
2. GitHub attestation может разрешить явное исключение только тогда, когда effective policy ОС допускает unsigned-пакеты. Он не превращает RPM в нативно подписанный и не отменяет обязательную подпись.
3. `repo_gpgcheck=1` требуется независимо. Корректная подпись пакета не спасает некорректные метаданные, а корректные метаданные не спасают unsigned или corrupted пакет при обязательной политике.
4. Глобальную проверку нельзя отключать. Любое допустимое исключение ограничивается одним проверенным source и одним точным digest пакета после явного согласия.
5. Подписание метаданных сохраняет байты RPM. Хеши репозитория обнаруживают замену пакета после генерации метаданных.

## Обязательные изменения решений (вход для ADR-006 и P1-005)

- Определить независимые gate для подписанного `repomd.xml` и package-level trust. Оба fail closed с раздельной диагностикой.
- В режиме `Native` требовать встроенную подпись RPM. В режиме `Attested` разрешать unsigned RPM только после production-проверки attestation, привязки точного digest, явного согласия пользователя и подтверждения, что effective policy ОС допускает исключение; иначе Hold.
- Никогда не записывать глобальный `gpgcheck=0`. Исключения DNF4, если разрешены, задаются для отдельного репозитория и подчиняются `%_pkgverify_level`. DNF5 использует явные `pkg_gpgcheck` и `repo_gpgcheck` с фиксацией `gpgcheck_policy` и effective-значений.
- Считать DNF4 и DNF5 отдельными adapters. Не выводить неподдерживаемые настройки и проверять каждую поддерживаемую сборку дистрибутива, а не выводить поведение из major version.
- Разделять ключи publisher пакетов и ключи метаданных репозитория. Ротация явно перекрывает trust или подготавливает новый ключ; восстановление требует аутентифицированной резервной копии.
- Генерировать метаданные только из финальных проверенных байтов RPM и повторно проверять digest перед публикацией. Подписание метаданных никогда не должно переписывать RPM.

## Негативные случаи и отклонения

Все обязательные негативные случаи прошли: unsigned при обязательной политике, несовпадение attestation, corrupted RPM signature, некорректная подпись метаданных, замена пакета после метаданных, недоверенный ключ ротации и запрос глобального отключения. Глобальная конфигурация DNF и репозитории host не менялись. Интерактивное подтверждение не автоматизировалось. Scope покрывает два перечисленных upstream-образа дистрибутивов, но не RED OS, protected modes Astra или production attestation infrastructure.
