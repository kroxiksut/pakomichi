# Отчёт R-004 — Активация через сокет, атомарные снимки и отказы

[English](../../en/research/R-004-report.md) · **Русский**

- **Дата / исполнитель:** 20.10.2026, программный агент по поручению владельца проекта; протокол: [R-004](R-004-delivery-failure.md).
- **Итог:** **PASS** для Debian 12 (APT 2.6), AlmaLinux 9 (DNF 4.14) и Fedora 44 (DNF5 5.4) в WSL2 с systemd в роли PID 1, плюс три жёстких отключения питания ВМ с Astra Linux 1.8.6, с изменениями проекта из раздела «Выводы». Принудительный режим SELinux/AppArmor, upstream по TLS и остальные поддерживаемые дистрибутивы не покрыты (см. «Не покрыто»).
- **Главные факты:** при неизменяемых поколениях, адресации индексов и пакетов по содержимому и сохранении старых поколений ни один штатный клиент не принял смешанные метаданные, в том числе около 2 700 параллельных обновлений на трёх целях во время многократных переключений поколений. Любая ошибка источника заканчивалась кодом ошибки, а не частичным или подменённым файлом. DNF нужны две дополнительные защиты, которые не нужны APT: отдельная подпись `repomd.xml.asc` может не совпасть с `repomd.xml` во время переключения, и DNF принимает повторно отданные более старые подписанные метаданные (APT — нет).

## Исследовательский сервер и стенд

`research/r-004/snapshotd` — исследовательский сервер на Rust 1.94.1, который использует только crate из стека ADR-017 (Tokio, `listenfd`, `rusqlite` с системной SQLite, `sha2`, `libc`). Он собран офлайн из кеша P0-004 на AlmaLinux 9, чтобы один бинарный файл работал на всех целях. Это исследовательский инструмент, а не рабочий код. Он реализует модель ADR-008:

- хранилище с адресацией по содержимому `objects/<sha256>`; объект пишется во временный файл, проверяются размер и SHA-256, затем `fsync`, режим только для чтения, переименование и `fsync` каталога;
- неизменяемые поколения: по одному манифесту на поколение (путь, digest, размер, необязательный URL источника) и атомарно заменяемый указатель `current` для каждого логического репозитория; один процесс обслуживает несколько логических репозиториев по адресам `/<repo>/<path>`;
- публикатор, который до переключения `current` проверяет подпись `InRelease` или `repomd.xml.asc` через `gpgv`, каждую ссылку из `Release`, `Packages`, `repomd.xml` и `primary.xml` на опубликованные байты, а также `Date`/`Valid-Until`;
- изменяемые пути (`InRelease`, `repomd.xml`, обычный `Packages`) отдаются только из текущего поколения, пути с адресацией по содержимому (`by-hash`, уникальные имена `repodata`, `pool/<sha256>/`, `packages/<sha256>/`) — из любого сохранённого поколения;
- HTTP/1.1-читатель только для чтения: только GET и HEAD, список разрешённых `Host`, ограничения размера заголовка и цели запроса, отказ от тела запроса, percent-декодирование с отказом от `..`, `/`, `\` и NUL в сегментах, открытие с `O_NOFOLLOW` и проверка SHA-256 каждого объекта перед отправкой (отключается для замеров);
- ленивая загрузка закреплённого объекта по URL источника: одна загрузка на digest, политика адресов на каждом шаге перенаправления с подключением именно к проверенному адресу, тайм-ауты простоя и общий, проверка размера и digest до того, как объект попадает в хранилище;
- состояние в SQLite (`quick_check` перед каждой публикацией) и команда `reconcile`, которая восстанавливает состояние по манифестам и объектам.

Источник — `research/r-004/upstream.py`, локальный HTTP-сервер с внедрением сбоев, заменяющий хост файлов GitHub. `research/r-004/run.ps1 -Target debian12|alma9|fedora44` пересоздаёт цель, выполняет `setup-target.sh` и `prepare.sh` (ключ Ed25519 TEST ONLY, тестовые пакеты собираются на самой цели) и запускает `scenarios.sh` по областям (`socket gen cas http db measure third`). Исследовательский сервер объединяет в одном процессе читателя репозитория и ленивый загрузчик; ADR-017 разносит их по разным ролям, что не меняет проверенный протокол файлов и HTTP.

## Результаты

Финальные прогоны с одним бинарным файлом (SHA-256 `57590afb…`) и одной версией стенда: Debian 12 — 53 PASS, 10 OBSERVED; AlmaLinux 9 — 50 PASS, 12 OBSERVED; Fedora 44 — 50 PASS, 12 OBSERVED; FAIL нет. «OBSERVED» — контрольные случаи и поведение, которое фиксируется, а не оценивается как прошедшее или нет. Более ранние прогоны падали только из-за исправленных дефектов стенда. Это сжатые списки APT в контейнерном образе Debian и тест, который портил объект, не отдаваемый текущим поколением. Ещё порт был занят другим дистрибутивом WSL2, а ожидания были слишком короткими.

### Потеря питания (шаг 4)

`research/r-004/powerloss.ps1` выполнялся на существующей ВМ с Astra Linux 1.8.6 (ядро 6.12.77, systemd 252, ext4 с `relatime`) в отдельном снимке VirtualBox, с одобрения владельца проекта. После работы ВМ выключена, возвращена к этому снимку, а снимок удалён. Внутри ВМ `research/r-004/powerloss.sh load` в цикле публиковал через r004-snapshotd поколения из четырёх случайных файлов (256 KiB–2 MiB). После каждой успешной публикации он дописывал ID поколения в файл подтверждений и выполнял для него `fsync`. Через 21–28 с хост выключал питание командой `VBoxManage controlvm poweroff`; затем ВМ загружалась, и запускался `powerloss.sh verify`. Три цикла:

| Цикл | Подтверждённых поколений | `current` | Повреждённые объекты или манифесты | Потерянные подтверждённые поколения | База состояния | `check` после `reconcile` |
|---|---|---|---|---|---|---|
| 1 | 82 | последнее подтверждённое | 0 | 0 | читается | чист |
| 2 | 124 | последнее подтверждённое | 0 | 0 | читается | чист |
| 3 | 169 | последнее подтверждённое | 0 | 0 | читается | чист |

Отключение питания действительно теряло несброшенные данные. Журнал stderr публикатора, который дописывался без `fsync`, после циклов 2 и 3 содержал в хвосте нулевые байты, а все файлы с `fsync` остались целыми. Это потеря питания гостя: VirtualBox может не передавать сброс кеша гостя на диск хоста, поэтому сбой самого хоста не моделировался.

### Защита HTTP (шаг 7)

H1 (все цели): 24 сконструированных запроса дали ожидаемые ответы, и ни в одном теле ответа не оказалось содержимого файлов:
- 404: `..` в обычной и percent-кодированной форме, закодированные `/` и `\`, NUL, цель в абсолютной форме, `//`, строка запроса, `/admin` и `/sync`;
- 405: POST, PUT, DELETE и OPTIONS;
- 400: неверный, отсутствующий или повторный `Host`, тело запроса, chunked-кодирование;
- 414: цель запроса длиной 3 000 байт;
- 431: заголовок длиной 9 000 байт;
- 200 без тела: HEAD.

H2: если манифест заменён символической ссылкой, репозиторий отвечает 503 (отказ в закрытую сторону).

### Условные запросы к GitHub (шаг 3)

Шесть анонимных запросов к `repos/cli/cli/releases/latest` (`research/r-004/github-304.sh`):

1. Безусловный GET возвращает 200 со слабым `ETag` и `Last-Modified`.
2. `If-None-Match` с этим `ETag` возвращает 304.
3. Другой `ETag` даёт 200.
4. Тот же `ETag` на другом URL (`releases?per_page=1`) даёт 200 и собственный `ETag`.
5. `If-Modified-Since` возвращает 304.
6. Анонимный ответ 304 **всё равно уменьшил** `x-ratelimit-remaining` (59 → 54 за шесть запросов).

## Не покрыто

- Потеря питания хоста, а также потеря питания во время ленивой загрузки и при работающем читателе. Циклы отключения питания покрыли только публикатор и хранилище на одной файловой системе гостя (ext4).
- Принудительный режим SELinux и AppArmor. В WSL2 нет ни того, ни другого, а директивы защиты юнита во время работы не проверялись.
- Источник по TLS и настоящий хост файлов GitHub. Политика адресов проверялась по обычному HTTP к локальной заглушке. Расход лимита ответами 304 с аутентификацией не проверялся.
- Astra Linux, РЕД ОС, Ubuntu и ALT; упаковка самого Pakomichi в DEB/RPM и его удаление менеджером пакетов. Удаление имитировалось удалением юнитов, данных и файлов репозитория.
- Разнесение читателя, загрузчика и владельца состояния по процессам (ADR-017). Привилегированные порты и захват порта, пока сокет не слушает (см. вывод 3), не проверялись.
- Длительные прогоны, много логических репозиториев одновременно и сборка мусора под нагрузкой. Команда `gc` в стенде есть, но в сценарии не входила.

## Выводы и требуемые изменения решений

1. **ADR-007 подтверждается** на systemd 252 и 259: сокет с `Accept=no` запускает ровно один процесс на параллельные холодные запросы, переживает падения и выход по простою, а резервный режим обычной службы работает с тем же протоколом. Читатель обязан отказываться от не-loopback адресов (показано).
2. **Цикл падений выключает сокет.** После 5 неудачных запусков в пределах стандартного интервала systemd переводит сокет в `failed`, и он перестаёт слушать до `systemctl reset-failed` и запуска сокета. Pakomichi нужны проверка состояния и документированная команда восстановления (`doctor`/административный путь), и он не должен завершаться с ошибкой в устранимых ситуациях.
3. **Пока сокет не слушает, порт свободен.** Любой локальный пользователь может занять `127.0.0.1:<порт>` и отвечать вместо Pakomichi. APT ограничивает повтор метаданных через `Valid-Until`, а DNF нет (см. 6). Стоит рассмотреть привилегированный порт (ниже 1024), который открывает systemd, чтобы непривилегированные пользователи не могли его занять. Это предложение из анализа, оно не проверялось.
4. **Перезапуск обрывает текущие запросы** (10–13 из 20 000). Перед обновлениями читателю нужно мягкое завершение по `SIGTERM`: перестать принимать соединения и дописать начатые ответы. При лимите в 64 соединения 70 локальных медленных клиентов задерживают остальных примерно на 10 с. Нужны ограничение на клиента и более короткий тайм-аут заголовка, хотя угроза только локальная.
5. **ADR-008 подтверждается с двумя обязательными уточнениями.**
   - Имена индексов с адресацией по содержимому (`Acquire-By-Hash: yes`; уникальные имена `repodata`) обязательны: без них переключение даёт несовпадение хешей (G3).
   - Старые поколения должны оставаться доступными не меньше, чем длится самое долгое обновление клиента. Без их сохранения APT не просто падает: он откатывается на изменяемый обычный путь и смешивает поколения, а затем это отвергает его же проверка хеша (G4).

   Сборка мусора должна учитывать достижимость и временное окно, а не только число поколений.
6. **DNF нужны серверная защита свежести и защита от отката.** В `repomd.xml` нет подписанного срока действия, и DNF принял более старые подписанные метаданные, отданные после более новых, и предложил более старую версию (G8). APT такой повтор проигнорировал и соблюдает `Valid-Until` (G7). Для DNF Pakomichi должен перестать раздавать поколение (503) после максимальной свежести из проекта доставки и восстановления. Указатель `current` никогда не должен возвращаться к более старому поколению.
7. **Отдельная подпись `repomd.xml.asc` может не совпасть во время переключения.** На Fedora 44 за прогон 1–3 из 640 параллельных обновлений падали с `Bad PGP signature`, пока поколения переключались каждые несколько секунд. Отказ безопасный (в закрытую сторону). Закрепление за соединением не помогает, потому что librepo использует несколько соединений. Pakomichi следует переключать RPM-поколения редко (по 6-часовой проверке, а не при каждом опросе), а его собственный `sync` должен считать ошибку подписи сразу после переключения повторяемой. Переключать поколения быстрее, чем клиенты успевают обновиться, нельзя.
8. **`skip_if_unavailable=False` из R-001 конфликтует с доступностью.** С ним недоступный источник Pakomichi блокирует любые операции DNF в системе, включая обновления дистрибутива (T1, T2, T3a). Решение в P1-005 должно взвесить это против причины, по которой R-001 выбрал `False` (не допускать тихого перехода на другой экземпляр). При любом выборе удаление обязано удалять файл репозитория (T3a), а сокет должен оставаться слушающим (вывод 2).
9. **Коды выхода APT — не сигнал исправности:** `apt-get update` завершается с кодом 0, когда наш источник недоступен или отвечает 503 (T1, T2), что совпадает с R-001.
10. **Протокол записи в CAS подтверждён:** временный файл, проверка digest, `fsync`, переименование, `fsync` каталога и очистка временных файлов при запуске выдерживают убийство на любом шаге и три отключения питания гостя во время непрерывной публикации. После каждого отключения `current` указывал на последнее подтверждённое поколение, и ничего подтверждённого не терялось. Ленивая загрузка никогда не публикует частичный, подменённый или слишком большой объект. Она переводит отказы в 502/504/507 и скачивает каждый digest один раз. Проверка объектов перед отправкой ловит порчу на диске ценой 15–20% пропускной способности на больших файлах. APT и DNF тоже ловят её сами, поэтому проверка перед отправкой (или периодический обход) рекомендуется, но не обязательна.
11. **SSRF:** разрешение каждого шага один раз, проверка каждого полученного адреса и подключение именно к проверенному адресу блокируют перенаправления на loopback, частные, link-local, адреса метаданных и IPv6 loopback. Рабочий загрузчик должен сохранить это для HTTPS и отвергать перенаправление на не-HTTPS URL.
12. **ADR-013 подтверждается:** источник истины — манифесты и объекты. Повреждённая база SQLite останавливает публикацию, но не раздачу, а `reconcile` восстанавливает её.
13. **Потеря ключа подписи** честно останавливает публикацию. Клиенты APT падают после `Valid-Until`, для клиентов DNF нужен вывод 6. Ключи подписи и `Valid-Until` нужно настроить так, чтобы истечение замечали раньше, чем оно заблокирует пользователей (предупреждение об устаревании через 24 часа в проекте доставки и восстановления).
14. **GitHub 304:** ответ 304 подтверждает «без изменений», только если запрос содержал `If-None-Match` с `ETag` из ранее проверенного ответа 200 для того же URL и тех же учётных данных. `ETag` слабый и привязан к URL. Ответ 304 никогда не подтверждает байты файлов релиза. Анонимные ответы 304 расходуют лимит, поэтому условные запросы не удешевляют анонимный опрос.
15. **Попутная находка для ADR-017:** в AlmaLinux 9 поставляется SQLite 3.34.1, старше версии 3.37, которую ADR-017 требует для таблиц `STRICT`. Для семейства EL9 нужно решение: встроенная SQLite для этого семейства, отказ от таблиц `STRICT` или исключение EL9 из 0.1. Владелец проекта выбрал отказ от таблиц `STRICT`: см. ADR-020.

Резервный режим протокола не понадобился: активация через сокет выполнила требования на всех проверенных целях.
