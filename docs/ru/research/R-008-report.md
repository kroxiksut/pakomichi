# Отчёт R-008 — источники пакетов (фаза A)

[English](../../en/research/R-008-report.md) · **Русский**

**Статус: фаза A завершена; протокол ещё не в состоянии PASS.**

- **Сделано:** у каждого источника в рамках есть строка, и по каждому месту устройства из вопроса 7 есть решение или эксперимент, который его решит.
- **Предлагаемый ADR:** набросан [ADR-032](../decisions/ADR-032.md); 22.10.2026 владелец в принципе согласился с подходом.
- **Не хватает:** принятия ADR-032 и экспериментов фазы B.

Протокол: [R-008](R-008-package-sources.md). Дата: 22.10.2026.

## Метод и ограничения

- Только фаза A: документы и анонимные запросы только на чтение с машины разработки.
  - Читались только метаданные: объекты API, `InRelease`, `repomd.xml`, манифесты каталогов. Ни один пакет не скачан и не установлен.
  - Учётные записи не создавались, ни в один сервис ничего не записано.
  - Сырые ответы и заголовки лежат в `.research-local/r-008/{forges,repos,catalogs}/`, матрица — в `research/r-008/sources-matrix.tsv`.
- Утверждения с пометкой «unconfirmed» в матрице взяты из единственного вторичного источника или не наблюдались напрямую.
- Это я перепроверил по сохранённым файлам:
  - ни в одном из 17 файлов `InRelease` нет `Valid-Until`;
  - `repomd.xml.asc` у COPR и РЕД ОС отвечает 404, а в `.repo` COPR стоит `repo_gpgcheck=0`;
  - у ссылок на файлы релиза GitLab нет полей размера и digest;
  - анонимный ответ 304 у GitLab всё равно уменьшил лимит (497 → 496).
- **Ограничения среды:**
  - flathub.org был недоступен с хоста, поэтому ответы по Flathub взяты из исходников его документации;
  - `apt.grafana.com` и `rpm.grafana.com` отвечали 403 на любой запрос;
  - GitFlic и GitVerse требуют токен для любого вызова API, поэтому не читались.

## Главные выводы

1. **Strict есть только у GitHub.** Attested реален ещё на одном сервисе — gitlab.com. Fulcio принимает его как издателя с теми же claims ID репозитория и ID владельца (`.15`/`.17`). API аттестаций GitLab — эксперимент, а у self-managed экземпляра публичного издателя нет.

   Остальные площадки, хостинги репозиториев и каталоги дают только digest, подписи OpenPGP издателя по соглашению или ключи, которые держит сервис. Значит, в лучшем случае Native (ADR-023) и Pinned (ADR-027), плюс отложенный уровень «Signed» для ключей OpenPGP издателя (Launchpad, Forgejo).
2. **Числовые или UUID-идентичности есть почти везде, но они действуют только в пределах экземпляра.**
   - Числовые: проект и пространство имён GitLab, репозиторий и владелец Gitea, Forgejo и GitVerse.
   - UUID или GUID: Bitbucket, GitFlic, Azure DevOps.
   - Только имя: Launchpad и хостинги репозиториев APT/DNF. Их идентичность — хост, путь и ключ.
   - Gitea и Forgejo требуют токен для чтения репозитория по ID, поэтому правило «сверять по ID, никогда по имени» требует там учётных данных.
3. **Объект выпуска у источников разный:**
   - в REST API GitLab нет ID выпуска, а ссылки на файлы можно править, и digest у них нет; digest лежат в generic-реестре пакетов;
   - у Bitbucket и SourceForge объекта выпуска нет вовсе;
   - generic-пакеты в GitLab по умолчанию дописывают файлы к существующей версии.

   Поэтому подменённый файл — не единственный вид изменения: новый файл в закреплённом выпуске — тоже изменение.
4. **Хосты скачивания отличаются от хостов API:**
   - подписанные ссылки S3 (Bitbucket, COPR);
   - Cloudflare R2 (gitea.com);
   - CloudFront (packagecloud);
   - сторонние зеркала (SourceForge);
   - отдельный хост файлов (Launchpad);
   - перенаправления между `repo1` и `repo2`/`repo3` (РЕД ОС);
   - любой хост, который указан в ссылке релиза GitLab.

   Один разрешённый хост на клиент не обобщается.
5. **Условные запросы и заголовки лимитов у источников разные.**
   - Без валидаторов вовсе: Gitea, Forgejo, SourceForge, Azure DevOps, Tailscale, Chocolatey, info API Snap.
   - Пять диалектов заголовков:
     - GitHub `x-ratelimit-*`;
     - GitLab `RateLimit-*`;
     - Bitbucket `X-RateLimit-*` с `w=3600`;
     - черновик IETF `ratelimit-policy` (Codeberg);
     - `GitVerse-RateLimit-*`.
6. **Каталоги-указатели добавляют заявление второй стороны о хеше, а не байты.** WinGet, Scoop, cask и исходники формул Homebrew, AppImageHub и cargo-binstall указывают на собственный URL производителя.
   - Для jq 1.8.2 `InstallerSha256` в WinGet и `hash` в Scoop равны digest файла в GitHub, а контрольная сумма исходников в Homebrew равна digest другого файла. Всё это проверено без скачивания.
   - Манифест WinGet изменился под той же версией (у jq 1.8.2 появился установщик для arm64), и видно это только в истории Git.
   - Общий каталог отстаёт: `Microsoft.OpenSSH.Preview` в WinGet — 10.0.0.0 (27.10.2025), а в GitHub Releases — 10.4.0.0p1-Preview (20.10.2026) (R-007, `.research-local/r-007/`).
   - Совпадение имени ничего не доказывает: snap `jq` принадлежит третьему лицу и застрял на версии 1.5.
7. **Подписи магазинов и упаковщиков — не подписи автора.**
   - Утверждения Snap, ключ репозитория Flathub и подписи реестра npm принадлежат магазину или реестру.
   - Аттестации bottle в Homebrew называют собственный workflow Homebrew, и одна аттестация покрывает 104 bottle.
   - Ничто из этого не может считаться Native или Attested для исходного проекта.
8. **Хостинги репозиториев APT/DNF не дают ничего сверх ключа, который APT/DNF и так проверяют, а этот ключ обычно принадлежит сервису, а не проекту.**
   - У Microsoft один ключ на сервис, у Launchpad — один на владельца. packagecloud, Cloudsmith, Gemfury и COPR держат закрытый ключ у себя.
   - Опереться на свежесть получателю не на что: `Valid-Until` нет нигде, а COPR и РЕД ОС вообще не подписывают `repomd.xml`.
   - Байты под той же версией законно меняются: HashiCorp переподписал пакеты с теми же NEVRA после смены ключа 10.09.2026, а COPR пересобирает ту же версию.
9. **Российские цели:**
   - **Astra.** Документированный путь для стороннего ПО — репозиторий производителя, проверенный по программе «Ready for Astra», с подписями ELF по цепочке Astra для замкнутой программной среды. `extended` явно не сертифицирован.
   - **РЕД ОС.** Сертифицированная редакция запрещает направлять службы автоматического обновления на внешние сторонние репозитории. RED SOFT сама размещает отдельное стороннее ПО в своём дереве `3rdparty`.
   - Считается ли локальный репозиторий Pakomichi таким внешним репозиторием — решение владельца, оно нужно до любого заявления о сертифицированной РЕД ОС.

## Материал для предлагаемого ADR о модели источника

1. У источника есть вид, например `github`, `gitlab`, `forgejo`, `bitbucket` или `sourceforge`. У него есть происхождение экземпляра, устойчивая идентичность этого вида и набор подтверждённых владельцев (миграция 0002).
2. Артефакт определяется как `(источник, ключ выпуска или null, ключ артефакта источника, алгоритм digest, digest)`. Закрепление никогда не перепривязывается, и подменённый, и добавленный файл — изменение.
3. Уровни:
   - Strict — только у GitHub;
   - Attested — от издателя с шаблоном claims (GitHub; gitlab.com);
   - Native и Pinned — для любого источника;
   - Signed остаётся отложенным.

   Заявления магазинов, упаковщиков и каталогов — доказательства, которые никогда не поднимают уровень.
4. Сеть: для каждого источника — список разрешённых хостов API и скачивания, обходчик страниц, диалект лимитов и необязательный валидатор.
5. Отозвано после решения владельца 22.10.2026: хостинги репозиториев APT/DNF и каталоги — виды источника. Черновик — [ADR-032](../decisions/ADR-032.md). По-прежнему вне рамок: Azure DevOps, Bitbucket Data Center, GitHub Packages (нужны учётные данные), а также Snap, Flatpak, AppImage как форматы.

## Результаты фазы B на сегодня (22.10.2026)

**Перепись хешей по каналам.** Только чтение, без скачивания бинарных файлов (`research/r-008/census.ps1`, `research/r-008/census.tsv`, сырые данные в `.research-local/r-008/census/`).
- Охват:
  - 18 популярных CLI-утилит (ripgrep, fd, bat, fzf, jq, yq, gh, lazygit, delta, starship, zoxide, eza, hyperfine, k9s, age, sops, croc, just);
  - 126 заявлений каталогов;
  - у каждого последнего выпуска GitHub `digest` был у каждого файла (518 файлов).
- **Расхождений нет нигде.**
- По каналам:
  - WinGet: 39 совпадений, 6 отставаний. В обоих отстающих случаях (yq 4.53.6 против 4.54.1, lazygit 0.66.1 против 0.66.2) хеш равен digest более старого выпуска GitHub.
  - Scoop: 42 из 42 совпадают, все на последней версии, каждый URL — файл выпуска GitHub.
  - Формулы Homebrew: сравнима только jq, и она совпадает. Остальные 17 используют автоматически собранные архивы `/archive/` или URL Git, а их bottle собирает сам Homebrew.
- **AUR:**
  - Ни одного из предполагаемых пакетов `<утилита>-bin` в AUR RPC нет.
  - URL `.SRCINFO` в cgit по-прежнему отдаёт устаревшие ветки удалённых пакетов, поэтому `.SRCINFO` не доказывает, что пакет существует.
  - Единственный живой `delta-bin` собирает другой проект, `zed-industries/delta-nix`: второй случай, когда совпадение имени означает другого издателя.

**APT без `Valid-Until`.** Одноразовый дистрибутив Debian 12.15, apt 2.6.1, ключ TEST ONLY и локальный репозиторий (`research/r-008/apt-freshness.sh`, `research/r-008/apt-freshness.tsv`, журналы в `.research-local/r-008/lab-apt/`). После проверки дистрибутив удалён.
- **Откат отклоняется молча и только клиентом, у которого уже есть более новые данные.**
  - После `InRelease` A более старый подписанный `InRelease` B был скачан (HTTP 200) и проигнорирован. Код выхода 0, без предупреждения, список пакетов A сохранился.
  - Клиент без списков принял бы B.
- **Без `Valid-Until` по умолчанию ничего не устаревает.** Метаданные десятидневной давности принимаются. `Acquire::Max-ValidTime` и поле `.sources` `Valid-Until-Max` превращают `Date` плюс максимум в срок действия («Release file … is expired», код 100), поэтому они работают как защита от заморозки для репозиториев, которые не публикуют `Valid-Until`.
- **APT разбирает нестандартную дату OBS** (`Mon Sep 14 16:13:08 2026`) и применяет к ней `Max-ValidTime`.
- **`Date` из будущего по умолчанию отклоняется** («not valid yet»). `Date-Max-Future`, `Acquire::Max-FutureTime` или `Acquire::Check-Date=false` её принимают.

Для Pakomichi отсюда следует:
- источник-нативный репозиторий может получить защиту от заморозки через `Valid-Until-Max` для каждого источника;
- откат виден, только если Pakomichi сам сравнивает `Date` с уже виденной, потому что APT никакого сигнала не даёт.

**Устойчивость Authenticode (вопрос 3 R-007, частично).** Разобраны два MSI Win32-OpenSSH (10.4.0.0p1 и 10.0.0.0p2): `research/r-007/authenticode-stability.tsv`, сырые данные в `.research-local/r-007/authenticode/`.

| Поле | Не изменилось между двумя выпусками? |
|---|---|
| Субъект (`CN=Microsoft Corporation`, …) | да |
| Корень (Microsoft Root Certificate Authority 2011) | да |
| Служба меток времени | да |
| Форма подписи (одна подпись SHA-256) | да |
| Промежуточный CA | **нет**: PCA 2011 → PCA 2024 |
| Отпечаток листового сертификата | **нет**: листовые сертификаты примерно на год, перевыпуск примерно раз в 10 месяцев |
| Время подписания | не записано; время несёт только контрподпись метки времени |

Значит, закреплять нельзя ни отпечаток листового сертификата, ни один промежуточный CA. Кандидат на закрепление — субъект плюс известный корень на действительной цепочке с меткой времени. Прежде чем это станет выводом, нужны более старые выпуски (9.8, 9.5, 8.9). `InstallerSha256` в WinGet для 10.0.0.0 равен digest GitHub; автоматическое сравнение с WinGet в скрипте пока содержит ошибку.

## Фаза B (каждый пункт требует одобрения владельца)

- **Площадки** (тестовые проекты создаёт владелец):
  - GitLab: переименование, передача, повторное использование старого пути, подмена ссылки, повторная загрузка, аттестация в CI и claims её сертификата;
  - Codeberg: переименование и повторное использование имени, повторная загрузка вложения;
  - Bitbucket — только с платным workspace;
  - GitFlic и GitVerse: только чтение с токеном владельца.
- **Хостинги репозиториев** (стенды R-001 и R-004):
  - заморозка APT без `Valid-Until`, с `Valid-Until-Max` и без него;
  - APT и формат `Date` у OBS;
  - откат DNF при неподписанных метаданных;
  - смена подключа RPM;
  - те же NEVRA с новыми байтами;
  - конфигурация РЕД ОС на `redos80`, только чтение.
- **Windows** (R-007, тестовая ВМ Windows 11):
  - REST-источник на loopback и минимальное изменение доверия, которое он требует;
  - заранее индексированный подписанный источник;
  - проверка хеша клиентом;
  - устойчивость закрепления Authenticode между выпусками.
- **Только чтение:** перепись хешей по каналам для ~20 проектов, которые публикуют только на GitHub; API Flathub из другой сети.
