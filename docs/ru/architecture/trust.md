# Модель доверия и угроз

[English](../../en/architecture/trust.md) · **Русский**

## Доверяем чему

Пользователь самостоятельно выбирает **конкретный** репозиторий; мы не доказываем честность издателя. Наша цель — не подменять выбор, не принимать байты из другого repo и не выдавать повреждённый артефакт. Не доверяем произвольной строке `owner/repo` после смены владельца, неподписанному имени файла, `latest`, имени RPM/DEB и HTTPS как доказательству отсутствия вредоносного ПО.

## Strict

GitHub immutable release + криптографически проверенное release attestation (с нужным типом предиката) + repository ID в certificate/attestation + соответствие release/assets + SHA-256 фактического файла. Проверить реальные поля/цепочку в R-003; одно лишь API `immutable=true` недостаточно для утверждения, что вся криптографическая процедура выполнена.

## Attested

Release может быть mutable, но для конкретного файла нужна криптографически проверенная аттестация с ожидаемыми source repository ID, workflow identity, predicate и digest. После принятия `(release_id,asset_id,sha)` не перезаписывать на новый digest: обнаруженную замену блокировать. Первое наблюдение не доказывает отсутствия изменений до него.

## Проверка (ADR-030)

Strict и Attested проверяет `src/attest` библиотекой `sigstore-verify` 0.15.0 с собственным провайдером Pakomichi на `ring`, который устанавливается при старте процесса. Для Strict и Attested используются раздельные корни доверия, которые никогда не смешиваются. Bundle проверяются до любой криптографии: не больше 256 КиБ каждый и 16 на digest, media type bundle v0.3, DSSE с одной подписью над in-toto statement. Statement интерпретируется только после проверки его подписи.

- **Strict** требует неизменяемого релиза и release attestation от удостоверяющего центра GitHub: SAN `https://dotcom.releases.github.com` и проверенное время RFC 3161, без журнала прозрачности. Её предикат должен называть закреплённый ID репозитория как `repositoryId` и `packageId`, подтверждённый ID владельца, ID и тег этого релиза, SHA объекта ссылки на тег в том виде, в каком его отдаёт GitHub (коммит для лёгкого тега, объект тега для аннотированного, без разыменования), а также имя файла релиза с его digest.
- **Attested** требует SLSA provenance от public-good Sigstore с проверенным SCT и включением в журнал прозрачности. Её Fulcio-claims должны нести закреплённые ID репозитория и владельца, workflow самого репозитория, подтверждённый администратором для источника (ADR-036, пункт 1; точный путь, без префикса и шаблона), ожидаемый ref и коммит, на который указывает тег релиза, а также runner GitHub.

Имена никогда не привязывают: переименование при тех же ID проходит, новый репозиторий под старым именем и форк — нет. После подтверждённой передачи прежние ID владельца остаются принятыми для аттестаций, сделанных до неё. Неудачная проверка — `E_ATTESTATION_INVALID` с одним подкодом из п. 7 ADR-030, который передаётся как `subcode` в событии причины версии 2 (ADR-031); отсутствие доказательства (нет bundle, нет release attestation, релиз не неизменяемый, нет provenance) — `E_EVIDENCE_DOWNGRADE`.

Доказательства хранятся так, чтобы их можно было проверить снова (ADR-034): каждый bundle, стоящий за записью `TrustEvidence`, сохраняется в хранилище блобов по своему digest и не собирается, пока существует доказательство; последующая проверка заново проверяет сохранённые bundle офлайн, а пропавший или изменённый bundle её не проходит. Digest никогда не определяет источник: байты, общие для двух источников, допускаются для каждого только по его собственному доказательству.

Записанные доказательства переиспользуются между синхронизациями (ADR-037, пункт 1): артефакт, у которого ID asset и SHA-256 уже записаны в том же источнике с доказательством Strict или с доказательством Attested от текущего подписанта источника и с тем ref, который его правило даёт для этого релиза, сохраняет это доказательство без запроса к площадке. Каждый релиз заново проверяется при полной проверке: при первой синхронизации источника, когда последней полной проверке 24 часа или больше (или она в будущем — после перевода часов назад), и по `pchi sync --force`. Результат без доказательства или недействительный запрашивается заново при каждой синхронизации. Поэтому удалённая аттестация или перенесённый тег релиза обнаруживаются при следующей полной проверке; идентичность репозитория и листинг релизов, а с ним и подменённый asset, проверяются при каждой синхронизации.

Корни доверия берутся из TUF (п. 8 ADR-030): каждый экземпляр начинает с TUF-корня, поставляемого с Pakomichi и закреплённого по SHA-256 (GitHub — версия 9, public-good — версия 15), проходит цепочку корней и проверяет timestamp, snapshot, targets и `trusted_root.json` через `sigstore-tuf`. Запросы идут только к `tuf-repo.github.com` и `tuf-repo-cdn.sigstore.dev` по правилам клиента API: одно разрешение имени на запрос, все адреса должны быть публичными, TLS по системному хранилищу CA, без редиректов, с ограничением размеров. Проверенные метаданные кешируются. Если репозиторий недоступен, кеш заново проверяется от закреплённого корня и используется, только пока он не истёк; истёкшие метаданные останавливают проверку с причиной, называющей экземпляр. Ошибка проверки данных из сети (подпись, откат, хеш цели) никогда не подменяется кешем. Обновление в процессе, который не установил криптографический провайдер (п. 2 ADR-030), отклоняется ошибкой до любого запроса и обращения к кешу — так же, как отказывается создаваться верификатор аттестаций; до паники библиотеки дело не доходит.

## Pinned (ADR-027)

Криптографического происхождения нет: защищают только закрепление по ID репозитория и заморозка digest. В 0.1 разрешён только после явного согласия администратора для этого источника, в котором назван риск (скомпрометированные учётная запись, токен или CI издателя могут опубликовать вредоносный релиз, который Pakomichi обнаружить не может), и только с ручным подтверждением каждого релиза. Подтверждение привязано к точным digest подтверждённых артефактов; до него релиз удерживается с `E_RELEASE_APPROVAL_REQUIRED`, а изменённый после подтверждения asset — `E_ASSET_MUTATED`. Согласие и подтверждение — административные действия, никогда не доступные через status API, loopback HTTP или `--yes`. Источник Pinned работает только в режиме `supplemental` и никогда не вытесняет пакет дистрибутива. Уровень Signed и карантин по времени для Pinned отложены до 0.2.

## Инварианты и храповик (ADR-027)

Не зависят от уровня и никогда не ослабляются: закрепление по ID репозитория; неизменность принятых байтов; защита семейств и системного пространства имён (ADR-022); проверка CAS перед выдачей; подписанные локальные индексы; системная политика подписей RPM; запрет переподписи чужих пакетов; запрет отключения глобальных проверок подписей; запрет автоматического `yes` для рискованного перехода.

Уровень источника — нижняя граница (`pinned` < `attested` < `strict`). Он автоматически повышается, когда релиз несёт более сильное проверенное доказательство. Релиз с более слабым доказательством, чем эта граница, удерживается с `E_EVIDENCE_DOWNGRADE` до решения пользователя; граница никогда не понижается молча. Каждый уровень выдаётся из своего логического репозитория с отдельными APT `Label`/`Origin` и ID и `name` DNF-репозитория, чтобы `apt policy` и `dnf repolist` показывали его без `pchi`.

Это реализует `policy::level` (P2-011a). Доказательства Strict и Attested не ниже границы допускаются и поднимают границу; более слабые — `E_EVIDENCE_DOWNGRADE`, граница остаётся. Релиз без криптографических доказательств допускается только у источника с согласием на Pinned и только когда одобрение называет его точный SHA-256: до этого — `E_RELEASE_APPROVAL_REQUIRED`, или `E_EVIDENCE_DOWNGRADE`, если граница уже Attested или Strict; одобренное понижение раздаётся из репозитория Pinned, а граница остаётся. Без согласия ничто не становится Pinned, что бы ни было в `trust_floor`, а отозванное согласие снова удерживает каждый релиз Pinned, включая опубликованные; одобрения остаются в своей таблице (только дописывание), но доказательством больше не являются. Недействительные доказательства одобрение никогда не спасает. Пока у источника есть согласие на Pinned, ядро решения считает его Pinned для ограничений режима: только `supplemental` и никакой миграции имени. У каждого источника и уровня свой логический репозиторий: APT `Origin: Pakomichi` и `Label`/DNF ID `pakomichi-<source>-<level>`, а DNF `name` для Pinned говорит «no cryptographic provenance, every release approved by hand».

## RPM

Подпись репозиторных метаданных — это **не** встроенная подпись RPM. Два независимых барьера закрываются при отказе (fail closed) с раздельной диагностикой: подписанный `repomd.xml` нашего репозитория (`repo_gpgcheck=1`, локальный ключ) и доверие к пакету (R-002, ADR-023).

- **Режим Native:** встроенная подпись RPM проверяется ключом издателя, закреплённым за источником, при включённой проверке пакетов для его репозитория. Импорт ключа издателя в системную связку ключей RPM требует явного согласия с его отпечатком и предупреждения, что RPM принимает его для пакетов из любого источника.
- **Исключение Attested (ждёт R-003):** неподписанный RPM публикуется только после проверки промышленным верификатором attestation, с привязкой к его точному SHA-256, с явным согласием для источника и только если эффективный `%_pkgverify_level` не равен ни `signature`, ни `all`. Он выдаётся из отдельного логического репозитория, содержащего только такие пакеты, с отключённой проверкой пакетов только для этого репозитория Pakomichi. Иначе — `E_SIGNATURE_POLICY`. Attestation никогда не превращает RPM в подписанный штатно.
- Pakomichi никогда не записывает глобальные `gpgcheck=0`, `pkg_gpgcheck=0`, изменение `localpkg_gpgcheck` или `%_pkgverify_level`.

## Недоверенные локальные данные пакетного менеджера

`/var/lib/apt/lists` и `/var/cache/apt/archives` никогда не являются доверенным вводом ни в одном дистрибутиве (ADR-025): в Astra Linux с мандатным контролем целостности их может записывать процесс уровня 0. Pakomichi опирается на собственную проверку подписей и хешей APT и на digest своего CAS.

## Локальная подпись

Создаём ограниченный локальный ключ для подписания *наших* индексов APT/RPM. Не используем для переподписания чужих DEB/RPM. Централизованный ключ — централизованная точка доверия: права доступа, восстановление и ротация обязательны; `localhost` не является достаточной защитой. Ключи издателей и локальный ключ метаданных разделены и никогда не взаимозаменяемы. Ротация двухфазная: сначала новому ключу доверяют (перекрытие), затем им подписывают метаданные, а старый ключ удаляют после этого. Потеря ключа никогда не создаёт молча новый корень доверия; восстановление — из аутентифицированной резервной копии или явным повторным доверием администратора (ADR-023, N-023).

## Допустимый риск

Компрометация издателя, его CI или ключей возможна в любой системе. Pakomichi должен предоставлять блокировку конкретных версий/источников, но не обещает невозможное стопроцентное предотвращение. Подпись подтверждает происхождение, не полезность программы.

## Защита от переносов и форков

События repo rename (тот же repo ID + owner) и owner transfer (тот же repo ID, другой owner) имеют различное поведение. При transfer/ID mismatch → suspension; никогда не искать по владельцу все repos. Удалённый и пересозданный на том же URL Git-проект — другой repo ID → reject.

## Подмена артефакта

Если upstream content исчез, подставлять соседний asset / новый digest / fork запрещено. Проверить byte-stream до передачи пакета штатному менеджеру. Содержимое кеша проверять по хешам и ссылкам текущего снимка.
