# Семейства пакетов и системная совместимость

[English](../../en/architecture/families-compatibility.md) · **Русский**

## Допускаемое семейство

Один Git-репозиторий с одним CI может отдавать `app`, `app-cli`, `app-service`, `app-common`. При первом подключении пользователь подтверждает набор имён и соответствующие нативные пакеты; новые версии тех же имён — по политике. Новый пакет, даже с похожим префиксом, требует пересмотра состава.

Нативные `Depends`, `Pre-Depends`, `Provides`, `Conflicts`, `Breaks`, `Replaces`, `Obsoletes` и архитектурные требования разбираются из подтверждённых файлов. Обычный `Provides` не следует всегда запрещать, но замены критических системных пакетов или захват чужого namespace не допускать автоматически.

## Системное пространство имён (ADR-022)

Системное пространство имён — это множество имён пакетов и `Provides` (имена пакетов и виртуальные возможности, file provides, soname provides) пакетов из собственных источников дистрибутива. Артефакт удерживается с `E_SYSTEM_PACKAGE_CONFLICT`, если любой его `Provides` называет элемент системного пространства имён, а также если его `Obsoletes` или `Replaces` называет такой элемент при любом ограничении версии. Возможности, которые предоставляет только само допущенное семейство, остаются разрешёнными. R-001 показал, что каждый проверенный менеджер принимает сторонний `Provides` библиотеки C и использует его для удовлетворения требования с версией, поэтому эта проверка выполняется при допуске в Pakomichi. Какие настроенные источники считаются собственными источниками дистрибутива на каждой поддерживаемой сборке, что входит в пространство имён и как сравниваются имена, фиксирует [`specifications/system-namespace.md`](../specifications/system-namespace.md).

Каждый член активированного семейства защищён от смены издателя так же, как основной пакет: более высокая версия из другого источника не меняет его издателя (пункт 3 ADR-022). Зависимости семейства между источниками штатные менеджеры разрешают молча, поэтому опубликованный снимок должен содержать всё согласованное семейство.

## Системные зависимости

- Разрешаются штатным менеджером из уже настроенных источников ОС; Pakomichi не ищет произвольные Git-проекты.
- Изменения библиотек из иных релизов ОС не инициируем; при конфликте с базовыми пакетами удерживаем выпуск.
- Условия совместимости делим на `format_arch_ok`, `declared_dependency_satisfiable`, `platform_claimed`, `platform_tested`; без `platform_tested` совместимость **не выдавать** за подтверждённую, и даже `platform_tested` не гарантирует успешную работу.
- Проверка предварительных зависимостей не подменяет реальную транзакцию `apt upgrade` или `dnf upgrade`.
- Приложения могут иметь неявные требования к ядру, API, systemd/путям; выводить степень определённости.

## Семейные обновления

Снимок предоставляет согласованные метаданные версий. Если `app (= 0.6)` зависит от `app-service (= 0.6)`, оба должны быть доступны в опубликованном снимке или новая версия `app` не допускается. **Не требовать** одинакового номера всех компонентов, если родные зависимости этого не требуют.

## Допуск семейства (P2-007)

Семейство находится в одном из двух состояний. **Предложено:** найдено при первом подключении; пока администратор не подтвердит набор имён, ничего не допускается. **Одобрено:** подтверждено на некоторой ревизии; новые версии этих имён следуют политике. Подтверждение указывает ревизию, которую видел администратор, поэтому подтверждение более старой ревизии отклоняется. И первое подтверждение, и каждое расширение исходят только от интерактивного действия администратора, никогда от автоматического `yes`.

Для одной цели допуск решает судьбу каждого известного артефакта семейства, новых и уже опубликованных, в таком порядке:

1. **Состав.** Имя вне семейства или член, собранный для неподтверждённой архитектуры, удерживается с `E_FAMILY_UNAPPROVED` и попадает в пересмотр состава. Ничто из заявленного пакетом (`Provides`, `Replaces`, `Obsoletes` или член семейства, который от него зависит) не делает его членом. Подтверждение пересмотра создаёт следующую ревизию с этими именами. Артефакт, который удерживает более ранняя проверка (системное пространство имён, уровень доверия, канал), сохраняет причину этой проверки.
2. **Идентичность.** Одинаковые байты дважды оставляют первый артефакт. Два разных файла одного имени и архитектуры, версии которых равны по нативным правилам, оба удерживаются с `E_SOURCE_AMBIGUOUS`; `1.0` и `1.00` — одна и та же версия dpkg.
3. **Зависимости семейства.** Запись зависимости принадлежит семейству, когда каждая альтернатива называет то, что предлагает только семейство: имя члена или `Provides` артефакта-члена, которого нет в системном пространстве имён. Её должен удовлетворять другой допустимый артефакт семейства по нативным правилам (dpkg: `Provides` без версии никогда не удовлетворяет зависимость с версией; RPM: пересечение диапазонов, `Provides` без версии подходит к любой версии, а требование без release — к любому release). Иначе артефакт удерживается с `E_DEPENDENCY_UNSATISFIABLE`, и это повторяется, пока новые удержания не перестанут появляться. Записи, которые может удовлетворить система, файловые зависимости и возможности `rpmlib()` остаются штатному менеджеру. Расширенная (rich) зависимость RPM, называющая члена семейства, не вычисляется и удерживает артефакт.
4. **Публикация.** Публикуется самая новая допустимая версия каждого имени и архитектуры вместе со всеми более старыми артефактами, которые нужны её зависимостям внутри семейства.

Версии сравниваются нативными алгоритмами (dpkg `verrevcmp`, RPM `rpmvercmp` и `rpmverOverlap`), никогда лексикографически. Общие векторы в `tests/data/native-versions.tsv` сверяются со сравнением Pakomichi через `cargo test` и с нативными инструментами через `scripts/check-native-versions.py`. Некорректная версия или поле связей отклоняет байты с `E_ARTIFACT_MALFORMED`. Это относится и к тому, что dpkg принимает лишь с предупреждением (недопустимый символ в версии или ревизии), кроме upstream-версии, которая не начинается с цифры.

## Смены вариантов сборки

GitHub static musl vs COPR dynamic `libpcap` NetWatch — один издатель, но не обязательно эквивалентный пакет. Поле `build_variant` допускает `unknown`. Смена варианта и поставщика — отдельное пользовательское решение, а не «следующее обновление» только по большей версии.

## Защищённые уровни Astra Linux (ADR-025)

При включённой замкнутой программной среде `dpkg` и APT устанавливают пакет с неподписанным ELF с кодом выхода 0, но программа завершается с `SIGSEGV`; ключу, не подписанному корневым ключом Astra Linux, доверие установить нельзя. Поэтому Pakomichi отказывается активировать источники и удерживает каждый артефакт, пока замкнутая среда включена или это нельзя исключить, никогда не подписывает и не изменяет чужие файлы, никогда не добавляет ключи в `/etc/digsig/keys` и никогда не меняет уровень защищённости. При включённой замкнутой среде установленная программа, завершившаяся с `SIGSEGV`, выводится как вероятный отказ в запуске неподписанного исполняемого файла, а не как дефект пакета. R-006 не покрыл режимы `external_sig` и xattr, блокировки интерпретаторов, `chmod +x` и `bash` (они могут затронуть maintainer scripts) и разделяемые библиотеки.

## Ограничение ответственности

Без глобального перехвата штатных транзакций Pakomichi не способен гарантировать отсутствие любых изменений системных зависимостей при будущих командах APT/DNF. Обеспечиваем допустимость *нашей публикации*, честно обозначаем пределы транзакционной защиты.
