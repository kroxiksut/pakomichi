# Правила разработки на Rust

[English](../../en/process/rust-engineering.md) · **Русский**

**Статус документа:** обязательный baseline после утверждения Rust и начального toolchain в ADR-015. Начальные runtime, библиотеки, упаковка и модель процессов утверждены ADR-017 после P0-004; зависимые интеграции всё ещё проходят R-001…R-004.

Документ адаптирует переносимый опыт другого Rust-проекта к границам Pakomichi. Он не переносит чужую архитектуру, Windows/Qt-решения, версии зависимостей или прежнюю лицензионную политику.

**Проверенная база на 19.10.2026:** локальный Windows quality gate использует `rustc 1.94.1`, `cargo 1.94.1`, `rustfmt 1.8.0-stable`, `clippy 0.1.94`, `cargo-deny 0.19.0`; P0-004 повторил Rust 1.94.1 в Ubuntu 24.04 WSL2 и проверил стек ADR-017. Это не является доказательством поведения пакетных менеджеров или поддерживаемой Linux-матрицы.

## Воспроизводимый toolchain

- Версию Rust фиксировать в `rust-toolchain.toml`; обновлять намеренно с полным прогоном quality gate.
- Для приложения коммитить `Cargo.lock` и проверять сборку с чистой среды.
- Workspace, профили и общие lint-настройки имеют один источник истины в корневом `Cargo.toml`.
- Не создавать основной Cargo workspace до выполнения зависимостей и приёмки, заданных локальным трекером. Подтверждённый pin используется как исходная точка прототипов и может быть намеренно обновлён отдельным документированным изменением.

## Минимальный quality gate

После появления workspace единая локальная команда и CI должны запускать как минимум:

```text
cargo fmt --check
cargo clippy --workspace --all-targets --all-features -- -D warnings
cargo test --workspace --all-targets --all-features
cargo deny check
```

Точный набор флагов утверждается после проверки стоимости и совместимости. Тестировать crate целиком, а не только `--lib`: интеграционные тесты находятся за границей библиотечного target. Сетевые, пакетные и системные сценарии из R-001…R-004 всё равно выполняются в контейнерах/VM, а не заменяются Cargo unit-тестами.

## Базовые lints

Рекомендуемый старт workspace:

- `unsafe_code = "deny"` и `unused_must_use = "deny"`;
- Clippy `dbg_macro = "deny"`, `unwrap_used = "deny"`;
- `expect_used`, `todo` и `unimplemented` как минимум предупреждения с планом ужесточения.

`unsafe` допускается только там, где системный API или FFI действительно не дают безопасной альтернативы. Разрешение локализуется на минимальном участке, сопровождается `// SAFETY:` с проверяемым контрактом и безопасной внешней обёрткой. Первое `unsafe` в ранее безопасном crate — отдельный предмет review, а не побочная деталь изменения.

## Недоверенные данные

GitHub API, release assets, DEB/RPM, локальные IPC-запросы и данные из изменяемых пользователем файлов считаются враждебными.

- Парсеры имеют явные пределы размера, количества, глубины и времени.
- Ошибка ограничивается одним запросом, файлом или операцией и не должна приводить к panic.
- До системного применения проверяются точные байты и сохранённое evidence.
- Для самостоятельных парсеров предусматриваются property tests и fuzz targets, вызывающие реальную production-точку входа с production-лимитами.
- Негативные случаи проверяют не только код ошибки, но и отсутствие публикации частичного снимка, ослабления политики или изменения чужих источников.

## Границы crate и полномочий

- Направление зависимостей следует `docs/ru/architecture/overview.md` и ADR, а не удобству первого прототипа.
- Запрещённые транзитивные зависимости проверяются по разрешённому графу `cargo metadata`; поиск только по `Cargo.toml` не доказывает отсутствие зависимости в бинарнике.
- Сетевой клиент и инспектор чужих пакетов не получают root и закрытый ключ локального репозитория.
- Формат IPC, хранилища и сериализованных решений имеет явную версию и один нормативный тип; `Debug`/`Display` не используются как устойчивый wire/storage format.
- OS-механизм отделяется от политики. Неподтверждённая возможность конкретной системы выражается capability/fallback, а не фиктивной общей реализацией.

## Зависимости и лицензии

- Только реестровые зависимости из утверждённого источника; Git dependencies и wildcard versions запрещены без отдельного решения.
- Проверять advisories, yanked crates, дубликаты версий и лицензии для всех поддерживаемых target-графов.
- `cargo deny` видит лицензии Rust crates, но не доказывает условия нативной библиотеки за `*-sys`/FFI; её происхождение и лицензию проверять отдельно.
- Разрешённость зависимости не делает её исходный код частью Pakomichi под `MIT OR Apache-2.0`.

## Код и комментарии

- Публичная поверхность узкая; реализация остаётся private, пока внешний контракт не доказан потребителем.
- Комментарий объясняет причину или инвариант, а не пересказывает код.
- Номера задач, фаз, даты и история изменений не помещаются в исходные комментарии. Рабочий статус живёт в `TASKS_RU.md`, архитектурное решение — в ADR, исследовательский факт — в R-отчёте.
- Исправление дефекта включает тест, который падает без исправления, если такой тест технически возможен и действительно проверяет механизм.

## Обязательные прототипные проверки

P0-004 проверил OpenPGP/репозиторные подписи, DEB/RPM parsing без запуска скриптов, GitHub attestations через reference oracle, SQLite, Tokio с bounded concurrency, systemd/socket activation, sandboxing, упаковку DEB/RPM и toolchain; протокол находится в `docs/ru/prototypes/P0-004-stack.md`. Это подтверждает начальный стек ADR-017, но не заменяет R-001…R-004 и их VM-матрицу.
