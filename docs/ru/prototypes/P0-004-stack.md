# Отчёт о прототипе стека реализации P0-004

[English](../../en/prototypes/P0-004-stack.md) · **Русский**

**Дата:** 2026-10-19  
**Результат:** PASS для ограниченного прототипа; ADR-017 принят владельцем проекта. Этот отчёт не завершает R-001…R-004 и не заявляет поддерживаемую Linux-матрицу.

## Среда

- Провайдер: VM WSL2, Ubuntu 24.04, x86_64.
- Ядро: `6.18.40.1-microsoft-standard-WSL2`.
- systemd: `255.4-1ubuntu8.18`, запущен.
- Rust: `rustc 1.94.1`, `cargo 1.94.1`, установлены без root скриптом `setup-rust.sh` после проверки SHA-256 для `rustup-init`.
- Системная SQLite: 3.45.1 через `pkg-config`/`libsqlite3`; feature встроенной (bundled) SQLite не включалась.
- Нативные инструменты, использованные без установки и без изменения репозиториев: `gpg`, `gpgv`, `dpkg-deb`, `systemd-socket-activate`, `systemd-analyze`, `curl` и Python 3.
- Сырые загрузки, ключи, логи, пакеты и JSON проверки оставались в игнорируемом `.research-local/p0-004/`. Временные деревья DEB размещались в файловой системе WSL и были удалены.

Манифест среды воспроизводится из корня репозитория командой:

```sh
wsl -d Ubuntu-24.04 -- bash prototypes/p0-004/environment-manifest.sh
```

Скрипты определяют корень репозитория по собственному расположению, поэтому путь checkout не имеет значения. Чтобы повторить прогон в чистой среде, выполнить по порядку:

```sh
bash prototypes/p0-004/setup-rust.sh
bash prototypes/p0-004/fetch-dependencies.sh
bash prototypes/p0-004/run-cargo.sh test --all-targets --locked
```

`fetch-dependencies.sh` — единственный шаг после `setup-rust.sh`, которому нужна сеть. Все остальные шаги собирают офлайн из этого кеша зависимостей. `prototypes/p0-004/paths.sh` держит результаты сборки и кеш вне рабочей копии (в WSL — в `C:\temp\pakomichi\p0-004`, иначе — во временном каталоге системы). `verify-packaging.sh` принимает `P0004_OUTPUT_ROOT`, чтобы повторный прогон не перезаписал пакеты, записанные ниже.

## Наблюдения по зависимостям

- Кандидаты зависимостей времени выполнения, подтверждённые здесь: `tokio 1.53.3` с выбранными features, `listenfd 1.0.2`, `rusqlite 0.40.2` и `rpm 0.30.2` только для метаданных.
- Tokio обязателен только для долгоживущего сетевого процесса. SQLite остаётся за одним синхронным владельцем; инспекция пакетов, подпись и привилегированное применение остаются процессными границами. Конкурентность использует ограниченные семафоры/каналы, а блокирующая работа не должна занимать рабочие потоки Tokio.
- Все лицензионные выражения графа fixture/сборки состояли только из MIT, Apache-2.0 (включая `WITH LLVM-exception`), Unicode-3.0, Unlicense и Zlib; единственный crate только под Zlib — `zlib-rs`. Git-зависимостей в графе не было.
- `gpgv` и `dpkg-deb` остаются процессными границами, чтобы недоверенные байты пакетов не разбирались привилегированным процессом Pakomichi.
- GitHub CLI подходит в качестве независимого эталонного оракула (reference oracle) для R-003. Этот прототип не утверждает его как обязательный устанавливаемый runtime и не утверждает экспериментальный Rust crate `sigstore`.

## Ограничения и обязательные последующие шаги

- WSL2 достаточно для этого прототипа без root, но это не доказательство для матрицы поддержки дистрибутивов, DNF4/DNF5, установки службы, SELinux/AppArmor, потери питания, переполнения диска, конкурентности или жизненного цикла загрузки.
- Тестовый ключ находился в игнорируемом каталоге DrvFS, для которого GnuPG предупреждал о широких эмулированных правах доступа. Production-ключи обязаны находиться в нативной файловой системе Linux с принудительно соблюдаемыми владельцем/режимом; этот путь проверяет R-004.
- Бинарник верификатора, использованный для повторного прогона attestation полностью внутри WSL, передавался через `GH_BIN`; production-реализация верификатора по-прежнему зависит от прохождения R-003.
- `systemd-analyze security --offline=yes` проверяет директивы hardening, но не доказывает их соблюдение во время выполнения. Тесты установленного unit и отказов относятся к R-004.
- Отмена в Tokio, поведение при перегрузке, параллельные ленивые загрузки и порядок завершения работы по-прежнему требуют сценариев отказов из R-004; тест P0 доказывает границу runtime, а не эти системные свойства.
