# Условия выпуска 0.1 alpha

[English](../../en/testing/release-gate.md) · **Русский**

Ниже обязательные критерии. Изменение границ поддерживаемых дистрибутивов возможно отдельным решением; скрыть провал нельзя.

## Исследования

- R-001, R-002, R-003, R-004 и R-006 должны иметь воспроизводимые отчёты PASS либо документированный fallback и ограничение функции. R-001, R-002, R-004, R-005 и R-006 отражены в ADR-021…ADR-027; R-003 завершён только в части read-only.
- ADR должны отражать результаты без противоречий между реализацией и документами.
- Каждая перечисленная сборка дистрибутива выполняет правило допуска пункта 1 ADR-026 на этой конкретной сборке; первые цели — Debian 12, AlmaLinux 9, Fedora 44 и Astra Linux 1.8.6 на уровне `base(orel)`. Сборка без этих доказательств указывается как «не проверено», никогда как поддерживаемая.

## Пользовательский путь

- Один конкретный GitHub repo ID закрепляется; его DEB/RPM-пакеты обнаруживаются; разрешённые имена выбираются явно.
- Нативные команды APT/DNF в поддержанной среде выполняют install и upgrade штатной командой обновления дистрибутива (ADR-022, пункт 4); проверяются точные байты.
- При совпадающих версиях чужого поставщика не происходит необъявленной подмены; большая версия из другого источника не меняет издателя активированного имени.
- Auto fork/owner-wide discovery отсутствует; системные библиотеки из Git не подключаются.
- Strict/Attested работают только при доказанных криптографических условиях (R-003 завершён и выбран продовый верификатор) либо режим ограничен и честно описан. Attested-исключение для RPM ждёт того же.
- Pinned работает только при согласии для конкретного источника и одобрении каждого релиза, в режиме `supplemental`; Signed и карантин Pinned не входят в 0.1 (ADR-027).

## Безопасность и надёжность

- APT/DNF проверяют подпись локальных индексов; глобальная политика подписи не ослаблена.
- `N-001..N-040` должны быть выполнены на каждой перечисленной сборке, где они применимы, либо требуется документированный мотивированный scope reduction.
- Кеш и снимки выдерживают одновременные запросы, disk-full, offline, рестарт и повреждение временной загрузки.
- Соблюдается разделение привилегий; status API доступен только для чтения; инспектор чужих пакетов не получает root.
- Удаление Pakomichi не удаляет установленное ПО и не повреждает чужие системные источники.

## Выпуск

- Код и code-like материалы оформляются как `MIT OR Apache-2.0`; проза документации и диаграммы — как `CC-BY-4.0`; обязательны `LICENSE-MIT`, `LICENSE-APACHE`, `LICENSE-DOCS` и согласованные правила вкладов согласно ADR-016.
- Нативный пакет предоставляет основную команду `pchi` и полную команду `pakomichi`; обе проходят один набор CLI-тестов и не расходятся по поведению.
- Руководство пользователя, troubleshooting, поддерживаемая матрица дистрибутивов, ограничения и сценарии восстановления входят в выпуск.
- К выпуску приложены реальные CI/E2E логи; отсутствуют обещания «поддерживается всё» или «безопасно на 100%».
- Доступна история миграций и причин отказа; release notes отражают ограничения, в том числе: недоступный DNF-репозиторий Pakomichi блокирует операции DNF с метаданными в системе до восстановления или удаления, с командой восстановления (ADR-021); активированное имя сохраняет издателя, поэтому обновления безопасности дистрибутива для этого имени требуют явной миграции (ADR-022); Pinned-источник с согласием всё ещё может доставить вредоносный релиз, если администратор его одобрит (ADR-027); вывод R-005, что лишь меньшинство изученных репозиториев публикует доказательства Strict или Attested (ADR-026).
