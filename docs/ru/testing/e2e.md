# Сквозные сценарии E2E

[English](../../en/testing/e2e.md) · **Русский**

Выполнять только на сборках дистрибутивов, допускаемых по ADR-026, с собственным пакетом Pakomichi; для AlmaLinux и Fedora — на VM с SELinux в режиме enforcing.

## E2E-01 GitHub → APT

VM с Debian, тестовый публичный GitHub Release с 1.0 и 1.1 `.deb`, подписанное provenance. Закрепить repo ID, `source add`, инспекция, активировать family, выполнить `apt update && apt install sampleapp`, новый Release → `apt update` и штатная команда обновления дистрибутива (`apt upgrade` на Debian и Ubuntu, `apt-get dist-upgrade` на Astra Linux, ADR-022); убедиться в нативной версии, SHA и отсутствии изменений чужих sources.

## E2E-02 GitHub → DNF

Аналогично на DNF4/DNF5 с `dnf upgrade`, с signed RPM и подписью repodata. Для unsigned RPM — отдельный положительный случай только после R-003 и выбора продового верификатора: явное согласие, разрешающий эффективный `%_pkgverify_level` и отдельный логический репозиторий (ADR-023); обязательная подпись блокирует.

## E2E-03 Multiple packages

Release `sampleapp`, `sampleapp-cli`, `sampleapp-service`. Нативные зависимости main→service; обновление 1.0→1.1 согласовано; новая `sampleapp-driver` не добавляется автоматически. Каждый член семейства сохраняет издателя, когда другой источник предлагает большую версию (ADR-022).

## E2E-04 Установленная программа из другого источника

В системе уже `sampleapp 1.0`; Git предлагает 1.1. Сначала observing, затем user-approved migration в допустимой конфигурации. При равной версии с разными SHA автоматический переход не совершается. После активации большая версия из дистрибутива или другого источника не меняет издателя при штатной команде обновления, а `pchi status` показывает уведомление.

## E2E-05 NetWatch (read-only внешний эталон)

Рассмотреть `matthart1983/netwatch`: `netwatch` `.deb/.rpm`, APT на GitHub Pages, COPR native dynamic vs GitHub static RPM, Rust name `netwatch-tui`. Не считать все варианты сборок идентичными. Не модифицировать чужой репозиторий и не пытаться установить конфликтующую сборку на рабочую машину.

## E2E-06 Uninstall / offline

В VM установить через нашу прослойку, оборвать сеть, проверить кеш и истечение freshness (APT: `Valid-Until`; DNF: подписанное пустое поколение, ADR-024); остановить службу и проверить, что DNF называет репозиторий Pakomichi, а `pchi doctor` сообщает способ восстановления (ADR-021); удалить Pakomichi, убедиться, что программа остаётся установленной, не остаётся ни одного файла репозитория Pakomichi, а прочие системные источники сохранены.

## E2E-07 Pinned-источник (ADR-027)

Тестовый репозиторий без attestations. `source allow-pinned` показывает риск и записывает согласие; новый релиз удерживается с `E_RELEASE_APPROVAL_REQUIRED` до `release approve`; после одобрения он отдаётся из логического Pinned-репозитория, который `apt policy`/`dnf repolist` показывают по его метке; asset, изменённый после одобрения, — `E_ASSET_MUTATED`; `--policy preferred` отклоняется.

Во всех случаях **фактические команды, хеши файлов, состояние пакетной базы до/после** — обязательное доказательство.
