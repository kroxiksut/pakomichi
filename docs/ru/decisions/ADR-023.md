# ADR-023 — Доверие к RPM-пакетам и подписанные метаданные репозитория

[English](../../en/decisions/ADR-023.md) · **Русский**

**Статус:** принято владельцем проекта 2026-10-20. ADR-006 и ADR-011 остаются в силе; это решение уточняет их и ничего не заменяет. Исключение Attested из пункта 3 ждало R-003; R-003 завершился с PASS 22.10.2026, а ADR-030 выбрал верификатор, поэтому это условие выполнено (ADR-034, пункт 4); остальные условия пункта 3 по-прежнему действуют.  
**Дата:** 2026-10-20.

## Контекст

ADR-006 отделяет подпись метаданных локальным ключом от штатной проверки подписи RPM и допускает неподписанный RPM с аттестацией, только если это разрешает политика репозитория и не запрещает обязательная системная проверка. R-002 проверил это на AlmaLinux 9.8 (DNF 4.14, RPM 4.16) и Fedora 44 (DNF5 5.4, RPM 6.0) с одинаковым вердиктом во всех 12 ячейках на обеих платформах ([отчёт R-002](../research/R-002-report.md)):

- подписанный `repomd.xml` и встроенная подпись RPM — независимые проверки: корректные метаданные не спасают неподписанный или повреждённый пакет при обязательной политике, а корректная подпись пакета не спасает некорректные метаданные;
- неподписанный пакет устанавливался только в явной ячейке модели Attested, после проверки точных байтов и с отключённой проверкой пакетов для этого тестового репозитория; те же байты блокировались, когда `%_pkgverify_level=signature` требовал подпись;
- в DNF 4.14 нет ни `pkg_gpgcheck`, ни `gpgcheck_policy`; DNF5 использует `pkg_gpgcheck` и `repo_gpgcheck`, а `gpgcheck_policy=legacy` раскрывает `gpgcheck=1` только в `pkg_gpgcheck=1`; RPM 6 по умолчанию принудительно проверяет транзакции;
- новый ключ метаданных отклоняется, пока ему явно не доверились; потеря закрытого ключа метаданных оставляет подписанный снимок действительным и останавливает новые подписи до восстановления из аутентифицированной резервной копии.

R-005 не нашёл встроенной подписи ни в одном из 10 RPM проверенной подвыборки, в том числе в RPM с проверенным доказательством Strict на GitHub ([отчёт R-005](../research/R-005-report.md), вывод 5). Без исключения Attested большинство RPM с GitHub можно было бы только удерживать.

Промышленный верификатор аттестаций ещё не выбран (пункт 9 ADR-017); R-003 завершён только в части, доступной только для чтения (`research/r-003/README.md`).

## Решение

1. **Два шлюза.** У каждого DNF-репозитория Pakomichi `repo_gpgcheck=1` и подписанный `repomd.xml` (ключ ADR-011), а доверие к пакету решается отдельно. Каждый шлюз отказывает закрыто со своей диагностикой: отказ метаданных никогда не сообщается как проблема пакета, и наоборот.
2. **Режим Native.** Пакет в режиме Native обязан нести встроенную подпись RPM, которая проверяется закреплённым для источника ключом издателя. Проверка пакетов для его репозитория остаётся включённой (`gpgcheck=1` в DNF4, `pkg_gpgcheck=1` в DNF5). Добавлять ключ издателя в системную связку ключей RPM можно только после явного согласия с отпечатком этого ключа и с предупреждением, что ключ действует на всю систему: RPM проверяет подписи по одной связке ключей, не ограниченной одним репозиторием, поэтому ключ принимается и для пакетов из любого другого источника. Порядок удаления импортированного ключа фиксирует спецификация адаптера DNF до реализации режима Native.
3. **Исключение Attested (ждёт R-003).** Неподписанный RPM публикуется, только если выполнено всё сразу: его проверил промышленный верификатор аттестаций (R-003); исключение привязано к точному SHA-256 пакета; пользователь явно согласился для этого источника; эффективная политика ОС разрешает неподписанные пакеты. Политика ОС разрешает неподписанные пакеты, только если эффективное значение `%_pkgverify_level` (как его вычисляет RPM в этой системе) не равно ни `signature`, ни `all`. Пакет выдаётся из отдельного логического репозитория этого источника, содержащего только такие привязанные к digest пакеты; проверка пакетов (`gpgcheck`/`pkg_gpgcheck`) отключается только для этого репозитория Pakomichi, никогда глобально и никогда для другого репозитория, чтобы это не затрагивало подписанные пакеты источника. Если хоть одно условие не выполнено, пакет удерживается с `E_SIGNATURE_POLICY`. Аттестация никогда не превращает RPM в штатно подписанный.
4. **Никогда глобально.** Pakomichi никогда не записывает глобальные `gpgcheck=0`, `pkg_gpgcheck=0`, изменение `localpkg_gpgcheck` или `%_pkgverify_level`. Запрос на глобальное отключение отклоняется до вызова DNF.
5. **Отдельные адаптеры.** DNF4 и DNF5 — отдельные адаптеры. DNF4 пишет `gpgcheck` и `repo_gpgcheck` на уровне репозитория и считает `%_pkgverify_level` старшей политикой; DNF5 явно пишет `pkg_gpgcheck` и `repo_gpgcheck` и записывает `gpgcheck_policy`. Адаптер никогда не выдаёт настройку, которую его DNF не поддерживает. После записи applier читает обратно эффективные значения; расхождение — `E_ADMIN_APPLY_FAILED`. RPM 6 — отдельный поддерживаемый стек. Проверяется каждая поддерживаемая сборка дистрибутива, а не выводится из старшей версии DNF.
6. **Ключи.** Ключи издателей и локальный ключ метаданных разделены и никогда не взаимозаменяемы. Ротация ключа метаданных двухфазная: сначала новому ключу доверяют (перекрытие), затем метаданные подписываются им, после этого старый ключ удаляется. Потеря ключа метаданных никогда молча не создаёт новый корень доверия (N-023); восстановление — из аутентифицированной резервной копии или явным повторным доверием администратора. Промышленное хранение ключей этим ADR не решается.
7. **Сохранность байтов.** Метаданные репозитория строятся только из окончательных проверенных байтов RPM, их digest перепроверяется перед публикацией, а подпись никогда не переписывает RPM.

## Альтернативы и причины отказа

- **Считать подписанные метаданные достаточными для неподписанных RPM везде:** противоречит обязательным политикам и ADR-006.
- **Глобальный `gpgcheck=0` или пониженный `%_pkgverify_level`:** ослабляет всю систему; запрещено `AGENTS.md`.
- **Переподписывать сторонние RPM локальным ключом:** запрещено `AGENTS.md` и ADR-006.
- **Один адаптер для DNF4 и DNF5:** DNF 4.14 не знает настроек DNF5, а `gpgcheck` в DNF5 значит другое.
- **Удерживать каждый неподписанный RPM:** безопаснее всего, но по данным R-005 удерживался бы практически каждый RPM из GitHub Releases; это поведение остаётся до завершения R-003.

## Последствия

- Пока R-003 не завершён и промышленный верификатор не выбран, неподписанный RPM можно только удерживать; публиковать можно только RPM режима Native.
- `specifications/dnf.md`, `architecture/trust.md`, `architecture/data-model.md` (режим доверия к пакету для каждого артефакта) и `testing/negative.md` обновлены в обоих языках. Собственный код причины шлюзу метаданных не нужен (решено 21.10.2026 по поручению владельца): сбой собственной проверки подписанных метаданных Pakomichi — `E_SNAPSHOT_INCONSISTENT`, сбой доверия к пакету — `E_SIGNATURE_POLICY`, так что два шлюза уже дают разные коды; на клиенте сбой метаданных — собственная ошибка пакетного менеджера (N-012).
- Владелец 2026-10-20 ответил, какие эффективные настройки считаются «политика ОС разрешает неподписанные пакеты» (пункт 3).

## Подтверждение

- Доказательства: отчёт R-002, «Результаты», «Синтаксис политики зависит от версии», «Ротация и восстановление ключа метаданных», «Обязательные изменения решений»; отчёт R-005, вывод 5.
- Обязательные тесты в реализации: N-011 и N-012 на каждой поддерживаемой сборке DNF; несовпадение аттестации удерживается до DNF; запрос глобального отключения отклоняется; расхождение при обратном чтении обнаруживается; ротация ключа метаданных с перекрытием; исключение Attested — только после R-003.
