# ADR-037 — Переиспользование доказательств между синхронизациями и удержание только новых членов семейства (уточняет ADR-022, ADR-030, ADR-034)

[English](../../en/decisions/ADR-037.md) · **Русский**

**Статус:** принят владельцем проекта 25.10.2026 («согласен с рекомендациями»). Пункт 1 уточняет, когда доказательства ADR-030 и ADR-034 запрашиваются заново. Пункт 2 для уже запиненных семейств заменяет правило «семейство пинится целиком или никак» из ADR-022, пункт 1, и из `specifications/apt.md`. Больше ничего не заменяет.  
**Дата:** 25.10.2026.

## Контекст

- Каждый `pchi sync` заново спрашивает у GitHub доказательства каждого релиза листинга: аттестации каждого asset, ссылку тега и коммит, на который он указывает, — около трёх запросов на asset. Без токена GitHub даёт 60 запросов в час на внешний адрес, и условный запрос с ответом `304 Not Modified` тоже засчитывается (измерено 25.10.2026: 34 → 33). При четырёх-пяти релизах стенд P3-007a исчерпал этот бюджет на третьей синхронизации за час (`E_FORGE_UNAVAILABLE`). Получатель с таймером синхронизации — тоже.
- Шлюз пинов от 25.10.2026 удерживает семейство целиком, если хотя бы один член нельзя запинить. Когда у нового члена уже запиненного семейства есть равная версия в другом источнике, снимаются и пины установленных членов, и, пока пользователь не решит, более высокая версия другого источника может забрать их под обычной командой обновления (ADR-022, пункт 3).

## Решение

1. **Проверенное доказательство тех же байтов переиспользуется; полная проверка — не реже раза в сутки.**
   - Артефакт, у которого ID asset и SHA-256 уже записаны в том же источнике с доказательством Strict или Attested, сохраняет это доказательство без запроса к GitHub. Доказательство Attested переиспользуется только если его подписант — текущий подписант Attested источника, а его ref — тот, который правило ref подписанта даёт для этого релиза (ADR-036, пункт 1).
   - Полная проверка, как и раньше, спрашивает GitHub о каждом релизе листинга. Она выполняется при первой синхронизации источника, когда последней полной проверке источника 24 часа или больше, и по `pchi sync --force`. Время последней полной проверки хранится по источнику.
   - Результат без доказательства (`Nothing`) или недействительный никогда не переиспользуется: он запрашивается заново при каждой синхронизации.
   - Каждая синхронизация по-прежнему сверяет идентичность репозитория по ID и читает листинг релизов, поэтому передача, замена, удалённый релиз и подменённый asset (новые байты под тем же ID, `E_ASSET_MUTATED`) видны сразу.
2. **Уже запиненное семейство сохраняет пины запиненных членов; ждут только новые.**
   - Члены семейства делятся на запиненных (есть открытая активация) и новых. Новые пинятся вместе или никак: если хотя бы один из них APT ещё не видит или у него есть равная версия в другом источнике, удерживаются все новые члены с указанием причины, а запиненные сохраняют пины.
   - Если равная версия в другом источнике есть у одного из запиненных членов, удерживается всё семейство, как требует ADR-022, пункт 1: сам этот пин мог бы поднять файл другого источника.
   - Семейство без запиненных членов обрабатывается как раньше: целиком или никак.

## Альтернативы и причины отказа

- **Обязательный токен для частой синхронизации:** перекладывает затраты на каждого получателя и всё равно повторяет одни и те же вопросы. Подходит как вариант для многих источников, но не как единственный способ уложиться в лимит.
- **Условные запросы (ETag):** `304` без токена всё равно засчитывается в лимит.
- **Переиспользование без полной проверки по расписанию:** удалённую аттестацию или перенесённый тег никто бы не заметил.
- **Сохранить правило «целиком» для уже запиненных семейств:** снимает защиту установленных членов из-за члена, который ещё не установлен.

## Последствия

- Удалённая аттестация или тег релиза, перенесённый после проверки, обнаруживаются при следующей полной проверке — в течение 24 часов или по `pchi sync --force`. Байты тем временем те же, а переиспользуемый bundle был проверен офлайн против доверенных корней, когда его записали.
- Миграция 0006 хранит время последней полной проверки доказательств по источнику. `pchi sync --force` принудительно запускает полную проверку.
- Синхронизация без полной проверки стоит двух запросов плюс около трёх на каждый ранее не виденный asset.
- Ограничение пункта 2: если новая версия запиненного члена зависит от удержанного нового члена, APT разрешает эту зависимость оттуда, где находит члена, — это может быть равная версия другого источника. Удержанный член показан с `E_SOURCE_AMBIGUOUS` в итоге операции и в статусе, так что пользователь видит его до обновления.
- `specifications/apt.md`, `specifications/cli-api.md` и `architecture/trust.md` описывают правила на обоих языках.

## Проверка

- Тесты: вторая синхронизация тех же байтов ничего не спрашивает у GitHub об их доказательстве; полная проверка выполняется, когда последней 24 часа, и по `--force`; сменённый подписант или другой ref не переиспользуются; результат без доказательства запрашивается заново; подменённый asset по-прежнему `E_ASSET_MUTATED`; новый член с равной версией в другом источнике удерживается один, а запиненные члены сохраняют пины; равная версия запиненного члена удерживает всё семейство.
- Стенд P3-007a проходит свои синхронизации за один час, не дожидаясь бюджета.
