# ADR-030 — Промышленный верификатор аттестаций: `sigstore-verify` под слоем политики Pakomichi

[English](../../en/decisions/ADR-030.md) · **Русский**

**Статус:** принято владельцем проекта 2026-10-22 вместе с его решениями того же дня по P1-003c. Выполняет п. 9 ADR-017 в части верификатора и ничего не заменяет. Перекрёстная проверка на тестовом репозитории владельца после переименования и передачи (P1-003b) остаётся условием закрытия P1-003c, а не этого решения. Предложение п. 7 о читателях версии 1 заменено ADR-031. ADR-034 уточняет его хранимыми bundle и поиском аттестаций после передачи.  
**Дата:** 2026-10-22.

## Контекст

ADR-005 и ADR-027 определяют два уровня доверия GitHub. Strict требует проверенной release attestation неизменяемого релиза; Attested — проверенной аттестации артефакта, привязанной к закреплённому ID репозитория и к точным байтам. П. 9 ADR-017 сделал GitHub CLI только эталоном для R-003 и оставил выбор промышленного верификатора за R-003. П. 3 ADR-023 ждёт его, прежде чем неподписанные RPM смогут пользоваться исключением Attested.

R-003 установило, что должен делать верификатор и почему им не может быть `gh`:

- **Release attestation.** Release attestation на github.com подписывает собственный удостоверяющий центр GitHub. В её сертификате есть только SAN `https://dotcom.releases.github.com`: ни Fulcio-claims, ни issuer, ни SCT, ни записи в журнале прозрачности, и одна метка времени RFC 3161. Этот SAN одинаков для всех репозиториев, поэтому привязка есть только внутри подписанного предиката `https://in-toto.io/attestation/release/v0.2`: `repositoryId`, `packageId`, `ownerId`, `databaseId` (ID релиза), `tag`, subject `sha1` для коммита тега и по одному именованному subject `sha256` на каждый файл релиза.
- **Аттестации артефактов.** Аттестации публичных репозиториев подписывает public-good Sigstore (Fulcio, SCT, Rekor). Claims сертификата `1.3.6.1.4.1.57264.1.15` и `.1.17` несут неизменяемые ID репозитория и владельца.
- **Почему не `gh`.** `gh attestation verify` привязывается по имени репозитория, на разные причины даёт одну ошибку и не умеет проверять release attestation без сети. `gh release verify` (v2.103.0) сверяет тег и digest, но не `repositoryId`. Три уязвимости сопоставления, исправленные после 2.95.0 (GHSA-mm27-mwq9-fr5g, GHSA-wjmr-j3rp-mh2g, GHSA-4mq3-hpgx-9cx8), показывают, как легко ошибиться при сравнении по имени и шаблону.

## Решение

1. **Библиотека.** Pakomichi проверяет аттестации библиотекой `sigstore-verify` из `sigstore/sigstore-rust`. Зависимость берётся только от опубликованных крейтов, никогда от Git-источника (`deny.toml`: `allow-git = []`): `sigstore-verify`, `sigstore-crypto`, `sigstore-trust-root` и `sigstore-types`, каждый закреплён на `=0.15.0` с `default-features = false`. Транзитивные `sigstore-bundle`, `sigstore-merkle`, `sigstore-rekor` и `sigstore-tsa` приходят той же версии, тоже без функций по умолчанию. Лицензия библиотеки — Apache-2.0, версия до 1.0; этот известный риск владелец принял 2026-10-22.
   - Обновление — осознанное изменение. Оно повторяет прогон кейсов пробы из п. 9 и записывает результат в журнал доказательств.
   - Версии ниже 0.12 недопустимы: находки аудита Trail of Bits TOB-SIGSTORE-6/9/11 исправлены только в 0.12.
   - В графе не может быть `aws-lc-rs` и `aws-lc-sys`; гейт проверяет это через `cargo tree -i`.
   - Найденный в библиотеке дефект исправляется в upstream: пулреквест отправляет владелец, кандидаты ведутся локально. Pakomichi никогда не держит исправленный форк.
2. **Криптографический провайдер.** Pakomichi один раз при старте процесса, до любой проверки, устанавливает собственный `sigstore_crypto::CryptoProvider` только для проверки, на `ring` (той же версии `ring`, что у TLS-стека ADR-017).
   - Процесс, который не смог его установить, не запускается. Без провайдера `sigstore-crypto` паникует при первом использовании (кейс пробы N42).
   - ECDSA по готовому хешу и ML-DSA в `ring` недоступны и отказывают закрыто. Для DSSE-bundle не используется ни то, ни другое.
3. **Граница.** Библиотека стоит за интерфейсом верификатора Pakomichi. Он принимает байты bundle, корень доверия и ожидаемую идентичность, а возвращает либо проверенный результат с флагами доказательств, либо один подкод (п. 7). Замена, например собственный верификатор, оформляется заменяющим ADR за тем же интерфейсом. Проверка идёт в непривилегированном процессе, никогда не в административном применителе. Bundle — сетевой ввод; его размер проверяется до разбора.
4. **Два верификатора с раздельными корнями доверия, корни никогда не смешиваются.**
   - **Strict:** корень GitHub (удостоверяющие центры и службы меток времени). Политика требует:
     - цепочку сертификата до этого корня;
     - SAN ровно `URI:https://dotcom.releases.github.com`;
     - хотя бы одну проверенную метку времени RFC 3161.

     Журнал прозрачности и SCT пропускаются: у экземпляра GitHub нет ни того, ни другого. Предикат должен быть release v0.2.
   - **Attested:** корень public-good. Политика требует полную цепочку, проверенный SCT, доказательство включения в Rekor с подписанной контрольной точкой и issuer ровно `https://token.actions.githubusercontent.com`. Предикат должен быть `https://slsa.dev/provenance/v1`.
   - Bundle, действительный только под другим корнем, отклоняется (кейсы пробы N8, N9).
   - Attested принимает только аттестации public-good. Аттестации артефактов экземпляра GitHub без журнала прозрачности, которыми пользуются приватные репозитории, отклоняются (решение владельца D3).
5. **Привязка по неизменяемым ID; имена не привязывают.** Все сравнения точные и с учётом регистра, без сравнения по префиксу и шаблону.
   - **Strict** (решение владельца D4). Должно выполняться всё перечисленное, иначе отказ:
     - `repositoryId == packageId ==` закреплённый ID репозитория;
     - `ownerId ==` закреплённый ID владельца;
     - `databaseId ==` ID релиза из API;
     - `tag ==` тег релиза;
     - subject `sha1` `==` SHA объекта ссылки на тег (`/repositories/{id}/git/ref/tags/<tag>`) как есть, без разыменования: коммит для лёгкого тега, объект тега для аннотированного (уточнено 22.10.2026 с одобрения владельца после того, как `github/github-mcp-server` v2.0.2 показал объект тега; `gh` сравнивает то же значение);
     - у subject с именем файла релиза — SHA-256 этого файла.

     Флаг API `immutable` по-прежнему обязателен по ADR-005, но сам по себе доказательством не служит. После передачи репозитория (transfer) меняется ID владельца, поэтому источник нужно подтвердить заново.
   - **Attested.** Должно выполняться всё перечисленное:
     - `.1.15 ==` закреплённый ID репозитория, `.1.17 ==` закреплённый ID владельца;
     - workflow подписанта (`.1.9` после URI исходного репозитория) `==` настроенному пути workflow, а его ref `==` настроенному ref;
     - `.1.14 ==` ref релиза, `.1.13 ==` коммит релиза (коммит, на который указывает тег, после разыменования);
     - `.1.11 == github-hosted`.

     Подписантом должен быть сам исходный репозиторий, поэтому в 0.1 переиспользуемый workflow из другого репозитория (например, отдельный генератор SLSA) отклоняется. Поддержка такого подписанта, закреплённого по собственному ID репозитория, требует отдельного ADR.
   - Сменившееся имя репозитория при неизменных ID — не отказ. Об этом сообщается уведомлением (кейсы пробы O1, O2).
6. **Что читается и когда.**
   - In-toto statement читается из того же bundle в памяти, который проверялся. Он интерпретируется только после проверки подписи конверта над ним; до этого он лишь выбирает, какие bundle пробовать (кейс пробы N39).
   - Проверки до криптографии: не больше 256 КиБ на bundle и 16 bundle на digest; только media type bundle v0.3; только DSSE ровно с одной подписью и типом содержимого `application/vnd.in-toto+json`.
   - Набор bundle проходит, если один bundle прошёл все проверки. Иначе сообщается первый отказ.
7. **Причины (решение владельца D5).** Неудачная проверка — это `E_ATTESTATION_INVALID` с типизированным подкодом. Отсутствие доказательства остаётся `E_EVIDENCE_DOWNGRADE`: нет bundle, нет release attestation в режиме Strict или нет provenance в режиме Attested. Контракт событий причин получает необязательное поле `subcode`, которое есть только у `E_ATTESTATION_INVALID`, в событии причины `schema_version` 2; читатели версии 1 продолжают работать по одному коду. Подкоды:

   | Подкод | Что охватывает |
   |---|---|
   | `bundle_too_large`, `too_many_bundles` | пределы размера из п. 6 |
   | `bundle_malformed`, `bundle_unsupported` | ошибка разбора; media type, вид содержимого, число подписей, тип содержимого; структурные правила библиотеки |
   | `signature_invalid` | подпись DSSE над statement |
   | `artifact_digest_mismatch` | байты не являются subject этого statement |
   | `certificate_untrusted`, `certificate_time`, `sct_invalid` | цепочка или профиль сертификата; нет центра или сертификата, действительного на проверенное время; SCT |
   | `tlog_inclusion`, `tlog_checkpoint`, `tlog_promise`, `tlog_entry` | доказательство включения; контрольная точка; обещание включения или время интеграции; запись не описывает bundle, повреждена или журнал неизвестен |
   | `timestamp_invalid`, `no_verified_time` | токен RFC 3161; нет ни одного проверенного времени |
   | `identity_mismatch` | SAN или OIDC issuer |
   | `repository_id_mismatch`, `owner_id_mismatch` | п. 5 |
   | `release_mismatch`, `subject_mismatch` | ID релиза, ID пакета, тег или объект ссылки на тег; имя файла релиза и digest |
   | `workflow_mismatch`, `ref_mismatch`, `commit_mismatch`, `runner_not_hosted` | п. 5 |
   | `statement_invalid` | тип statement или повреждённый statement после проверки |
   | `trust_root_invalid` | дефект самого корня доверия, например нет ключей CT-журналов; выдаётся для диагностики через `pchi doctor` |

8. **Корни доверия обновляются через TUF (решение владельца D2).**
   - Оба корня обновляются из своих TUF-репозиториев через `sigstore-tuf` (`default-features = false`) по собственному HTTP-стеку Pakomichi. Через функцию `tuf` крейта `sigstore-trust-root` они не берутся никогда: она включает функции `sigstore-tuf` по умолчанию, а с ними `aws-lc-rs`.
   - Если метаданные TUF истекли и обновить их не удаётся, проверка отказывает закрыто с причиной, называющей корень. Pakomichi никогда не продолжает молча проверять по корню, который больше не может обновить.
   - Клиент TUF вместе с транспортом проверяется в P2-003; эта проба его не затрагивала.
9. **Доказательства и эталон.**
   - Кейсы `research/r-003/verifier-probe-cases.sh` — приёмочный набор для любого обновления или замены верификатора. Их результаты лежат в `research/r-003/results/verifier-probe-cases.tsv`.
   - Эталон для перекрёстных проверок R-003 — `gh` 2.103.0 или новее, закреплённый по SHA-256. `cosign` вторым эталоном не добавляется, пока `gh` и Pakomichi не разойдутся.

## Альтернативы и причины отказа

- **Крейт `sigstore` 0.14 (sigstore-rs):** помечен экспериментальным, `aws-lc-rs` обязателен, поддержки RFC 3161 нет, а значит, нет Strict.
- **`gh`, `cosign` или `sigstore-go` во время работы:** зависимость от среды Go, привязка по имени, одна нетипизированная ошибка, а в `gh` нет Strict без сети.
- **`jdx/sigstore-verification` 0.2.8:** обёртка над старым `sigstore` 0.13 с `reqwest` и `tokio`. Скачивает аттестации из сети, привязывается по имени владельца и репозитория и не поддерживает RFC 3161. На неё не опирается ни один опубликованный крейт; сам mise перешёл на `sigstore-verify`.
- **Собственный верификатор:** 3–5 тысяч строк кода, критичного для безопасности, без внешней проверки. Остаётся запасным вариантом за интерфейсом из п. 3.
- **Ждать 1.0:** срока нет, а Strict и Attested всё это время были бы заблокированы.
- **Мелкие крейты (`sigstore-verifier`, `attestation-verify`, `airgap-verify`):** недостаточно зрелые или построены на той же библиотеке.

## Последствия

- P2-003 (Strict) и P2-004 (Attested) реализуют пп. 2–8 за интерфейсом из п. 3. Проба — исследовательский инструмент, а не код продукта.
- `specifications/errors.md` получит событие причины `schema_version` 2 с `subcode`, когда его реализует P2-003. До тех пор контракт остаётся v1.
- П. 3 ADR-023 сможет опираться на результат Attested, когда будет реализована P2-004. Сама по себе проба его не включает.
- Набор зависимостей в обычном графе пробы вырастает на 56 крейтов. Единственный дубль — `syn` 2 и 3 времени сборки.
- Риски:
  - частые изменения до 1.0 и один основной сопровождающий;
  - у библиотеки нет опубликованного аудита, кроме находок, исправленных в 0.12;
  - Strict держится только на удостоверяющем центре и службе меток времени GitHub;
  - ID в предикате — расширения GitHub сверх in-toto release v0.2: если GitHub их уберёт, Strict будет отказывать везде.

## Доказательства

- `research/r-003/verifier-probe/` (крейт пробы), `verifier-probe.sh` (сборка и проверки зависимостей), `verifier-probe-inputs.py` (подделанные входы), `verifier-probe-cases.sh` (кейсы), `verifier-probe-oracle.sh` (сверка с `gh`).
- Результаты: `research/r-003/results/verifier-probe-cases.tsv` и `verifier-probe-oracle.tsv`. Сырые журналы — в `.research-local/p1-003c/`.
- Перекрёстная проверка на тестовом репозитории владельца после переименования, занятия старого имени, передачи и форка (`verifier-probe-owner.sh`, `research/r-003/results/verifier-probe-owner.tsv`): 10 из 10 как ожидалось. Новый репозиторий, занявший старое имя, отклоняется по ID репозитория, а `gh` без сети принимает его по имени. После передачи аттестации, сделанные до неё, несут прежний ID владельца, поэтому подтверждение нового владельца не должно делать недействительными релизы, аттестованные при старом (P2-003, P2-004).
- Кабинетный анализ: исходники крейтов 0.15.0, отчёт R-003, прогоны R-003 от 2026-10-20 и 2026-10-22.
