# ADR-020 — Системная SQLite 3.34.1 без таблиц STRICT

[English](../../en/decisions/ADR-020.md) · **Русский**

**Статус:** принято владельцем проекта 2026-10-20; заменяет (supersedes) только пункт 2 ADR-017. Остальные пункты ADR-017 остаются в силе.  
**Дата:** 2026-10-20.

## Контекст

Пункт 2 ADR-017 выбирает `rusqlite 0.40.2` с библиотекой SQLite из дистрибутива и требует SQLite 3.37 или новее, потому что миграция 0001 объявляла каждую таблицу `STRICT`. R-004 установил, что AlmaLinux 9.8 поставляет `sqlite-libs-3.34.1-11.el9_8` ([отчёт R-004](../research/R-004-report.md), вывод 15). SQLite 3.34.1 не разбирает `STRICT`: на этой системе прежняя миграция 0001 падает с `near "STRICT": syntax error`. Поэтому для семейства EL9 требовалось одно из трёх изменений: встроенная SQLite для EL9, отказ от таблиц `STRICT` или исключение EL9 из 0.1.

`STRICT` использовался только для контроля типов хранения столбцов. То же правило записывается ограничениями `CHECK (typeof(column) = ...)`, которые понимает любая версия SQLite, на которую может ориентироваться Pakomichi. Сам `rusqlite 0.40.2` поддерживает SQLite 3.34.1 или новее: его привязки по умолчанию — `min_sqlite_version_3_34_1`.

Миграция 0001 ни разу не применялась к установке: ни один пакет или выпуск её не поставлял. Поэтому её ещё можно править на месте, как это было сделано при доработке P0-002 по ревью; её версия остаётся 1, а имя — `initial`.

## Решение

1. Сохранить `rusqlite 0.40.2` с отключёнными default features и **библиотекой SQLite из дистрибутива** на каждом поддерживаемом дистрибутиве, включая EL9. Встроенная (bundled) SQLite по умолчанию не используется; её включение где-либо требует нового решения владельца.
2. Не использовать таблицы `STRICT`. Каждый столбец каждой таблицы несёт проверку типа первым ограничением: `CHECK (typeof(c) = 'text')` или `CHECK (typeof(c) = 'integer')` для столбца `NOT NULL` и `CHECK (typeof(c) IN ('text', 'null'))` для столбца, допускающего NULL. Объявленные типы сохраняют свою affinity, поэтому результат совпадает с таблицей `STRICT`: значение, которое преобразуется без потерь (целое 5 в `TEXT`, текст `'5'` в `INTEGER`), сохраняется в объявленном типе, а любое другое значение (BLOB в `TEXT`, `'abc'` или 1.5 в `INTEGER`) отклоняется. `INTEGER PRIMARY KEY` — это rowid, и нецелое значение для него отклоняет сама SQLite. Все внешние ключи, ограничения `UNIQUE`, триггеры и существующие проверки не меняются.
3. Минимальная поддерживаемая версия SQLite — **3.34.1**. Это самая старая версия, на которой запускались схема и её тесты (AlmaLinux 9.8), и это нижняя граница `rusqlite 0.40.2`. Схема и приложение не должны использовать возможности SQLite новее 3.34.1, в том числе `RETURNING` и `ALTER TABLE ... DROP COLUMN` (3.35.0), `STRICT` (3.37.0), `unixepoch()` и операторы `->`/`->>` (3.38.0). SQL не должен полагаться на параметры сборки, которые дистрибутив может не включить, например на JSON-функции до 3.38.0; JSON-столбцы хранятся как текст и разбираются в Rust.
4. Миграция 0001 изменена на месте в форму из пункта 2. Последующие миграции следуют тому же правилу и проверяются на самой старой поддерживаемой SQLite.
5. Владелец состояния проверяет версию SQLite во время выполнения (`sqlite3_libversion_number()`) до открытия базы состояния и отказывается запускаться на версии ниже 3.34.1 с понятной диагностикой. Код причины и сообщение фиксирует задача, которая добавляет `rusqlite` в основной crate.

Платформа, системная SQLite которой старше 3.34.1, этим решением не поддерживается. Её добавление требует доказательств на этой платформе и отдельного решения владельца (например, встроенной SQLite только для этой платформы).

## Рассмотренные альтернативы

- **Встроенная SQLite только для EL9:** сохраняет `STRICT`, но поставляет вторую SQLite в одном семействе пакетов, делает Pakomichi ответственным за обновления безопасности SQLite на EL9 и раздваивает матрицу сборки. Отклонено владельцем проекта.
- **Встроенная SQLite везде:** одна версия SQLite на всех платформах, но та же стоимость обслуживания на каждом дистрибутиве и дубликат библиотеки, которую и так поставляет каждая целевая система. ADR-017 уже отклонил её как вариант по умолчанию. Отклонено владельцем проекта.
- **Без EL9 в 0.1:** сохраняет схему без изменений, но исключает семейство EL9 — платформу DNF4, на которой выполнялись R-001, R-002 и R-004, хотя схеме не нужна ни одна возможность новее 3.34.1. Отклонено владельцем проекта.
- **Без контроля типов:** обычная affinity SQLite приняла бы BLOB или произвольный текст в любом столбце. Отклонено, потому что ошибки типов в столбцах идентичности и digest должны отклоняться в базе данных, а не только в коде приложения.

## Последствия

Схема контролирует те же типы хранения, что и прежде, на SQLite 3.34.1 и новее, а EL9 продолжает использовать SQLite из дистрибутива с её обновлениями безопасности. Каждое определение таблицы стало длиннее; столбец, добавленный без проверки типа, обнаруживают тесты миграций, которые пробуют значение неверного типа в каждом столбце каждой таблицы.

Каждый SQL-оператор Pakomichi ограничен возможностями SQLite 3.34.1. `RETURNING` недоступен, а удаление столбца в forward-only миграции требует пересборки таблицы.

Поддерживаемые платформы, версия SQLite которых не сверена с 3.34.1, остаются непроверенными до такой сверки. Сюда входит RED OS 7.3. Такую платформу нельзя объявлять поддерживаемой, пока не записана версия её SQLite и на ней не прошли тесты миграций. Astra Linux 1.7.6 проверена 20.10.2026: в ней `libsqlite3-0 3.34.1-3+ci202402082153+astra2` (бэкпорт Astra новее версии Debian 10), миграция 0001 применяется, и 13 тестов миграций проходят на её Python 3.7.3.

`prototypes/p0-004/tests/stack.rs` сохраняет проверку SQLite 3.37 или новее: это записанное доказательство P0-004 для ADR-017, а не требование продукта.

## Подтверждение

- `python3 -m unittest discover -s tests -p "test_*.py" -v` на AlmaLinux 9.8 (`sqlite-libs-3.34.1-11.el9_8`, Python 3.9.25, `_sqlite3` связан с `/lib64/libsqlite3.so.0`, `sqlite3.sqlite_version` = 3.34.1): 13 тестов пройдены. Те же тесты проходят на Windows-хосте (SQLite 3.45.3) в составе `scripts/quality.ps1`.
- Контроль на той же системе: прежняя миграция 0001 со `STRICT` падает с `near "STRICT": syntax error`.
- Негативные тесты в `tests/test_schema_migrations.py`: значение неверного типа отклоняется проверкой типа в каждом столбце всех 16 таблиц (BLOB в `TEXT`; `'not-an-integer'`, 1.5 и BLOB в `INTEGER`); каждый столбец, допускающий NULL, принимает NULL; значения без потерь сохраняются в объявленном типе. Удаление одной проверки типа из миграции приводит к провалу постолбцового теста.
