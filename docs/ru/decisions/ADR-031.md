# ADR-031 — События причин v2 с подкодом аттестации

[English](../../en/decisions/ADR-031.md) · **Русский**

**Статус:** принято владельцем проекта 2026-10-22. Заменяет последнее предложение п. 5 ADR-029 («события причин внутри ответов сохраняют wire contract v1») и предложение п. 7 ADR-030 о читателях версии 1; больше ни в одном из них ничего не меняется.  
**Дата:** 2026-10-22.

## Контекст

П. 7 ADR-030 (решение владельца D5) даёт каждой неудачной проверке аттестации типизированный подкод под `E_ATTESTATION_INVALID`; он передаётся в необязательном поле `subcode` события причины с `schema_version` 2. Там же сказано, что читатели версии 1 продолжают работать по одному коду. Это неверно: контракт версии 1 в `specifications/errors.md` отвергает неизвестную `schema_version` и неизвестные поля, поэтому читатель версии 1 отвергает любое событие версии 2.

П. 5 ADR-029, принятый раньше, говорит, что события причин внутри ответов IPC сохраняют wire contract v1. Вместе эти два решения не могут выполняться для отказа аттестации, который проходит через IPC.

## Решение

1. **Две версии.** Версия 1 не меняется. Версия 2 — это версия 1 плюс `reason.subcode`, значение которого — один из подкодов п. 7 ADR-030 (`specifications/errors.md`, «Wire contract v2»).
2. **Версия 2 только когда нужна.** Писатель использует версию 2 только для `E_ATTESTATION_INVALID` с подкодом. Все остальные события, в том числе `E_ATTESTATION_INVALID` без подкода, остаются версией 1. Поэтому читатель версии 1 продолжает читать все остальные события и отвергает только события версии 2, как того требует его контракт.
3. **Читатели.** Читатели Pakomichi (CLI, клиент IPC и служба) принимают обе версии. Событие версии 2 без `subcode`, событие версии 1 с ним, `subcode` при другом коде и неизвестный `subcode` отвергаются. CLI и служба поставляются вместе, поэтому ни один установленный читатель не старше писателя.
4. **IPC.** События причин внутри ответов IPC следуют этому контракту, версиям 1 и 2. Конверт сообщений IPC из ADR-029 (его собственная `schema_version` 1) не меняется.
5. **Сообщение.** `message` отказа аттестации — фиксированный текст для его подкода. Подробности верификатора могут цитировать значения сертификата или bundle из сети и сохраняются только для локальной диагностики.

## Альтернативы и причины отказа

- **Оставить только версию 1, а подкод писать в текст сообщения:** просто, но не машиночитаемо, то есть отменяет решение владельца D5.
- **Оставить событие причины в версии 1, а подкод добавить отдельным полем ответа IPC:** контракт причин сохраняется, но причина хранится в двух местах, а собственный вывод CLI остаётся без подкода.
- **Сделать все события версией 2:** любой читатель версии 1 отвергал бы всё, в том числе события без подкода.

## Последствия

- `src/error.rs`: `REASON_SCHEMA_VERSION` (1), `REASON_SCHEMA_VERSION_SUBCODE` (2), `ATTESTATION_SUBCODES`, `ReasonSubcode`, `Reason::attestation_invalid`. `ReasonEvent::new` выбирает версию по наличию подкода.
- `AttestationFailure::reason` строит событие: версию 2 для недействительной аттестации и версию 1 `E_EVIDENCE_DOWNGRADE` для отсутствующего доказательства.
- Контрактные тесты проверяют обе версии, все перечисленные отказы и то, что подкоды в `specifications/errors.md` совпадают с `ATTESTATION_SUBCODES` и со списком `SubReason` верификатора.
