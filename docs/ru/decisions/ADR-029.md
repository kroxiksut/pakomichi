# ADR-029 — Локальный IPC: Unix-сокет на каждый канал и JSON с префиксом длины

[English](../../en/decisions/ADR-029.md) · **Русский**

**Статус:** принято владельцем проекта 2026-10-21. Уточняет ADR-009 и пункт 7 ADR-017, ничего не заменяет. Ко всем сообщениям из этого решения применяется пункт 2 ADR-019. Последнее предложение пункта 5 заменено ADR-031. Пункты 2, 5 и 8 уточнены ADR-033. Пункты 2 и 3 уточнены ADR-035.  
**Дата:** 2026-10-21.

## Контекст

Пункт 7 ADR-017 разделяет Pakomichi на непривилегированное ядро и владельца состояния, одноразовый инспектор пакетов, read-only reader репозиториев, signer метаданных и узко привилегированный административный applier и делает сообщения IPC и владение файлами границей полномочий. ADR-009 требует read-only status API и привилегированного помощника, который применяет только собственные файлы Pakomichi. `specifications/cli-api.md` требует, чтобы согласие, одобрение релиза и восстановление сокета были административными и интерактивными и никогда не были доступны через status API, loopback-HTTP или `--yes`. Пункт 2 ADR-019 требует для каждого собственного формата Pakomichi явного `schema_version`, отказа на неизвестные поля и преобразования в проверенные доменные типы. Транспорт и кадрирование оставались открытыми (`architecture/overview.md`, «Неопределённые детали»).

Pakomichi работает только на Linux с systemd (ADR-014, ADR-026). Известные классы отказов локального протокола службы, которые это решение должно исключить: решение о полномочиях берётся из поля запроса; проверка живости стоит в очереди за долгой операцией, и «занят» читается как «мёртв»; идентификаторы операций можно угадать; отсутствующее поле молча означает «выключено» для защиты; одно значение по умолчанию объявлено по обе стороны провода и расходится; атрибуты сериализации переименовывают не то, что ожидал автор; ответ обрезан, потому что поток закрыли до сброса буфера.

## Решение

1. **Транспорт.** Локальный IPC использует потоковые Unix domain sockets, которые создают socket-юниты systemd в `/run/pakomichi/` (`RuntimeDirectory`, режим 0755, владелец root). Процессы получают их уже привязанными; запасного самостоятельного bind нет. Ни один сокет IPC не является TCP-сокетом, и никакой IPC Pakomichi не доступен из сети.
2. **Один сокет на канал; полномочия решает канал.**

   | Сокет | Режим и владелец | Допустимые собеседники | Допустимые запросы |
   |---|---|---|---|
   | `/run/pakomichi/status.sock` | 0666, root | любой локальный пользователь | только запросы чтения |
   | `/run/pakomichi/admin.sock` | 0600, root | только uid 0 | запросы чтения и административные |
   | `/run/pakomichi/apply.sock` | 0600, системный пользователь владельца состояния | только uid владельца состояния | запросы applier от владельца состояния |

   - Слушающий процесс наследует сокет от systemd, поэтому владелец файла решает только, кто может подключиться: владелец состояния обслуживает `status.sock` и `admin.sock`, а root-applier — `apply.sock`, который должен открываться непривилегированным владельцем состояния.
   - Сервер читает `SO_PEERCRED` (uid, gid, pid) на каждом принятом соединении и сверяет uid с таблицей до чтения первого кадра; несовпадение закрывает соединение без ответа. Режим файла — второй барьер, а не единственный.
   - Административные запросы требуют root (`sudo pchi …`), как у `apt` и `dnf`. Делегированной группы администраторов в 0.1 нет: `SO_PEERCRED` несёт только основной gid, поэтому проверка группы требует отдельного проекта и заменяющего решения.
   - У каждого канала свой тип запроса в коде. В типе канала статуса нет административных вариантов, поэтому административный запрос в нём не разбирается и отклоняется как неизвестный вариант; сервер никогда не выбирает проверку по полю запроса. Какие проверки нужны запросу, сервер вычисляет сам — по типу запроса и каналу.
3. **Дочерние процессы.** Инспектор пакетов и signer — дочерние процессы владельца состояния и общаются с ним через стандартные ввод и вывод с тем же кадрированием и теми же правилами сообщений. Инспектор обрабатывает ровно один запрос за процесс (ADR-017). Signer в 0.1 обрабатывает один запрос подписи за запуск. Стандартный поток ошибок несёт только диагностику и ограничен, как сейчас у инспектора.
4. **Кадрирование.** Каждое сообщение — один кадр: 4-байтовая беззнаковая длина в порядке big-endian и ровно столько байтов JSON в UTF-8. Кадр запроса — не больше 1 МиБ, кадр ответа — не больше 8 МиБ. Длина больше предела, нулевая длина, обрезанный кадр или неверный UTF-8 закрывают соединение без разбора. На соединении в полёте один запрос; клиент, которому нужна параллельная работа, открывает больше соединений.
5. **Сообщения.** Каждое сообщение — JSON-объект с `schema_version` (1 для этого протокола) и `type`. Типы провода используют `#[serde(deny_unknown_fields)]` и преобразуются в проверенные доменные типы (ADR-019). На неизвестный `schema_version` отвечают ошибкой с перечнем поддерживаемых версий и закрывают соединение. На неизвестное поле, неизвестный `type` или значение не того типа отвечают ошибкой, и никакая часть запроса не применяется. События причин внутри ответов сохраняют wire contract v1 из `specifications/errors.md`.
   - У поля, которое выключает, ослабляет или подтверждает защиту, нет значения по умолчанию: оно обязательно, и запрос без него отклоняется. Частичное обновление называет поля, которые меняет; полная замена обязана нести их все.
   - Значение по умолчанию, нужное обеим сторонам, определено один раз — в протокольном модуле на Rust, и CLI использует этот модуль; второй копии нет.
6. **Живость.** На `ping` отвечает цикл приёма каждого канала, не ставя его в очередь работы, в пределах короткого дедлайна. Долгая административная работа никогда не выполняется внутри запроса: запрос запускает операцию и сразу возвращает её идентификатор, а ход читается запросами статуса. Поэтому истекший таймаут живости значит, что сервер не отвечает, а не что он занят.
7. **Идентификаторы операций.** Идентификатор операции — 128 бит из криптографического источника случайности ОС, записанные 32 строчными шестнадцатеричными символами, и он привязан к uid, запустившему операцию. Чтение или отмена операции требует того же uid или uid 0; неизвестный и чужой идентификатор получают одинаковый ответ. Идентификатор сам по себе никогда не даёт полномочий.
8. **Подтверждение административных действий.** CLI показывает план и спрашивает администратора интерактивно (`cli-api.md`). Сервер сначала возвращает план с digest его точного содержимого; подтверждающий запрос обязан нести `confirmed: true` и этот digest и принимается только на `admin.sock`. План, изменившийся в промежутке, отклоняется. Сервер не может доказать, что ответил человек; он гарантирует, что подтверждение приходит только от root по административному каналу и только для показанного плана. `--yes` никогда не выставляет его для действий, которые исключает `cli-api.md`.
9. **Дедлайны и пределы.** На `status.sock`: первый кадр должен прийти в течение 5 секунд после приёма соединения (меньше 10 секунд, которые R-004 использовал для медленных HTTP-клиентов), бездействующее соединение закрывается через 30 секунд, не больше 8 одновременных соединений на uid и 64 всего; соединения сверх предела сразу закрываются. На `admin.sock` и `apply.sock`: не больше 4 одновременных соединений. Значения фиксирует и проверяет P2-013; изменение записывается вместе с тестом, как пункт 5 ADR-024 требует для HTTP reader.
10. **Закрытие.** Сервер пишет весь кадр ответа, сбрасывает буфер (flush), закрывает свою сторону записи и только потом закрывает сокет. Клиент читает до конца кадра ответа. Ответ никогда не пишется после того, как сервер наполовину закрыл соединение.

## Альтернативы и причины отказа

- **D-Bus (system bus):** файлы политик для демона шины, вторая модель полномочий рядом с режимами сокетов и крупная зависимость для протокола с тремя клиентами. Уместен, когда службу должны вызывать интеграция с рабочим столом или другие программы; для 0.1 не нужен.
- **gRPC или protobuf поверх сокета:** генератор кода и язык схем рядом с serde и кадрирование HTTP/2 для локального протокола «запрос — ответ». Уместны, когда API используют клиенты на многих языках; у нас это CLI на Rust и собственные процессы Pakomichi.
- **Один сокет с полем роли или токеном в запросе:** полномочия брались бы из самого запроса. Отклонено.
- **JSON, разделённый переводами строк:** просто, но размер известен только после чтения, и сообщение без перевода строки растёт до срабатывания предела. Кадры с префиксом длины отклоняют слишком большое сообщение до чтения.
- **Varlink:** подходящая модель, но дополнительный протокол и библиотека ради тех же гарантий, что даёт кадрирование выше.
- **Группа администраторов на `admin.sock` (режим 0660):** удобно, но требует проверки дополнительных групп, которой `SO_PEERCRED` не даёт, и делает членство в группе эквивалентом root для файлов Pakomichi. Отложено.

## Последствия

- Каждой административной команде нужен `sudo`; командам статуса — нет.
- Протокольный модуль общий для CLI и сервера, поэтому CLI пишется на Rust и использует те же типы сообщений.
- P2-013 реализует сокеты, кадрирование, типы запросов по каналам, проверку собеседника, пределы, путь живости, идентификаторы операций, digest плана и каналы дочерних процессов; если существующих кодов не хватает, добавляет стабильный код причины для отклонённого сообщения протокола (пункт 2 ADR-019) с согласия владельца.
- Юниты systemd из P5-004a несут пути, режимы и владельцев сокетов из пункта 2.
- `architecture/overview.md` больше не числит формат IPC неопределённым.

## Подтверждение

- Обязательные тесты в P2-013: собеседник с неверным uid отклоняется на каждом сокете; административный запрос на `status.sock` отклоняется как неизвестный; кадры больше предела, нулевой длины, обрезанные и не в UTF-8 закрывают соединение без разбора; неизвестные `schema_version`, поле или `type` отклоняются, и ничего не применяется; запрос без обязательного поля защиты отклоняется; тест формы провода закрепляет точный JSON каждого варианта запроса и ответа; `ping` отвечает в пределах дедлайна, пока идёт долгая операция; чужой и неизвестный идентификатор операции получают одинаковый отказ; подтверждение с устаревшим digest плана отклоняется; медленный клиент отсекается по дедлайну первого кадра, и предел на uid соблюдается; клиент полностью читает ответ после закрытия сервером.
- Режимы и владельцы сокетов проверяются в ВМ с настоящими юнитами systemd (P5-001, P5-004b). Ни одного из этих тестов пока нет.
