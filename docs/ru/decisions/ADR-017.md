# ADR-017 — Начальная модель эксплуатации и упаковки на Rust

[English](../../en/decisions/ADR-017.md) · **Русский**

**Статус:** принято владельцем проекта. Пункт 2 заменён ADR-020. Пункт 4 частично заменён ADR-028. Пункт 7 уточнён ADR-035.  
**Дата:** 2026-10-19.

## Контекст

ADR-015 выбирает Rust, но явно не утверждает стек зависимостей, runtime, путь упаковки или модель процессов. P0-004 проверил требуемые механизмы в изолированной VM Ubuntu 24.04 WSL2. Доказательства находятся в `docs/ru/prototypes/P0-004-stack.md`.

Сделанный здесь выбор обязан сохранить socket activation из ADR-007, разделение привилегий из ADR-009, локальную подпись только метаданных из ADR-011 и SQLite плюс CAS из ADR-013. При этом нельзя утверждать, что более широкие гипотезы R-001…R-004 прошли проверку.

## Решение

1. Сохранить Rust 1.94.1 как начальный закреплённый toolchain. Использовать Tokio 1.53.3 как обязательный async runtime для долгоживущего сетевого процесса: GitHub I/O, ленивый loopback HTTP, socket activation, таймеры, отмена и ограниченная координация. Tokio не является межпроцессным контрактом и не требуется в инспекторе, подписанте, миграции или привилегированном применителе (applier). Блокирующая работа использует ограниченный `spawn_blocking` только тогда, когда она обязана оставаться внутри процесса; разбор враждебных пакетов и привилегированные операции сохраняют свои процессные границы. Никогда не удерживать блокировку или транзакцию SQLite через `.await`.
2. Использовать `rusqlite 0.40.2` с отключёнными default features и библиотекой SQLite из дистрибутива. Требовать SQLite 3.37 или новее для таблиц `STRICT`. Сохранять единственного владельца состояния и использовать online backup API SQLite; не делать вид, что SQLite и файловая система образуют одну транзакцию.
3. Использовать `rpm 0.30.2` с отключёнными default features для инспекции заголовков RPM. Включать payload/compression только в непривилегированном сборщике fixtures/пакетов, а не в production-читателе метаданных.
4. Использовать `dpkg-deb --field/--info` для метаданных DEB за непривилегированным процессом-инспектором с ограниченными ресурсами. Никогда не вызывать install, unpack или maintainer scripts во время инспекции.
5. Использовать `gpgv` для проверки APT `InRelease` и RPM `repomd.xml.asc`. Отдельный подписант вызывает `gpg` с доступом только к локальному ключу метаданных; загрузчик, инспектор, HTTP-читатель и root-применитель этот ключ не получают.
6. Использовать `listenfd 1.0.2` для systemd socket activation. Читатель репозитория принимает только унаследованные loopback-сокеты, реализует маршруты только для чтения и не имеет fallback-привязки к внешнему интерфейсу. Fallback из ADR-007 в виде обычной службы сохраняет тот же loopback listener и протокол.
7. Разделить развёрнутые обязанности на непривилегированное ядро/владельца состояния, одноразовый непривилегированный инспектор пакетов, читатель репозитория только для чтения, подписанта метаданных и узко привилегированный административный применитель (applier). Границей полномочий служат IPC-сообщения и владение в файловой системе; разбор данных из сети никогда не выполняется от root.
8. Собирать Rust-бинарник один раз, затем собирать нативный DEB с помощью `dpkg-deb` и RPM с помощью закреплённого Rust-сборщика `rpm`. Пакеты содержат бинарник и усиленные (hardened) systemd units, но не содержат ни одного maintainer script, выполняющего операции пакетного менеджера. Поведение при установке и удалении проверяется позже в чистых VM.
9. Считать проверку attestation через GitHub CLI независимым эталонным оракулом (reference oracle) для R-003. Пока не делать `gh` или экспериментальный Rust crate `sigstore` production-зависимостью времени выполнения. R-003 обязано выбрать и перекрёстно проверить production-верификатор до P2-003/P2-004.

## Отклонённые альтернативы

- Сетевой/парсящий демон от root: противоречит ADR-009 и не потребовался в прототипе.
- Встроенная (bundled) SQLite по умолчанию: дублирует системную библиотеку и усложняет обслуживание безопасности без доказательств того, что она нужна поддерживаемым дистрибутивам.
- Выполнение скриптов DEB/RPM для получения метаданных: небезопасно и не нужно.
- Tokio в каждом процессе, включая инспекторы и привилегированный применитель: async не даёт преимуществ этим короткоживущим или намеренно изолированным операциям и размыл бы их границы полномочий.
- Повторная подпись upstream-пакетов: противоречит ADR-006 и ADR-011.
- Сделать GitHub CLI обязательным в продукте лишь потому, что он прошёл эталонный тест: прототип доказывает путь протокола, а не доступность в дистрибутивах или окончательную границу библиотеки.

## Последствия

Принятой модели достаточно, чтобы начать изолированные исследования и небольшие срезы реализации. Конкретные crates для HTTP, GitHub API и production-проверки attestation остаются решениями зависимых задач, причём R-003 — жёсткий шлюз для проверки происхождения (provenance). Сетевая конкурентность должна быть ограниченной и обеспечивать backpressure; синхронное владение SQLite и вспомогательные процессы не должны блокировать рабочие потоки Tokio. При любом провале в R-001…R-004 используется его документированный fallback или superseding ADR; это не ослабляет данную модель молча.

Пакеты, созданные в P0-004, — одноразовые fixtures и не являются поддерживаемыми выпусками. Ничего не утверждается о готовности какого-либо дистрибутива, варианта DNF, жизненного цикла загрузки или alpha.
