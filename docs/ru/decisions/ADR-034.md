# ADR-034 — Доказательства аттестации после R-003: хранимые bundle и поиск после передачи

[English](../../en/decisions/ADR-034.md) · **Русский**

**Статус:** принят владельцем проекта 23.10.2026. Уточняет ADR-030 и модель данных (`architecture/data-model.md`) и ничего не заменяет. Пункт 4 фиксирует, что условие пункта 3 ADR-023 выполнено.  
**Дата:** 23.10.2026.

## Контекст

R-003 ([отчёт](../research/R-003-report.md)) закончился тремя фактами, которые ADR-030 не решает:

- **Аттестации не следуют за передачей репозитория** (находка 6). После передачи тестового репозитория владельца в организацию `attestations/…` возвращал HTTP 404 для репозитория (по имени и по ID) и для нового владельца, а эндпоинт прежнего владельца `users/{login}/attestations/…` по-прежнему их возвращал. Поведение не менялось около 19 часов. Оно не задокументировано, о нём сообщено (обсуждение GitHub Community 211055).
- **Хранится только запись о проверке.** `trust_evidence` хранит результат проверки (`record_json`), а не проверенный bundle. Поэтому принятый артефакт нельзя проверить снова: ни для аудита, ни новой версией верификатора, ни после ротации доверенного корня, ни после передачи, когда площадка bundle больше не отдаёт.
- **Digest не определяет источник** (находка 4, шаг 5). Одни и те же байты аттестованы двумя репозиториями: форк и репозиторий, занявший старое имя, выпустили побайтно одинаковый asset, каждый со своей действительной provenance.

Пункт 3 ADR-023 разрешал исключение Attested для неподписанных RPM только после R-003. R-003 завершился с PASS 22.10.2026, а ADR-030 выбрал промышленный верификатор.

## Решение

1. **Каждый проверенный bundle хранится.** Bundle, по которым создана запись `TrustEvidence`, сохраняются в хранилище блобов по своему SHA-256 побайтно в полученном виде, в пределах ADR-030 (не больше 256 КиБ каждый и 16 на digest). Доказательство называет digest своих bundle и версии доверенных корней, по которым проверялось.
   - Доказательство можно проверить снова только по сохранённым данным. Последующая проверка (аудит, `pchi doctor`, новая версия верификатора, ротация корня) проверяет сохранённые bundle заново и никогда не скачивает их повторно для уже принятого артефакта.
   - Хранилище блобов никогда не собирает bundle, на который ссылается доказательство; доказательства только дописываются, и их bundle тоже.
   - Сохранённый bundle, который пропал или чьи байты больше не совпадают с digest, не проходит проверку с причиной целостности хранилища и никогда не считается пройденным. Записанное доказательство остаётся как факт аудита, но по нему больше ничего не допускается.
   - Будет ли ссылка столбцом (новая миграция) или частью `record_json`, решает задача реализации; сборщик хранилища блобов должен видеть её в обоих случаях.
2. **Поиск аттестаций после передачи.** Для ещё не принятого релиза верификатор ищет аттестации в таком порядке:
   1. репозиторий по ID (`/repositories/{id}/attestations/{digest}`);
   2. каждый owner ID, подтверждённый ранее для источника (миграция 0002), начиная с последнего: его текущий логин определяется по ID (`GET /user/{id}` для пользователя, `GET /organizations/{id}` для организации), затем запрашивается `users/{login}/attestations/{digest}` или `orgs/{login}/attestations/{digest}`. Сохранённый логин никогда не используется, потому что логины меняются.
   - Место поиска не добавляет доверия: bundle из любого из этих мест проходит только полную проверку ADR-030, где первым сравнивается закреплённый repository ID, а owner ID должен быть подтверждён для источника. Владелец, которого никогда не подтверждали, не запрашивается.
   - Если ничего не найдено, релиз удерживается с `E_EVIDENCE_DOWNGRADE`, а не `E_ATTESTATION_INVALID`, и статус объясняет, что после передачи аттестации недоступны.
   - Дополнительные запросы ограничены: один запрос логина и один запрос аттестаций на каждого ранее подтверждённого владельца, в пределах лимитов `specifications/github.md`.
3. **Digest никогда не определяет источник.** Хранилище блобов может держать одну копию байтов, общих для двух источников. Доказательства, допуск, закрепления и одобрения принадлежат одному источнику: артефакт источника B с байтами, равными принятому артефакту источника A, допускается для B только по собственному доказательству B.
4. **Пункт 3 ADR-023 разблокирован.** Его условие «после R-003» выполнено (R-003 PASS 22.10.2026, верификатор ADR-030). Остальные условия исключения Attested не меняются: проверка промышленным верификатором, привязка к точному SHA-256 пакета, явное согласие пользователя для этого источника и действующая политика подписей ОС, которая это допускает. Реализуется в P3-004c.

## Альтернативы и причины отказа

- **Хранить только запись о проверке:** меньше места, но «мы когда-то проверили» никто не может проверить снова, а после передачи проверять нечем.
- **Скачивать bundle заново при каждой синхронизации:** после передачи площадка их не отдаёт, а запросов становится больше без прибавки доверия.
- **Запрашивать прежнего владельца по сохранённому логину:** логин можно переименовать или занять другим аккаунтом; определение по owner ID исключает привязку по имени, как и для репозиториев.
- **Ничего не искать и удерживать все релизы до передачи:** честно, но отбрасывает релизы, доказательства которых всё ещё доступны у прежнего владельца и полностью проходят проверку.

## Последствия

- В `specifications/github.md` добавляется порядок поиска из пункта 2; `architecture/trust.md` и `architecture/data-model.md` описывают хранимые bundle и доказательства по источнику.
- P2-004b реализует пункты 1–3 (хранимые bundle, ссылки для сборщика, порядок поиска, допуск по источнику); P3-004c реализует исключение Attested для RPM.
- В худшем случае хранилище растёт не больше чем на 4 МиБ на принятый digest (16 bundle по 256 КиБ); в R-003 у digest было один-два bundle по несколько килобайт.

## Проверка

Тесты пишутся от сбоя и проверяют обещание пользователю (AGENTS.md):

- после того как площадка перестала отдавать аттестацию (HTTP 404 везде), принятый артефакт по-прежнему проверяется заново офлайн по сохранённому bundle;
- сохранённый bundle, изменённый на один байт, усечённый или пропавший, не проходит повторную проверку, и об этом сообщается; он никогда не проходит;
- сборщик никогда не удаляет bundle, на который ссылается доказательство, в том числе при нехватке места;
- после передачи релиз, выпущенный до неё и ещё не принятый, проверяется по эндпоинту ранее подтверждённого владельца; bundle оттуда, где указан другой repository ID или никогда не подтверждённый owner ID, отвергается;
- ранее подтверждённый владелец, переименовавший аккаунт, всё равно находится по своему ID; никогда не подтверждённый владелец не запрашивается;
- если нигде ничего не найдено, результат — `E_EVIDENCE_DOWNGRADE`, никогда не `E_ATTESTATION_INVALID`, и ничего не допускается;
- форк или репозиторий, занявший старое имя, с байтами, равными принятому артефакту оригинала, не допускается по доказательству оригинала (R-003 F1, C1).
