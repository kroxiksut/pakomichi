# ADR-036 — Настройки источника, которые подтверждает администратор: подписант Attested, порт loopback, утверждение семейства

[English](../../en/decisions/ADR-036.md) · **Русский**

**Статус:** принят владельцем проекта 24.10.2026. Уточняет пункт 5 ADR-030 (откуда берутся настроенные workflow и ref), пункт 6 ADR-024 (порт до проведения N-034) и допуск семейства из `architecture/families-compatibility.md` (какая команда подтверждает семейство). Ничего не заменяет. Порт по умолчанию из пункта 2 выбран владельцем 24.10.2026 после N-034: 879 (`architecture/delivery-recovery.md`).  
**Дата:** 24.10.2026.

## Контекст

Конвейер синхронизации P4-001a упёрся в три вопроса:

- Пункт 5 ADR-030 требует, чтобы workflow подписанта и его ref в provenance уровня Attested совпадали с «настроенными» workflow и ref, но ни один документ не говорит, где они настраиваются для источника.
- Пункт 6 ADR-024 откладывает выбор порта loopback до теста привилегированного порта N-034, а конфигурации APT (P4-003a) и сокет-юниту reader порт нужен уже сейчас.
- `architecture/families-compatibility.md` говорит, что администратор подтверждает имена семейства на ревизии, но команды для этого нет.

## Решение

1. **Подписант Attested — часть источника; его подтверждают при добавлении источника.**
   - У источника не больше одного подписанта Attested: путь workflow внутри репозитория источника (`.github/workflows/<файл>.yml|yaml`) и правило ref. Правило — либо «тег релиза» (ref в provenance равен `refs/tags/<тег проверяемого релиза>`), либо одна ветка (`refs/heads/<имя>`).
   - `pchi source add` ищет подписанта сам. Он берёт последний релиз, запрашивает у GitHub аттестации каждого asset по закреплённому ID репозитория (ADR-034) и проверяет каждый SLSA provenance всеми проверками пунктов 4–6 ADR-030, кроме двух: workflow и ref читаются из проверенного сертификата, а не сравниваются. Подписант по-прежнему должен быть workflow самого репозитория источника, собранным на раннере GitHub, из коммита, на который указывает тег релиза.
   - План показывает найденного подписанта или говорит, что подписант не найден, и почему. `yes` администратора подтверждает его вместе с источником; до этого ничего не сохраняется.
   - `--workflow <путь>` и `--ref tag|refs/heads/<имя>` задают подписанта явно. Если они заданы, а поиск нашёл другого подписанта, план отклоняется и показывает обоих. Явные значения позволяют добавить источник до его первого аттестованного релиза.
   - Если в последнем релизе два разных подписанта, план отклоняется и просит `--workflow` и `--ref`. Поиск никогда не выбирает одного из них.
   - Без подписанта источник добавляется и работает на уровнях Strict и Pinned. Релиз, у которого есть только доказательства Attested, удерживается с `E_EVIDENCE_DOWNGRADE`, а статус называет отсутствующего подписанта.
   - Подписант меняется только отдельной интерактивной административной командой, которая показывает старого и нового подписанта. Её имя владелец утверждает при реализации. Provenance от другого workflow или ref — это `workflow_mismatch` или `ref_mismatch` (пункт 7 ADR-030), а не повод сменить подписанта автоматически.
2. **Порт loopback — настройка, пока N-034 не выберет значение по умолчанию.**
   - Порт — аргумент запуска владельца состояния (`--loopback-port`, по умолчанию 18080) и `ListenStream=` сокет-юнита reader. P5-004a поставляет оба с одинаковым значением, а администратор меняет оба вместе через drop-in.
   - Владелец состояния формирует источники APT со своим портом, поэтому порт попадает в APT только через root-applier (ADR-035, P4-003a). `pchi doctor` сообщает, если сокет слушает другой порт.
   - N-034 проводится до альфы на стенде: привилегированный порт (ниже 1024) занят сокет-юнитом systemd, сокет остановлен, затем в состоянии `failed`, непривилегированный пользователь пытается занять тот же адрес. Результат выбирает значение по умолчанию, которое записывается в журнал доказательств и в `architecture/delivery-recovery.md`; привилегированное значение по умолчанию это решение не меняет.
3. **`pchi source activate` подтверждает семейство.**
   - План `pchi source activate <id> --packages a,b` показывает ревизию семейства на сервере, каждое имя и архитектуру, замеченные в источнике на этой ревизии, и имена, которые будут активированы.
   - `yes` утверждает следующую ревизию семейства: ранее утверждённые имена плюс перечисленные, с показанными архитектурами. Он же активирует перечисленные имена. Digest плана покрывает ревизию, поэтому подтверждение более старой ревизии отклоняется (`families-compatibility.md`).
   - Имя, которого источник никогда не предлагал, отклоняется при планировании. У источника, который ещё не синхронизировался, семейства нет; его активация отклоняется с предложением сначала выполнить `pchi sync <id>`.
   - Замеченное, но не перечисленное имя остаётся вне семейства и удерживается с `E_FAMILY_UNAPPROVED`. Новое имя в следующем релизе удерживается так же, пока его не активируют той же командой.
   - Отдельной команды `approve-family` нет.

## Альтернативы и причины отказа

- **Обязательный `--workflow` для каждого источника:** администратор копирует путь из репозитория и ошибается при наборе. Источник без `--workflow` работал бы только на Strict и Pinned, даже если его релизы аттестованы. Подходит для forge или инстансов, где поиск не может проверить найденное.
- **Брать подписанта из первого provenance при каждой синхронизации:** скомпрометированный workflow того же репозитория стал бы подписантом, опубликовав релиз первым. Подписанта фиксирует и меняет только администратор.
- **Выбрать порт сейчас:** пункт 6 ADR-024 ставит выбор в зависимость от N-034. Настройка со значением по умолчанию держит стенды и пакеты согласованными до тех пор.
- **Отдельная команда `approve-family`:** ещё одно подтверждение того же решения. Активация уже показывает имена и требует администратора. Подходит, если семейство когда-нибудь понадобится утвердить, ничего не активируя, например для источника, который только наблюдается.

## Последствия

- Миграция 0004 хранит подписанта источника. План `source add` получает изменение вида `set_signer`, а `SourceAdd` — необязательные аргументы `workflow` и `ref`. Протокол ещё не выпущен, поэтому `schema_version` остаётся 1.
- Владельцу состояния нужны доверенные корни и проверяющий для планирования `source add`, как и для синхронизации.
- `specifications/cli-api.md`, `architecture/families-compatibility.md`, `architecture/trust.md` и `architecture/delivery-recovery.md` описывают правила на обоих языках.
- План активации называет ревизию семейства, а запуск отклоняется, если ревизия сдвинулась.

## Проверка

- Тесты в P4-001a: поиск возвращает подписанта только из проверенного provenance; provenance другого репозитория, self-hosted раннера или другого коммита подписантом не становится; два разных подписанта отклоняют план; явные значения, расходящиеся с поиском, отклоняют план; релиз только с доказательствами Attested и без подписанта удерживается с `E_EVIDENCE_DOWNGRADE`; активация имени, которого источник никогда не предлагал, отклоняется; подтверждение более старой ревизии семейства отклоняется; новое имя после активации удерживается с `E_FAMILY_UNAPPROVED`.
- N-034 на стенде с настоящими юнитами, с записью в журнал доказательств.
