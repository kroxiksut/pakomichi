# ADR-032 — Модель источника: любой вид источника, честные уровни доказательств, настраиваемая политика

[English](../../en/decisions/ADR-032.md) · **Русский**

**Статус:** предложен, черновик. Владелец проекта в принципе согласился с подходом 22.10.2026 и рассчитывает не раз его править. Ничего из этого не реализовано, и ничто не меняет рамки 0.1 (ADR-014: только GitHub Releases).

Если ADR будет принят, он изменит:

- ADR-027, пункт 4 (заранее заданное согласие, пункт 7 ниже);
- правило AGENTS.md «никогда не заменять явное подтверждение рискованного перехода автоматическим «да»» — только для переходов из пункта 7.

**Дата:** 22.10.2026.

## Контекст

Фаза A обзора R-008 ([отчёт](../research/R-008-report.md), [матрица](../../../research/r-008/sources-matrix.tsv)) показала, что предполагает текущее устройство. Оно предполагает, что источник — это репозиторий GitHub с числовыми ID репозитория и владельца, ID выпусков и файлов, digest SHA-256 из API, одним хостом API и правилами лимитов и постраничной выдачи GitHub.

Места, где публикуют разработчики, отличаются по каждому из этих пунктов:

- другие площадки;
- репозитории APT/DNF производителей и организаций;
- PPA, COPR и OBS;
- каталоги вроде WinGet, Scoop, Chocolatey и Homebrew.

Strict есть только у GitHub, а Attested за пределами GitHub — только у gitlab.com.

Отчёт фазы A рекомендовал не включать хостинги репозиториев APT/DNF и каталоги-указатели в модель источника. Владелец проекта отклонил это 22.10.2026.

- **Источники не ограничиваются.** Репозитории производителей (Zabbix, ClickHouse, PostgreSQL), собственные репозитории организации и каталоги вроде WinGet — тоже источники.
- **Поведение задаёт пользователь.** Проект поставляет наиболее компромиссные умолчания.
- **Уже подключённые в системе репозитории** по умолчанию не трогаются.
- Уровень подписи ключом репозитория и поведение на сертифицированных редакциях — настройки, а не жёсткие правила.

Польза Pakomichi для репозитория производителя — не в более сильной криптографии: его защищает тот же ключ, который уже проверяют APT/DNF. Польза в другом:

- контроль над тем, какие пакеты из него допускаются, с защитой системных пакетов (R-001, ADR-022);
- подтверждённая смена ключа вместо молчаливого импорта ключа;
- обнаружение отката и заморозки, которые метаданные производителя не предотвращают (`Valid-Until` нет в 17 из 17 файлов `InRelease`; DNF принимает более старый подписанный `repomd.xml`, R-004);
- снимки и откат, одинаковое состояние на всех машинах и записанное происхождение каждого установленного пакета.

## Решение (черновик)

1. **Виды источника.** Источником может быть любое из перечисленного. У каждого вида свой адаптер, идентичность, доказательства и сетевые правила. В 0.1 реализован только GitHub.

   | Группа | Виды |
   |---|---|
   | Выпуски площадок | GitHub, GitLab (gitlab.com и self-managed), Forgejo и Gitea, Bitbucket Cloud, SourceForge, GitFlic, GitVerse, загрузки Launchpad |
   | Нативные репозитории | Репозитории APT и DNF производителей и организаций, PPA, COPR, OBS, хостинги репозиториев |
   | Каталоги | Источники WinGet, buckets Scoop, Chocolatey, taps Homebrew |

2. **Идентичность.** Источник определяется как `(вид, происхождение экземпляра, устойчивая идентичность)`. Идентификаторы уникальны только в пределах экземпляра.
   - Площадки: ID репозитория или проекта и ID владельца, с подтверждениями владельцев из миграции 0002.
   - Нативные репозитории: шаблон URL и suites или `$releasever`, плюс разрешённые отпечатки ключей. Смена ключа подтверждается так же, как передача владельцу.
   - Каталоги: каталог плюс точный идентификатор пакета. Никогда не поиск по имени.

   Вид с идентичностью только по имени помечается как таковой и никогда не достигает Attested.
3. **Артефакты.** Артефакт — это `(источник, ключ выпуска или его отсутствие, ключ артефакта источника, алгоритм digest, digest)`. Алгоритм digest записывается (SHA-256, SHA-512, SHA3-384); MD5 — не более чем подсказка.
   - Закрепление никогда не перепривязывается.
   - Подменённый файл и файл, добавленный в закреплённый выпуск, — оба изменения (`E_ASSET_MUTATED`).
   - «Та же версия, новые байты, верная подпись подтверждённым ключом» (переподпись производителем после смены ключа, пересборка в COPR) удерживается до явного решения. Это поведение управляется настройкой из пункта 6.
4. **Уровни.** Порядок — `pinned < signed < attested < strict`, к нему применяется храповик из пункта 3 ADR-027.
   - `signed` — верная подпись закреплённым ключом: ключом издателя (OpenPGP над файлом или его контрольными суммами, Authenticode, встроенная подпись RPM по ADR-023) или ключом репозитория. Метка всегда говорит, каким именно.
   - Strict остаётся только у GitHub. Attested определяется издателем и шаблоном его claims (GitHub Actions; gitlab.com).
   - Заявления магазинов, упаковщиков и каталогов записываются как доказательства, но никогда не поднимают уровень: утверждения Snap, ключ репозитория Flathub, аттестации bottle Homebrew, хеши манифестов WinGet. Хеш каталога, расходящийся с digest площадки, — это находка (пункт 6).
   - **Одобрение каждого выпуска** — отдельный флаг, совместимый с любым уровнем. Для `pinned` он обязателен, как в ADR-027.
5. **Классы настроек.**
   1. **Неизменяемое, без настроек.**
      - Инварианты пункта 2 ADR-027.
      - Закрепление никогда не перепривязывается.
      - Скрипты сопровождающего и custom actions MSI никогда не выполняются при проверке.
      - API управления никогда не открывается на внешнем интерфейсе.
      - Уровень никогда не падает молча, и его метка всегда видна.
   2. **Ослабление.** Разрешено только явной настройкой администратора. Настройка видна в `pchi status` и `pchi doctor` и записывается в журнал решений; ослабление никогда не бывает умолчанием.
   3. **Ужесточение.** Разрешено свободно.

   Настройки накладываются слоями: глобальные умолчания, затем профиль, затем настройки источника (`source_policy`).
6. **Умолчания (черновик).**

   | Область | Умолчание | Настраивается |
   |---|---|---|
   | Пакеты, допускаемые из нативного репозитория | Только семейства, выбранные при подключении источника; системные пакеты никогда не вытесняются | Список разрешённых; весь репозиторий; вытеснение — только явным решением |
   | Смена ключа нативного репозитория | Удержание до подтверждения | Принимать автоматически, если новый ключ заверен старым |
   | Откат или устаревание метаданных | Откат удерживается; устаревание даёт предупреждение | Порог устаревания на источник; только предупреждать; удерживать |
   | Та же версия, новые байты, верный подтверждённый ключ | Удержание до решения | Принимать с записью в журнал |
   | Репозитории, уже подключённые в системе | Показываются, не трогаются | Предлагать перевод под Pakomichi; переводить автоматически |
   | Сертифицированные редакции (сертифицированная РЕД ОС, Astra с замкнутой программной средой) | Распознаются; предупреждение; отдельное согласие администратора | Запретить; заранее заданное согласие (пункт 7) |
   | Хеш каталога, расходящийся с digest площадки | Предупреждение | Удерживать |
   | Одобрение каждого выпуска | Только для `pinned` | Для любого уровня или источника |

7. **Заранее заданное согласие.** Переход, требующий интерактивного согласия, может вместо этого быть разрешён заранее, но только при выполнении всех условий:
   - согласие записано в файле конфигурации, принадлежащем root и недоступном на запись другим;
   - в нём названы точный источник и переход;
   - применение записывается в журнал решений, и `pchi status` его показывает.

   Переходы, которые можно разрешить заранее (черновик):
   - согласие на `pinned` для источника;
   - одобрение выпусков источника;
   - принятие смены ключа;
   - согласие на сертифицированной редакции.

   Заранее заданное согласие никогда не доступно через API статуса, HTTP-адрес на loopback или `--yes`.
8. **Сеть по видам источника.**
   - Список разрешённых хостов: хост API и объявленные хосты скачивания, с проверкой DNS на каждом переходе. Целостность обеспечивают только закреплённые digest или подпись, а не хост.
   - Проверяемый обходчик страниц, свой диалект заголовков лимитов, необязательные валидаторы — с отдельным путём для источников, которые валидаторов не отдают.
   - Учётные данные на каждый экземпляр источника.
   - Предел ответа 16 МиБ остаётся.

## Последствия

- **Схема.** Следующим миграциям понадобятся вид источника и происхождение экземпляра, допускающий NULL или составной ключ выпуска, непрозрачный ключ артефакта с алгоритмом digest, новые типы доказательств, идентичность нативных репозиториев и подтверждение смены ключа, а также настройки политики. До принятия ничего из этого не пишется.
- **Код.** Модуль `github` остаётся как есть. Абстракция источника появляется только тогда, когда реализуется второй вид.
  - `src/attest` знает только Strict и Attested (ADR-030, ADR-031). Уровню `signed` нужен свой путь проверки и, вероятно, свои подпричины; не предполагается, что он укладывается в `E_ATTESTATION_INVALID`.
  - Этот черновик не меняет правила Strict и Attested из ADR-030.
- **R-008.** Рекомендации отчёта «не вид источника» и «только перекрёстная проверка» отозваны. Открытые детали решают эксперименты фазы B.
- **Документы, которые меняются при принятии:**
  - `architecture/trust.md` и `architecture/policy-engine.md`;
  - `specifications/github.md`, который станет одним адаптером из нескольких;
  - ADR-027, пункт 4;
  - AGENTS.md.

## Открытые вопросы

- Формат и расположение конфигурации, имена и содержание профилей.
- Нужно ли сделать ключ издателя и ключ репозитория двумя уровнями вместо одного `signed` с меткой.
- Окончательный список переходов, которые можно разрешить заранее.
- Что означает распознавание «сертифицированной редакции» на каждом дистрибутиве и точная формулировка предупреждения.
