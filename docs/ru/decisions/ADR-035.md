# ADR-035 — Устройство процессов: изолированные подписчик и инспектор, канал ленивого скачивания для reader

[English](../../en/decisions/ADR-035.md) · **Русский**

**Статус:** принят владельцем проекта 23.10.2026. Уточняет пункт 7 ADR-017 и пункты 2 и 3 ADR-029, ничего не заменяет.  
**Дата:** 23.10.2026.

## Контекст

Пункт 7 ADR-017 делит Pakomichi на непривилегированного владельца состояния, одноразовый инспектор пакетов, reader репозиториев только для чтения, подписчика метаданных и root-applier. Пункт 3 ADR-029 делает инспектор и подписчика дочерними процессами владельца состояния, которые общаются через стандартный ввод и вывод. При планировании процессов (P2-013b) обнаружились три пробела:

- Дочерний процесс работает под пользователем родителя. Тогда подписчик работал бы под пользователем владельца состояния, и локальный ключ метаданных был бы доступен владельцу состояния. P2-013b требует обратного: закрытый ключ не может прочитать никто, кроме подписчика (`architecture/trust.md`, ADR-011).
- Инспектор разбирает недоверенные байты пакетов (ADR-009, ADR-028). Под пользователем владельца состояния взломанный инспектор получил бы базу состояния и CAS.
- Ленивому скачиванию из P3-005b нужно, чтобы reader только для чтения попросил недостающий пакет у владельца состояния, у которого запись в CAS и сеть. В пункте 2 ADR-029 такого канала нет.

## Решение

1. **Подписчик и инспектор — службы systemd по сокету с `Accept=yes`.** systemd запускает по экземпляру службы на каждое подключение и передаёт подключение экземпляру как стандартный ввод и вывод. Поэтому кадры и правила сообщений пунктов 3–5 ADR-029 не меняются, и каждый запрос по-прежнему получает новый процесс.
   - **Подписчик:** отдельный системный пользователь `pakomichi-signer`; ключ метаданных лежит в его каталоге состояния с режимом 0700, и ни один другой пользователь Pakomichi его не прочтёт. Один запрос подписи на экземпляр.
   - **Инспектор:** `DynamicUser=yes`, без сети (`PrivateNetwork=yes`, `RestrictAddressFamilies=AF_UNIX`), файловая система только для чтения, ограничения ресурсов пункта 4 ADR-017; пакет приходит на стандартный ввод. Одна проверка на экземпляр.
2. **Сокеты, добавленные к таблице пункта 2 ADR-029:**

   | Сокет | Режим и владелец | Допустимые клиенты | Допустимые запросы | Кто обслуживает |
   |---|---|---|---|---|
   | `/run/pakomichi/sign.sock` | 0600, пользователь владельца состояния | uid владельца состояния | один запрос подписи | экземпляр подписчика |
   | `/run/pakomichi/inspect.sock` | 0600, пользователь владельца состояния | uid владельца состояния | один запрос проверки | экземпляр инспектора |
   | `/run/pakomichi/fetch.sock` | 0600, пользователь reader | uid reader | запросы скачивания | владелец состояния |

   Каждый сервер проверяет `SO_PEERCRED` до первого кадра, как требует пункт 2 ADR-029. Экземпляр `Accept=yes` читает учётные данные клиента того подключения, которое ему передано.
3. **Канал ленивого скачивания несёт один тип запроса:** скачать объект с этим SHA-256 и размером. Ответ — «сохранено» или ошибка с HTTP-статусом, который отдаёт reader (502, 504, 507, 500, `architecture/delivery-recovery.md`). Байтов он не несёт: reader сам открывает и хеширует объект в CAS, прежде чем его отдать. Digest без пина владелец состояния отвергает.
4. **Доступ к сети остаётся у владельца состояния** (пункт 1 ADR-017). Отдельного сетевого процесса в 0.1 нет.

## Альтернативы и причины отказа

- **Обычные дочерние процессы владельца состояния (пункт 3 ADR-029 буквально):** проще, но ключ и разбор недоверенных байтов оказались бы под пользователем владельца состояния. Уместно, когда ключ и разбор уже ограничены другими средствами (отдельный контейнер, аппаратный токен).
- **setuid-помощник для подписчика:** второй привилегированный бинарник ради одной операции; смену пользователя systemd уже даёт.
- **Reader сам скачивает и пишет в CAS:** reader перестал бы быть только читающим, вопреки пункту 7 ADR-017.
- **Отдельный сетевой процесс уже сейчас:** ещё один канал и процесс без выигрыша в 0.1; уместно, когда владелец состояния должен работать без сети.

## Последствия

- P2-013b реализует три сокета, правила для клиентов, экземпляры `Accept=yes` и проверки привилегий при старте; P5-004a поставляет юниты с режимами и владельцами из пункта 2.
- `architecture/privileges.md` и `architecture/overview.md` описывают это устройство; вызовы подписчика и инспектора у владельца состояния идут через сокеты, а не через собственный запуск `gpg` и инспектора.
- Подпись и проверка, как и раньше, стоят одного запуска процесса на запрос.

## Проверка

- Тесты в P2-013b: клиент с другим uid отвергается на каждом новом сокете до первого кадра; файл ключа не читается пользователем владельца состояния; у экземпляра инспектора нет сети и он не может писать вне своего временного пространства; запрос скачивания digest без пина отвергается, и ничего не скачивается.
- Режимы, владельцы и песочница проверяются на ВМ с настоящими юнитами (P5-001, P5-004b).
