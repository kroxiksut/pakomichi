# ADR-033 — Локальный API для клиентов, отличных от CLI

[English](../../en/decisions/ADR-033.md) · **Русский**

**Статус:** принят владельцем проекта 23.10.2026 как направление. Пределы и таймауты в пунктах 3, 4 и 7 — начальные значения; их проверяют тесты P2-013c, а изменение записывается вместе с тестом. Уточняет ADR-029 (пункты 2, 5 и 8) и ничего не заменяет: при умолчаниях ниже поведение ADR-029 не меняется.  
**Дата:** 23.10.2026.

## Контекст

Графический интерфейс вне 0.1 (ADR-014, `product/scope-0.1.md`), и для его добавления нужно отдельное решение. Локальный API, которым он будет пользоваться, строится сейчас (ADR-029, P2-013): если этот API подходит только для CLI, то GUI позже означает изменение принятого протокола под уже существующими клиентами.

ADR-029 уже даёт то, что GUI нужнее всего: полномочия по каналу и никогда по запросу, раздельные каналы статуса и администрирования, план с digest перед любым административным изменением, операции, которые сразу возвращают идентификатор, и машиночитаемые коды причин (ADR-031). API никогда не устанавливает программы; это делает штатный менеджер пакетов (`specifications/cli-api.md`).

Чего не хватает клиенту, который не является CLI:

- **Расхождение версий.** Каждый тип протокола отвергает неизвестные поля (ADR-019, пункт 2). CLI ставится вместе с сервисом, поэтому его это не касается. GUI из отдельного пакета или написанный кем-то другим ломается на первом новом поле в ответе.
- **Права.** GUI работает от имени пользователя рабочего стола, а `admin.sock` принимает только uid 0.
- **Предпросмотр.** «Вставить ссылку и увидеть пакеты, совместимость и конфликты» не должно добавлять источник. Сейчас ближайшая команда, `source add --observe`, меняет состояние.
- **Уведомление об изменениях.** Окно должно узнавать об изменении состояния без опроса каждую секунду.
- **Дублирование политики.** Если клиент сам решает, какое действие возможно, или разбирает план из текста, политика реализуется дважды.
- **Другие языки.** Типы протокола существуют только в Rust.

## Решение

1. **Согласование версий.** Каждый канал принимает `hello` первым запросом: клиент перечисляет поддерживаемые версии протокола, сервер отвечает выбранной и списком имён возможностей (`preview`, `wait_changes`, …). Любое изменение формы запроса или ответа повышает `schema_version` протокола; строгость ADR-019 остаётся как есть. После выхода новой версии сервер ещё один выпуск обслуживает как минимум предыдущую. Клиент пропускает незнакомые имена возможностей: имя возможности — данные, а не поле. Запрос без `hello` обслуживается по версии 1, как определяет ADR-029. Собственный GUI Pakomichi, когда он появится, ставится вместе с сервисом той же версии и всё равно выполняет `hello`.
2. **Кто может подтвердить административное действие.** Это решает сервер в одном заменяемом шаге между планом и подтверждением и никогда — по полю запроса. Настройка — `admin_authorization`; в 0.1 реализовано только `root` (ADR-029, пункт 2, uid 0 на `admin.sock`), любое другое значение отвергается при запуске. Авторизация для пользователей рабочего стола (`pkexec` с маленьким помощником или polkit, проверяемый сервером) выбирается вместе с GUI и требует решения, заменяющего пункт 2 ADR-029. Само подтверждение не меняется: digest плана из пункта 8 ADR-029.
3. **Предпросмотр.** Запрос `preview` принимает один HTTPS URL поддерживаемой площадки (в 0.1 — GitHub) и возвращает то, что показал бы для него `source inspect`: релизы, пакеты и их семейства, достижимый уровень доказательств, совместимость и конфликты с установленными источниками и системным пространством имён. Он не пишет состояние: ни источника, ни закрепления, ничего в хранилище блобов. Он выполняется как операция (ADR-029, пункт 6). Сервер обращается только к API площадки и к URL asset, которые возвращает API, никогда — к URL из запроса, кроме адреса репозитория, и не принимает токен от клиента. Начальные пределы: один предпросмотр на uid одновременно, десять на uid в час, два всего; результат хранится в памяти 15 минут. Настройка `preview_for_users` (по умолчанию `true`) разрешает его на `status.sock`; при `false` он принимается только на `admin.sock`.
4. **Уведомление об изменениях.** Каждый ответ статуса содержит `state_epoch` (случайное значение на каждый запуск владельца состояния) и `state_revision` (монотонный в пределах эпохи). Запрос `wait_changes` с эпохой и ревизией возвращается, когда состояние новее, или не позже чем через 25 секунд с той же ревизией; при другой эпохе ответ приходит сразу, поэтому клиент видит перезапуск. Ожидающее соединение учитывается в пределе на uid из пункта 9 ADR-029. Подписки через удерживаемое соединение в 0.1 не входят.
5. **Сервер перечисляет возможные действия.** Ответ статуса перечисляет для каждого объекта действия, возможные сейчас: имя действия, объект, нужный канал и нужен ли план (например: подтвердить передачу репозитория для источника X, одобрить релиз Pinned, восстановить сокет). Клиенты показывают эти действия и не выводят их сами. План — структурированный список изменений (вид, цель, digest до и после, коды причин для рисков) в канонической форме, определённой один раз в модуле протокола; digest из пункта 8 ADR-029 вычисляется по этой форме. CLI печатает ту же структуру текстом.
6. **Опубликованная схема.** Протокол публикуется как JSON Schema рядом со спецификациями и сверяется с типами Rust тестом: каждый закреплённый пример проходит схему, а схема, как и типы, отвергает неизвестные поля. Как получать схему (крейт или схема, написанная вручную и сверяемая тестом), решает P2-013c.
7. **Упаковка и доступ.** У основных пакетов нет графических зависимостей; GUI — отдельный пакет, и серверу без рабочего стола он никогда не нужен. Настройка `status_access` (по умолчанию `all`, как в пункте 2 ADR-029; `root` ограничивает `status.sock` до uid 0) — для общих машин, где список источников не для каждого локального пользователя.
8. **Что остаётся вне.** Никакой установки, обновления, импорта ключей или изменения источников через API (`cli-api.md`); GUI передаёт управление центру приложений или показывает штатную команду. Интеграция с GNOME Software и KDE Discover идёт через метаданные AppStream в репозиториях Pakomichi, а не через этот API; это отдельное исследование для 0.2. Сервиса D-Bus в 0.1 нет (ADR-029, альтернативы).

## Альтернативы и причины отказа

- **Оставить API только для CLI и спроектировать заново под GUI:** дешевле всего сейчас, но позже меняет принятый протокол под существующими клиентами.
- **Ослабить строгость ADR-019 для ответов (клиенты пропускают неизвестные поля):** согласование проще, но старый клиент может молча пропустить поле, которое ослабляет защиту. Отклонено; вместо этого версии явные.
- **Системный сервис D-Bus с polkit сейчас (как PackageKit или fwupd):** обычный подход для рабочего стола, но вторая модель полномочий и большая зависимость раньше, чем появится GUI (ADR-029). Остаётся вариантом для пункта 2.
- **Предпросмотр через добавление источника в режиме наблюдения и его удаление:** оставляет следы (закрепления, блобы, историю) и требует прав администратора для вопроса, который ничего не меняет.

## Последствия

- P2-013c реализует `hello`, `preview`, `wait_changes`, список действий, структурированный план и схему, а также настройки `admin_authorization`, `preview_for_users` и `status_access`.
- `specifications/cli-api.md` и `architecture/privileges.md` описывают новые запросы, когда они будут реализованы; `preview` — сетевое действие, которое может запустить любой локальный пользователь, поэтому его пределы относятся к документу о привилегиях.
- GUI остаётся отдельной будущей задачей (`roadmap.md`) и требует своего решения, включая пункт 2.

## Проверка

Тесты пишутся от сбоя и проверяют обещание пользователю (AGENTS.md):

- клиент предыдущей версии продолжает работать после того, как сервер добавил поле в ответ, а клиент, предлагающий только неподдерживаемую версию, получает список поддерживаемых и ничего больше;
- поле ответа, добавленное без повышения версии, не проходит тест схемы;
- подтверждение от пира не-root отвергается при `admin_authorization = root`, а незнакомое значение настройки останавливает запуск;
- предпросмотр ничего не пишет: база состояния, хранилище блобов и список источников побайтно совпадают до и после, в том числе когда предпросмотр обрывается на середине;
- URL предпросмотра с userinfo, другим хостом, перенаправлением на другой хост или схемой не HTTPS отвергается до любого запроса; одиннадцатый предпросмотр uid за час и второй параллельный отвергаются; токен от клиента отвергается;
- `wait_changes` возвращается в свой срок с прежней ревизией, сразу после изменения и сразу при другой эпохе после перезапуска; клиент, ожидающий на всех своих соединениях, не может заблокировать `ping` других клиентов;
- действие, которого нет в статусе, отвергается, если клиент всё же его запросил;
- план, изменившийся между показом и подтверждением, отвергается, как в ADR-029.
