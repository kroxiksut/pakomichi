# Контракт APT

[English](../../en/specifications/apt.md) · **Русский**

## Выходы адаптера

- Для каждого активного логического источника — принадлежащий Pakomichi `.sources`/`.list` файл (по возможности современный deb822), уникальные поля `Origin`, `Label`, `Suite`, заданный `Signed-By` на *наш* keyring; не использовать глобальный `apt-key`/`trusted=yes`. У каждого уровня происхождения источника свой логический репозиторий с отдельными `Label`/`Origin`, чтобы `apt policy` показывал уровень (ADR-027).
- Подписанный `InRelease` (при необходимости `Release.gpg`), `Packages`/`Packages.gz`, корректные поля checksums/architectures и временная валидность `Valid-Until`, равная подтверждённой свежести.
- `Acquire-By-Hash: yes` обязателен, и каждый индекс выдаётся по своему пути `by-hash`. Изменяемы только `InRelease`, `Release`, `Release.gpg` и простые пути индексов для совместимости, и они выдаются только из текущего поколения (ADR-024).
- **Изначально низкий приоритет** Git-источника: в его `Release` стоят `NotAutomatic: yes` и `ButAutomaticUpgrades: yes`, поэтому APT даёт каждой его версии приоритет 100 (как у backports). Он никогда не вытесняет версию из другого источника, а пакет, установленный из него, по-прежнему получает обновления; защита не зависит от файла предпочтений. Для каждого активированного имени, включая каждого члена активированного семейства, — адресное предпочтение с `Pin-Priority: 990`, сопоставленное через `Pin: release o=…,l=…` логического репозитория источника (пункт 3 ADR-022) и сверяемое `apt-cache policy`. `Pin: origin` не используется, потому что все логические репозитории обслуживаются с одного loopback-хоста; приоритет 1000 и выше никогда не записывается, потому что он разрешает понижение версии.

### Публикатор индексов

Публикатор (`src/publish/apt.rs`, `apt_store.rs`, `sign.rs`, P3-001) строит одно поколение одного логического репозитория за раз.

- **Раскладка:** `dists/<label>/InRelease`, `dists/<label>/main/binary-<arch>/Packages` с псевдонимом `by-hash/SHA256/<digest>` и `pool/<sha256>/<package>_<version>_<arch>.deb`. Метка — `Label` логического репозитория (`pakomichi-<source>-<level>`); `Suite` и `Codename` равны ей, `Origin` — `Pakomichi`, единственный компонент — `main`, а `NotAutomatic: yes` с `ButAutomaticUpgrades: yes` дают репозиторию приоритет 100. Пакеты для `all` перечислены в индексе каждой обслуживаемой архитектуры. Имя в pool строится из полей control без эпохи и никогда не берётся из имени файла asset; уникальность даёт каталог digest.
- **Точные bytes:** каждая строфа — собственный абзац control пакета, поле за полем, за ним `Filename`, `Size` и `SHA256` сохранённого объекта. Абзац control, в котором уже есть `Filename`, `Size`, `MD5sum`, `SHA1`, `SHA256` или `SHA512`, отвергается (`E_ARTIFACT_MALFORMED`): иначе пакет мог бы направить APT к другому файлу. Два разных файла с одним пакетом, версией (сравнение как в dpkg, поэтому `1.0` равна `1.0-0` и `0:1.0`) и архитектурой — `E_SOURCE_AMBIGUOUS`; одни и те же bytes, предложенные дважды, — одна запись.
- **Release:** `Date` — время подписи, `Valid-Until` — последняя подтверждённая синхронизация плюс максимальная свежесть, а не время подписи плюс максимальная свежесть. Когда этот момент прошёл, ничего не подписывается (`E_SOURCE_STALE`); последнее подтверждение из будущего тоже отвергается. `Acquire-By-Hash: yes` и список `SHA256` всех индексов; даты в виде `Fri, 23 Oct 2026 10:00:00 UTC`.
- **Только `InRelease`:** неподписанный `Release` и `Release.gpg` не публикуются, поэтому у APT нет неподписанного или отделённого пути для отката. `Packages` публикуется без сжатия; APT забирает ровно те варианты, которые перечислены в `Release`.
- **Подпись:** подписчик метаданных запускает `gpg --clearsign` с SHA-512 в своём дочернем процессе со своим домашним каталогом; публикатор никогда не читает ключ (ADR-011, пункт 5 ADR-017). Проверка запускает `gpgv` с keyring, который настроен в APT (`Signed-By`): ровно одна верная подпись, ожидаемым первичным ключом, с SHA-256, SHA-384 или SHA-512 (APT в Debian 13 проверяет через `sqv`, который отвергает SHA-1), и ничего вне clear-signed сообщения. Текст под подписью должен байт в байт совпадать с построенным `Release`.
- **Проверка до публикации:** отдельный читатель заново читает подписанный текст и все индексы: `Origin`, `Label`, `Suite`, `Codename`, `Components`, `Architectures`, `NotAutomatic`, `ButAutomaticUpgrades`, `Acquire-By-Hash`, даты против подтверждённой свежести, каждый перечисленный индекс выдаётся с его digest и размером и каждый выдаваемый индекс перечислен, каждая строфа называет выдаваемый файл pool с его digest и размером, каждый файл pool перечислен. Все логические репозитории подписаны одним локальным ключом, поэтому APT принял бы `InRelease` другого уровня того же источника; эта проверка — нет.
- **Порядок:** индексы в CAS, подпись, проверка, `InRelease` в CAS, затем хранилище поколений пишет манифест и заменяет `current` (`delivery-recovery.md`). Любой сбой до этого оставляет `current` прежним, и клиенты держат предыдущее поколение до его `Valid-Until` (R-004 G9).

### Адаптер

Адаптер (`src/apt/`, P3-002) пишет и читает обратно конфигурацию источников; привилегированный applier, который запускает его от root, — P4-003.

- **Файлы:** локальный keyring `/etc/apt/keyrings/pakomichi.gpg`; для каждого источника `/etc/apt/sources.list.d/pakomichi-<source>.sources` (deb822, строфа на логический репозиторий: `URIs: http://127.0.0.1:<port>/<label>`, `Suites: <label>`, `Components: main`, `Signed-By` — локальный keyring) и `/etc/apt/preferences.d/pakomichi-<source>.pref`: для каждого логического репозитория с активированными именами одна строфа `Package: <имена>`, `Pin: release o=Pakomichi,l=<label>`, `Pin-Priority: 990`. У источника без активированных имён файла предпочтений нет. Имена пакетов следуют Debian Policy, метки — `[a-z0-9-]`, поэтому ни одно значение не может добавить поле (`*` и перевод строки отвергаются). Одно имя, активированное в двух логических репозиториях или в двух источниках, отвергается: при двух пинах 990 решает более высокая версия.
- **Когда пишется пин:** только для семейства, каждого члена которого APT уже видит в репозитории семейства и ни одну версию которого другой источник не предлагает в равной версии (сравнение как в dpkg). Иначе семейство удерживается целиком: `E_SOURCE_AMBIGUOUS` при равной версии (APT 2.6 сливает её, 2.8+ показывает дважды) или ожидание до следующего `apt update`, который прочтёт репозиторий. Поэтому активация идёт в два шага: источник (сам по себе безопасен с приоритетом 100), `apt update`, затем пины.
- **Изменения:** только пути выше и только когда в них те bytes, которые Pakomichi записал последними (их хранит вызывающий). Файл, который кто-то изменил, удалил или создал под нашим именем, или symlink на его месте — это расхождение: о нём сообщается, он не перезаписывается и не удаляется, и пока есть расхождение, ничего не применяется. Файл, в котором уже нужные bytes, принимается как есть — так завершается применение, прерванное после rename. Запись идёт в порядке keyring, предпочтения, источники; удаление — источники, предпочтения, keyring, поэтому источник никогда не существует без пинов своих активированных имён. Каждая запись готовится в каталоге цели как `.<name>.pakomichi-new~` (такое имя APT молча пропускает), синхронизируется, переименовывается на место, после чего синхронизируется каталог; цель, изменившаяся между планом и применением, не трогается.
- **Чтение обратно:** `apt-cache policy <names>` с `LC_ALL=C`. Небезопасно и показывается: активированное имя, у которого кандидат — не версия его репозитория с 990 (потерянный пин, чужое предпочтение, пропавший источник); равная версия в другом источнике; опубликованное, но не активированное имя, которое заменило бы версию другого источника. Более высокая версия активированного имени в другом источнике, включая обновление безопасности дистрибутива, — уведомление с этим источником и версией; издатель остаётся (пункт 3 ADR-022).

## Ограничения

- `apt_preferences` выбирает **версию**, а не экземпляр одинаковой версии из нескольких URL. APT 2.6 сливает равные версии, и решает порядок источников; APT 2.8+ привязывает экземпляр только при новой установке. Равная версия с разными байтами — `E_SOURCE_AMBIGUOUS` на любой версии APT, и никакой pin не заявляется как обеспечивающий origin safety (R-001, пункт 1 ADR-022).
- Активированное имя сохраняет издателя, когда другой источник, в том числе обновление безопасности дистрибутива, позже предлагает более высокую версию; Pakomichi показывает уведомление, а смена — явное решение пользователя (ADR-022).
- Артефакт, чей `Provides` или `Replaces` называет элемент системного пространства имён, удерживается при допуске (`E_SYSTEM_PACKAGE_CONFLICT`, пункт 2 ADR-022); сам APT принимает сторонний `Provides` библиотеки C (R-001 N-008/N-009).
- Не переименовывать и не модифицировать чужие пакеты; не менять файлы чужих APT-репозиториев и глобальную политику. Никогда не требовать `APT::Get::EnableUpgrade`.
- Двоичное совпадение SHA двух *доступных файлов* может свидетельствовать об эквивалентности содержимого; требуется реально доказанный SHA, не только имя/версия.
- Активация — после чтения инвентаризации `dpkg`, репозиториев и проверенной симуляции транзакции `apt-get -s`, с пониманием ограничений этой симуляции.
- При неисполнимом режиме preferred оставить `observing`/`held`. Не изменять исходную версию пакета ради pin.
- `apt-get update` завершается с кодом 0, когда источник недоступен; здоровье источника берётся из собственного состояния Pakomichi, никогда из этого кода выхода (пункт 6 ADR-022).
- `/var/lib/apt/lists` и `/var/cache/apt/archives` никогда не являются доверенным входом (пункт 7 ADR-025).

## Обычная команда обновления

`apt upgrade` и `apt full-upgrade` в Debian и Ubuntu; `apt-get dist-upgrade` в Astra Linux, которая отклоняет `apt upgrade` и `apt-get upgrade` (R-001). Защиту выше нужно показать для каждой перечисленной команды (пункт 4 ADR-022).

## Astra Linux

Поддерживаемый уровень в 0.1 — `base(orel)` на Astra Linux 1.8.6 (ADR-026). Уровень безопасности, замкнутая программная среда и контроль целостности определяются без root; пока замкнутая среда включена или её нельзя исключить, активация отклоняется, а каждый артефакт удерживается с кодом `E_EXECUTION_POLICY` (ADR-025). Applier работает на уровне целостности 63 (служба systemd или сеанс администратора); неудачное применение с более низкого уровня сообщается как проблема уровня целостности (`E_SECURITY_CONTEXT`).

## Испытания

Только на сборках, допущенных ADR-026; первые цели APT — Debian 12 и Astra Linux 1.8.6 на `base(orel)`. Два `.deb` с одной версией и разными sha, перестановка order и Pin-Priority, выбранное семейство (main/service), более высокая версия активированного имени из другого источника при каждой обычной команде обновления, сопоставление `Pin: release` на одном loopback-хосте, обновление системной зависимости, пропажа local server, Valid-Until, повтор более старого поколения.
