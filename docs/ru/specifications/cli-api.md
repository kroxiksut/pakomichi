# Предлагаемые CLI и read-only API

[English](../../en/specifications/cli-api.md) · **Русский**

**Имена команд утверждены владельцем:** основная короткая команда — `pchi`, полная команда — `pakomichi`. Обе точки входа предоставляют один и тот же CLI, набор аргументов, коды завершения и семантику вывода. Документация и интерактивные примеры по умолчанию используют `pchi`. Конфликтующее имя `gitbridge` не использовать.

```text
pchi source add <https-git-url> [--observe] [--workflow <path> --ref tag|refs/heads/<name>]
pchi source list
pchi source inspect <id>
pchi source activate <id> --packages <comma-list> [--policy supplemental|preferred]
pchi source suspend <id>
pchi source remove <id>  # не удаляет программы
pchi sync [<id>] [--force]
pchi source allow-pinned <id>  # согласие на Pinned для одного источника (ADR-027)
pchi release approve <source-id> <release-id>  # Pinned: подтвердить один релиз
pchi status [--json]
pchi doctor [--json] [--repair]
pchi cache status
```

Полная форма заменяет только имя точки входа: `pakomichi source list` эквивалентно `pchi source list`. Способ поставки двух точек входа (например, alias, symlink или отдельный launcher) выбирается при реализации пакета, но не должен создавать две расходящиеся реализации CLI.

`add` сам по себе не активирует пакет. Не применять `--yes` для подтверждения transfer repo owner, смены издателя, неоднозначности, согласия на Pinned или подтверждения релиза Pinned. Активирование требует прав администратора и выводит исходный и итоговый план файлов/источников.

**Подписант Attested** (ADR-036, пункт 1): `source add` ищет workflow, который подписывает provenance последнего релиза, и показывает его в плане; подтверждение сохраняет его вместе с источником. `--workflow` и `--ref` (`tag` — тег релиза, или `refs/heads/<имя>`) задают его явно и должны совпасть с найденным. Два разных подписанта отклоняют план. Источник без подписанта работает на уровнях Strict и Pinned.

**Семейство** (ADR-036, пункт 3): план `source activate` показывает ревизию семейства, каждое имя и архитектуру, которые предлагает источник, и имена для активации; подтверждение утверждает перечисленные имена в следующую ревизию. Имя, которого источник никогда не предлагал, отклоняется; источник, который ни разу не синхронизировался, отклоняется с предложением сначала выполнить `pchi sync <id>`.

**`pchi doctor`** (ADR-021, ADR-022, ADR-024, ADR-025) диагностирует, ничего не меняя: состояние юнитов сокета и службы (сокет в `failed` или `service-start-limit-hit` сообщается как отказ репозиториев Pakomichi вместе с командой восстановления), последнюю подтверждённую синхронизацию и возраст выдаваемого поколения по каждому источнику (`E_SOURCE_STALE`), обновления активированного имени, которые предлагает другой источник, уровень безопасности Astra Linux и имя каждого отказавшего репозитория Pakomichi. Код выхода `apt-get update` никогда не используется как признак здоровья. `--repair` выполняет только задокументированное восстановление сокета (`systemctl reset-failed` для юнитов, затем запуск сокета); оно требует прав администратора и явного интерактивного подтверждения, не принимает `--yes` и никогда не предлагается через status API или loopback HTTP.

**Что `pchi doctor` проверяет в этой сборке** (P4-001, 25.10.2026). Он работает без root и ничего не меняет; то, что служба не отвечает, — одна из находок, а не причина остановиться. Каждый юнит установки (семь сокетов и `pakomichi-state.service`): не установлен, сокет в `failed` (для сокета reader — репозитории Pakomichi недоступны, с восстановлением `systemctl reset-failed … && systemctl start …`), сокет не слушает, упавший владелец состояния. Порт сокета reader: 1024 и выше не защищён, а `net.ipv4.ip_unprivileged_port_start`, не превышающий порт или нечитаемый, — риск (N-034); порт, отличный от того, который называют источники APT (`loopback_port` в статусе), — проблема. Каждый источник статуса: ещё не синхронизирован (уведомление), последнее подтверждение старше максимальной свежести в 7 дней (`E_SOURCE_STALE`), обновления активированных имён из других источников (уведомления) и обещания, которые APT не выполняет (`apt_problems`). Политика исполнения ОС включена или не исключена (`E_EXECUTION_POLICY`). Каждая находка печатается как `PROBLEM`, `RISK` или `notice` с кодом и строкой `fix:`. Код выхода: `0`, если остались только уведомления, `1`, если найдена проблема или риск. В этой сборке ещё нет: возраста выдаваемого поколения, уровня безопасности Astra Linux сверх политики исполнения, непубличного диапазона хоста asset и имени каждого отказавшего репозитория.

**`pchi doctor --repair`** (P4-001, решение владельца от 25.10.2026) выполняется в самом процессе CLI, никогда через владельца состояния: служба работает от непривилегированного пользователя и не может вызывать systemctl, а восстановление нужнее всего, когда упала сама служба. В каналах статуса и администрирования для него нет запроса. Если эффективный пользователь не root, команда отклоняется с кодом выхода `1`, прежде чем что-либо прочитано или изменено. Затем она диагностирует так же, как `pchi doctor`, и планирует задокументированное восстановление каждого установленного юнита в `failed`: сокеты в фиксированном порядке, затем `pakomichi-state.service`, которому нужны его сокеты. Для сокета восстановление — `systemctl reset-failed <service> <socket>`, затем `systemctl start <socket>`, где `<service>` — то, что запускает сокет: `pakomichi-reader.service` для сокета reader, `pakomichi-state.service` для сокетов status, admin и fetch и экземпляры `pakomichi-<name>@*.service` для принимающих соединения сокетов sign, inspect и apply. Для владельца состояния — `systemctl reset-failed pakomichi-state.service`, затем `systemctl start pakomichi-state.service`. Строка `fix:` в `pchi doctor` называет те же команды. Сокет, который просто остановлен, и неустановленный юнит выводятся в диагностике, но не восстанавливаются: задокументированное восстановление относится к `failed` (ADR-021, пункт 3.1). Если ничего не упало, команда печатает `nothing to repair` и завершается с `0`. Иначе она печатает команды и выполняет их только после того, как администратор наберёт `yes` в терминале; без терминала или при любом другом ответе код выхода `3`, и ничего не изменено. Каждая команда выполняется как `/usr/bin/systemctl` с `LC_ALL=C`; на первой неудаче выполнение останавливается и неудача выводится, затем диагностика повторяется и печатается её результат. Код выхода: `0`, если после этого ни у одного восстановленного юнита нет проблемы, иначе `1`.

**Уровень Pinned** (ADR-027): `source allow-pinned` называет риск (скомпрометированные учётная запись, токен или CI издателя могут опубликовать вредоносный релиз, который Pakomichi обнаружить не может) и записывает согласие только для этого источника; `release approve` показывает релиз и точные digest его артефактов и подтверждает только эти digest. Обе команды административные, интерактивные и отклоняют `--yes`. Источник Pinned можно активировать только с `--policy supplemental`. Имена команд одобрены владельцем проекта 21.10.2026. `<release-id>` — ID релиза на площадке: синхронизация, у которой релиз ждёт одобрения (`E_RELEASE_APPROVAL_REQUIRED`), печатает точную строку `pchi release approve <source-id> <release-id>`. План одобрения перечисляет каждый ещё не одобренный артефакт релиза по имени файла и SHA-256; выполнение пересчитывает его и отказывает, если релиз изменился после плана, затем одобряет ровно эти digest и синхронизирует источник, так что релиз публикуется на уровне Pinned и пинится как любой другой.

**Статус API (только чтение):** список источников, идентичность, режим, уровень происхождения и нижняя граница доверия, last_successful_sync, trusted snapshot age, список установленных/допустимых версий, причины held (включая `E_EVIDENCE_DOWNGRADE` и `E_RELEASE_APPROVAL_REQUIRED`), обновления активированных имён, которые предлагает другой источник, build variant/confidence, app/package statuses. JSON-ответ содержит `schema_version`, machine-readable `state`, `reason_code`. Status API никогда не принимает согласие, подтверждение или восстановление.

**Что выберет APT** (ADR-022, пункт 3; N-027): у каждого источника в статусе есть `updates_elsewhere` — более новая версия одного из его активированных имён, которую предлагает другой источник, включая обновление безопасности дистрибутива (`name`, `version`, `offered_by` — источник так, как его называет APT: URI и suite); издатель остаётся прежним, пока пользователь сам его не сменит, — и `apt_problems` — обещание, которое APT сейчас не выполняет: активированное имя, которое APT взял бы из другого места или ещё не видит (`E_ADMIN_APPLY_FAILED`), версия, которую предлагает и другой источник (`E_SOURCE_AMBIGUOUS`), опубликованное, но не активированное имя, которое заменило бы копию, установленную из другого источника (`E_ADMIN_APPLY_FAILED`). Если APT спросить не удалось, у каждого источника одна проблема без имени и кода, которая об этом говорит: неизвестное никогда не выдаётся за выполненное. Владелец состояния читает `apt-cache policy` для имён, за которые отвечает, при запуске и после каждой операции, поэтому запрос статуса никогда не запускает процесс; после `apt update` картина снова актуальна со следующей операцией (например, `pchi sync`). `pchi status` печатает строку `notice:` для каждого обновления в другом источнике и строку `PROBLEM` для каждой проблемы.

API не должен предоставлять команды `install`, `upgrade`, `change source`, `add repo`, `import key`. Приложения могут показать пользователю доступное обновление, но установку выполняет нативный пакетный менеджер.

**Ошибки:** подробности см. `errors.md`. Вывод без секретов/токенов. Не вводить фальшивое сообщение «пакет защищён», если проверено лишь совпадение SHA.

## Реализация (P4-001a)

Обе точки входа обслуживает одна реализация: `src/cli`, которую вызывают бинарники `pchi` и `pakomichi`. Команды только для чтения (`status`, `source list`, `source inspect`) идут через `status.sock`; административные (`source add`, `source activate`, `sync`) — через `admin.sock` и поэтому требуют root. `doctor --repair` тоже требует root, но сам вызывает `systemctl`, а не обращается к службе (см. выше).

- **Подтверждение:** CLI запрашивает у сервера план, печатает его сводку и каждое изменение (вид, цель, digest до и после и коды причин рисков) и применяет его только после того, как администратор наберёт `yes` в терминале. Без терминала ничего не меняется. Ни одна команда не принимает `--yes` или другой способ подтвердить из аргументов; digest плана связывает действие и его аргументы (ADR-029, пункт 8; ADR-033, пункт 5).
- **Код выхода:** `0` — выполнено; `1` — отказ (сервера или `doctor --repair` без root) или операция не удалась; `2` — ошибка в аргументах; `3` — не подтверждено или нет терминала для подтверждения (ничего не изменено); `4` — служба не ответила.
- **Умолчания:** `source activate` без `--policy` запрашивает `supplemental`, никогда `preferred`.
- `PAKOMICHI_RUNTIME_DIR` направляет CLI в другой каталог сокетов для тестового стенда; пакеты его не задают.
- **Поиск подписанта:** `source add` запрашивает у GitHub последний релиз, коммит его тега и аттестации не более чем 20 загруженных asset с digest от API, каждый раз по закреплённому ID репозитория. Asset без digest пропускается: его аттестации нельзя найти, не скачав его. Владелец состояния проверяет их доверенными корнями, обновлёнными через TUF при старте (`pakomichi-state --tuf-cache DIR`); без них план говорит, что ничего не проверено, и источник остаётся без подписанта, если его не назвали явно.
- **Синхронизация** (`sync` и каждая активация): идентичность по ID репозитория; каждый релиз из списка, от старых к новым, чтобы уровень доверия рос так же, как росли релизы; asset для цели скачиваются в CAS и проверяются изолированным инспектором; доказательства Strict или Attested для точных байтов, которые для уже проверенных байтов переиспользуются до ежедневной полной проверки (`--force` спрашивает площадку о каждом релизе сразу, ADR-037, пункт 1); семейство (предлагается при первой синхронизации, имя вне его записывается как замеченное и удерживается с `E_FAMILY_UNAPPROVED`); пространство имён системы, совместимость и ядро решений, каждое решение — в журнал; подписанное поколение на каждый уровень для активированных имён; затем конфигурация APT всех источников через root-applier, причём пин пишется только там, где APT уже видит семейство и ни один другой источник не предлагает равную версию (`apt.md`; удержанное семейство названо в итоге операции — с `E_SOURCE_AMBIGUOUS` или «run apt update, then pchi sync»). Журнал активаций следует только за проверенным применением, и состояние источника тоже: `active`, пока проверенная конфигурация пинит хотя бы одно его имя, и снова `registered`, когда таких не осталось; наблюдаемый или приостановленный источник своё состояние сохраняет. Ошибка при обращении к GitHub, инспектору или публикатору останавливает проход этого источника, и операция завершается неудачей; опубликованное раньше остаётся, остальные источники всё равно обрабатываются.
- `source activate` и `sync` требуют, чтобы `pakomichi-state` был запущен с аргументами конвейера (`--publish-root`, `--sign-socket`, `--inspect-socket`, `--apply-socket`, `--keyring`, `--key-fingerprint` и `--loopback-port`); без них они отклоняются.
