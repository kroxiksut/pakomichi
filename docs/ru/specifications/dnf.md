# Контракт RPM/DNF4/DNF5

[English](../../en/specifications/dnf.md) · **Русский**

## Конфигурация репозитория

- Каждый Git-источник имеет уникальный repo ID; `baseurl` указывает на наш loopback HTTP. Метаданные `repomd.xml` и связанные файлы образуют согласованный Snapshot. ID репозиториев и значения `name` указывают на Pakomichi, источник и уровень происхождения, чтобы `dnf repolist` и собственные сообщения DNF об ошибках указывали на репозиторий Pakomichi (ADR-021, ADR-027).
- Каждая секция репозитория Pakomichi явно задаёт `skip_if_unavailable=False` в DNF4 и DNF5 независимо от значения по умолчанию в дистрибутиве (ADR-021). Пока репозиторий Pakomichi недоступен, операции DNF, которые загружают метаданные всех включённых репозиториев, завершаются ошибкой; это задокументированное ограничение. Pakomichi никогда не переключает свои репозитории на `True`, никогда не отключает их и никогда не правит файлы сторонних репозиториев ради восстановления доступности. `pchi doctor` сообщает об отказе и команду восстановления.
- `includepkgs` ограничивает видимость разрешённых имён только в нашем repo, но не заменяет **фильтрацию до публикации**: пользователь может менять локальные настройки или опции DNF.
- `priority` проверяется на конкретной сборке DNF; меньшее число = более предпочтительный источник. Для активированных имён у нашего репозитория приоритет лучше, чем у репозиториев дистрибутива, а `includepkgs` перечисляет только эти имена (пункт 3 ADR-022). `allow_vendor_change` читается и показывается, но никогда не записывается (он глобальный) и на него не полагаются (в DNF 4.2 его нет). `excludepkgs` никогда не записывается в другие репозитории. Не считать policy из нашей БД достаточной.
- Файлы `repodata` имеют уникальные имена с digest (никогда `--simple-md-filenames`); изменяемы только `repomd.xml` и `repomd.xml.asc`, и они выдаются только из текущего поколения (ADR-024).

## Подписи (ADR-023)

- Два независимых шлюза, каждый отказывает закрыто со своей диагностикой: `repo_gpgcheck=1` с подписанным `repomd.xml` (локальный ключ) и доверие к пакету.
- DNF4 и DNF5 — отдельные адаптеры. DNF4 пишет `gpgcheck` и `repo_gpgcheck` для репозитория и считает `%_pkgverify_level` вышестоящей политикой (в DNF 4.14 нет ни `pkg_gpgcheck`, ни `gpgcheck_policy`); DNF5 явно пишет `pkg_gpgcheck` и `repo_gpgcheck` и записывает `gpgcheck_policy`. Адаптер никогда не выдаёт настройку, которую его DNF не поддерживает. После записи applier перечитывает эффективные значения; расхождение — `E_ADMIN_APPLY_FAILED`. RPM 6 — отдельный поддерживаемый стек.
- **Режим Native:** RPM, подписанный издателем, проверяется штатно по закреплённому для источника ключу издателя, проверка пакетов для его репозитория включена. Импорт этого ключа в системную связку ключей RPM требует явного согласия с его отпечатком и предупреждения, что RPM затем принимает его для пакетов из любого источника. Порядок удаления импортированного ключа фиксируется здесь до реализации режима Native.
- **Исключение Attested (ждёт R-003):** неподписанный RPM публикуется, только если его проверил промышленный верификатор аттестаций, исключение привязано к его точному SHA-256, есть явное согласие для источника, и только если эффективное `%_pkgverify_level` не равно ни `signature`, ни `all`. Он выдаётся из отдельного логического репозитория этого источника, содержащего только такие пакеты; проверка пакетов отключается только для этого репозитория Pakomichi. Иначе он удерживается с `E_SIGNATURE_POLICY`.
- Никогда не записывать глобальные `gpgcheck=0`, `pkg_gpgcheck=0`, изменение `localpkg_gpgcheck` или `%_pkgverify_level`; запрос на глобальное отключение отклоняется до вызова DNF.
- Метаданные репозитория строятся только из итоговых проверенных байтов RPM; подпись никогда не переписывает RPM.

## Свежесть и поколения (ADR-024)

- У `repomd.xml` нет подписанного срока действия, и DNF принимает повтор более старых подписанных метаданных, поэтому свежесть и запрет отката обеспечиваются на сервере: ID поколений монотонны, а `current` никогда не возвращается назад.
- Когда последняя подтверждённая синхронизация источника старше максимальной свежести (по умолчанию 7 дней), Pakomichi публикует новое подписанное **пустое поколение** репозитория этого источника вместо ответа 503 или выдачи устаревших данных. Установленные пакеты остаются установленными, DNF продолжает работать для остальной системы, пакеты источника не предлагаются до успешного `sync`, а `pchi doctor`/`pchi status` показывают `E_SOURCE_STALE`.
- RPM-поколения переключаются не чаще одного раза за интервал регулярной проверки (6 ч), кроме `sync --force` и пустого поколения, потому что `repomd.xml.asc` и `repomd.xml` — отдельные пути. Отказ подписи метаданных сразу после переключения повторяем, а не повреждение.

## Выбор и установленное состояние

- Равная версия с разными байтами — `E_SOURCE_AMBIGUOUS`; приоритет DNF её не заменяет (`distro-sync` и `reinstall` переходят на текущий предпочтительный экземпляр; в РЕД ОС 7.3 и 8 `reinstall` берёт экземпляр из репозитория с *худшим* приоритетом, R-001).
- Активированное имя сохраняет издателя, когда другой источник, в том числе обновление безопасности дистрибутива, позже предлагает более высокую версию; Pakomichi показывает уведомление (ADR-022).
- Установленный из COPR NetWatch не переключать автоматически на GitHub static RPM, даже при большей версии Git. `build_variant` может быть unknown, и это не доказательство эквивалентности.
- Определение источника установленного RPM должно опираться на реальные данные менеджера; при недостоверности статус unknown.
- Удаление Pakomichi и удаление источника стирают `.repo`-файлы Pakomichi для этого источника (ADR-021).

## Обычная команда обновления и сборки

`dnf upgrade`. Каждое правило проверяется на каждой поддерживаемой сборке дистрибутива, а не выводится из версии DNF: РЕД ОС отличается от upstream DNF 4.14/4.20 поведением `reinstall`, значениями по умолчанию и параметрами (пункт 5 ADR-022). Для AlmaLinux и Fedora поддержка заявляется только после прогонов с SELinux в режиме enforcing (ADR-026).

`R-001`: конфликты и приоритеты. `R-002`: проверки подписи. `R-004`: доставка и поколения. Тесты DNF4/DNF5 проводить изолированно; не устанавливать неподписанные пакеты на production ради теста.
