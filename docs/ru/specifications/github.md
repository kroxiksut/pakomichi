# Контракт адаптера GitHub Releases

[English](../../en/specifications/github.md) · **Русский**

1. При `source add` получать repo canonical URL, numerical repository ID, owner ID из API. При каждой синхронизации сверять их. Git rename с неизменными ID допускается; owner transfer -> приостановить.
   - Первое разрешение `owner/name` закрепляет repository ID и owner ID. Canonical URL строится из проверенных owner и name, а не копируется из `html_url`.
   - Синхронизация сверяет через `GET /repositories/{id}`, никогда не через имя. Исходы: без изменений; **переименование** (тот же repository ID и owner ID, новый login владельца или имя репозитория) → допускается, предыдущий адрес записывается; **owner transfer** (тот же repository ID, новый owner ID) → приостановить с `E_OWNER_TRANSFER`; **подмена** (другой repository ID, например новый репозиторий под старым именем) → отклонить с `E_REPO_ID_CHANGED`, никогда не следовать.
   - Поиск по имени следует только перенаправлению GitHub на `https://api.github.com/repositories/{id}`; любое другое перенаправление отклоняется.
   - `gh attestation verify` связывает аттестации только по имени репозитория, без учёта регистра (R-003), поэтому эта проверка по ID всегда выполняется самим Pakomichi.
2. Запрашивать только Releases выбранного repo ID (`/repositories/{id}/releases`, `.../releases/latest`, `.../releases/tags/{tag}`). Никаких Search API для соседних repos, форков, альтернативных владельцев. Не использовать HTML scraping.
3. Release ID/tag/target_commitish — разные поля. Требуется верифицированная связь с коммитом и выпуском там, где режим доверия её заявляет; `target_commitish` не является достаточной криптографической проверкой SHA.
4. Сначала изучать список assets (name, size, digest, ID), отфильтровывать формат/архитектуру; по необходимости скачивать *только* кандидатов и инспектировать родные метаданные. API может не вернуть `digest` asset (R-005: 23% последних выпусков) или поле выпуска `immutable`; отсутствующее значение остаётся неизвестным и никогда не придумывается.
   - До любого скачивания (`src/inventory`, P2-002): имена `.deb`/`.rpm` экосистемы цели — кандидаты; исходные, delta- и отладочные пакеты, компоненты установщика, архивы (включая `.tar.gz` для Linux), контрольные суммы, подписи, SBOM и пакеты других систем пропускаются с записанной причиной; любое другое имя требует review и никогда не скачивается и не публикуется. Пустой файл, похожий на пакет, — `E_ARTIFACT_MALFORMED`; незавершённая загрузка или файл больше предела пропускаются.
   - Архитектура в имени (`amd64`, `x86_64`, `x64`, `linux_386` и `linux_armv6` у Go, `all`/`noarch`, ...) только позволяет пропустить файлы, явно названные для другого CPU; она никогда не допускает файл. Решают нативные метаданные из инспектора: допускается только нативная архитектура цели или универсальная, иначе `E_PLATFORM_UNSUPPORTED`. Чужие архитектуры (multiarch, multilib) в 0.1 не являются целями.
   - После скачивания байты, SHA-256 которых отличается от `digest` API, отклоняются (`E_ASSET_MUTATED`); без digest API единственным остаётся digest скачанных байтов из CAS. Два разных файла одного релиза с одинаковыми нативным именем и архитектурой удерживаются оба (`E_SOURCE_AMBIGUOUS`); одинаковые байты под двумя именами — остаётся первый. SRPM с именем как у бинарного RPM отклоняется.
5. Сверять digest полученного содержимого, не считать API `digest` независимой подписью. Проверить cryptographic attestation, predicate, verified source repo ID, workflow и exact digest.
6. Каналы stable/beta/alpha — явная политика и нативная версия; флаг `prerelease` изменяем и не единственный критерий.
   - Релиз относится к каналу stable, только если флаг равен `false` и ни тег, ни одна нативная версия не называют предрелиз (`~` или слово `alpha`, `beta`, `rc`, `pre`, `preview`, `dev`, `nightly`, `snapshot`, `canary`, `unstable` как целая последовательность букв). Флаг stable рядом с таким тегом или версией — неясный случай (`E_CHANNEL_UNCLEAR`), и на канале stable такой релиз не предлагается (пример: Win32-OpenSSH `10.4.0.0p1-Preview` с `prerelease: false`, R-007). Следить за предрелизами — явный выбор для источника. Черновики не предлагаются никогда.
7. Записывать ETag/Last-Modified, использовать условные запросы, backoff по `Retry-After` и лимитам; при ошибке не подменять достоверную дату успешной синхронизации.
   - Условные запросы используют только `ETag`; `If-Modified-Since` не отправляется. `If-None-Match` несёт ETag, сохранённый из более раннего **проверенного** ответа 200 для того же URL и той же идентичности учётных данных (односторонний отпечаток токена, никогда не сам токен). Ответ 304 подтверждает «без изменений» только как ответ на такой запрос и никогда не подтверждает байты asset; любой другой 304 — ошибка (вывод 14 R-004). Анонимные ответы 304 всё равно расходуют лимит запросов.
   - `x-ratelimit-remaining: 0` останавливает запросы до `x-ratelimit-reset`, даже после успешного ответа. Ответ 403 или 429 с `Retry-After` ждёт указанное время; с `x-ratelimit-remaining: 0` — до сброса; другой 429 или 403, в сообщении которого названо ограничение частоты, ждёт одну минуту с удвоением при каждом следующем подряд отказе. Любое ожидание ограничено 61 минутой. Клиент никогда не повторяет запросы сам; запросы во время ожидания отклоняются локально без обращения к сети.
   - Постраничная выборка следует `rel="next"` только к тому же origin и пути, с тем же `per_page` и ровно следующим номером страницы, до предела страниц (по умолчанию 10 страниц по 100). Список, достигший предела, помечается как усечённый. Ссылки GitHub для `/repositories/{id}/releases` имеют вид `https://api.github.com/repositories/{id}/releases?per_page={n}&page={m}` (проверено вживую 20.10.2026), и это правило их принимает.
8. HTTP redirect validation на каждом hop; не обращаться к приватным IP/metadata endpoints по параметрам недоверенного источника; ограничить размеры/число assets.
   - Клиент API обращается только к `https://api.github.com`. Он разрешает имя хоста один раз на запрос, отклоняет весь ответ DNS, если любой адрес относится к loopback, частным, link-local (включая metadata), shared, benchmarking, documentation, multicast или зарезервированным, и подключается к проверенному адресу (вывод 11 R-004).
   - Соединение использует TLS 1.2 или 1.3 с SNI `api.github.com` и всегда проверяет цепочку сертификатов и имя хоста по системному хранилищу корневых сертификатов; возможности отключить проверку нет. ALPN предлагает только `http/1.1`. Пустое или непригодное хранилище корней — ошибка настройки, а отвергнутый сертификат сообщается отдельно от прочих сбоев TLS.
   - Тело ответа ограничено 16 МиБ до разбора, страница — 100 выпусками, выпуск — 1000 assets. Клиент запрашивает `Accept-Encoding: identity` и отклоняет сжатые тела. Токен необязателен, передаётся вызывающим кодом (из файла или переменной окружения) и никогда не появляется в журналах, выводе `Debug`, URL или ключах кэша.
   - Ответы обрабатываются по пункту 3 ADR-019: десериализуются только используемые поля, неизвестные поля допускаются, отсутствующее или неверно типизированное обязательное поле — ошибка, ID и размеры — целые числа.
9. Нет аттестации/проблемы repo ID/файл изменился → `held`/`rejected`, событие журнала, не публикация.
