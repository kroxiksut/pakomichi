> **Состояние:** исходный комплект требований и минимальный нефункциональный каркас Rust-репозитория для проектирования и разработки 0.1 alpha, 18.10.2026. Pakomichi — согласованное название проекта. Основная команда CLI — `pchi`; `pakomichi` — её полный алиас.

Pakomichi позволяет подключить **конкретный Git-репозиторий**, публикующий готовые `.deb` / `.rpm` в Releases, и предоставить выбранные проверенные пакеты через локальные репозитории APT/DNF. Пользователь продолжает пользоваться `apt install`, `apt upgrade`, `dnf install`, `dnf upgrade`; Pakomichi не реализует собственный разрешитель системных зависимостей.

**Для кого:** пользователь Linux, нашедший готовый пакет в Git Releases, но не получивший удобного репозитория обновлений; разработчик, не желающий отдельно обслуживать APT/RPM-индексы; администратор нескольких машин (в дальнейшем).

## Ключевые правила

1. **Один источник — один закреплённый репозиторий с постоянным ID.** Не искать другие проекты автора, форки, одноимённые пакеты и зеркала для обновления.
2. **Один Git-репозиторий может выпускать несколько системных пакетов** (например, основную программу, CLI, службу, общий компонент), в том числе одним CI. Разрешённые наборы фиксируются явно.
3. **Не доставлять системные библиотеки из иных Git-проектов.** Зависимости обычным порядком разрешает APT/DNF из существующих источников ОС; опасную частичную миграцию системы не инициируем.
4. **Не вытеснять системные репозитории автоматически.** Сначала обнаружение конфликта, потом выбор пользователя. Одинаковая версия с разными файлами не является безопасно разрешённым переключением источника.
5. **Проверять происхождение и точные байты.** Режимы Strict/Attested, проверка привязки к репозиторию, SHA-256 и неизменяемая история принятых артефактов приняты как часть проекта. Уровень происхождения источника никогда не понижается молча. Источник без криптографического происхождения (Pinned) допускается только после явного согласия для этого источника и ручного подтверждения каждого релиза и никогда не вытесняет пакет дистрибутива.
6. **Подписанные локальные индексы, атомарные снимки и неизменяемые URL файлов.** В системе не хранится доверие только к `localhost`.
7. **Установленное ПО остаётся после удаления Pakomichi.** Обновление через мост при этом прекращается.

## Чем Pakomichi отличается

Pakomichi — не новый формат пакетов и не магазин приложений. Он задуман, чтобы превращать Releases одного выбранного вами репозитория в обычный источник обновлений для APT или DNF.

| Если вам нужно… | Лучше подойдёт | Чем отличается Pakomichi |
|---|---|---|
| Готовый каталог популярных программ | `deb-get` | Каталога нет: вы подключаете именно тот репозиторий, которому доверяете, а его обновления приходят обычным `apt upgrade` или `dnf upgrade`, без отдельной команды |
| Один бинарник в `~/.local/bin` | `eget`, `aqua` | Нативные `.deb`/`.rpm`: пакетный менеджер знает файлы, зависимости и умеет удалять |
| Изолированные приложения, не зависящие от дистрибутива | Flatpak, AppImage | Нативный пакет издателя с зависимостями из вашего дистрибутива |
| У издателя уже есть свой репозиторий | PPA, COPR, OBS, репозиторий издателя | Используйте его; Pakomichi — для проектов, которые публикуют пакеты только в Releases |

В отличие от ручного скачивания пакета, Pakomichi задуман так, чтобы:

- закреплять источник по постоянному ID репозитория: переименованный, переданный или пересозданный репозиторий не сможет незаметно занять его место;
- проверять каждый файл по криптографическому доказательству происхождения и точному SHA-256 и никогда не принимать подменённый файл;
- не заменять системные библиотеки и пакеты дистрибутива без вашего решения;
- оставлять установленные программы, если удалить сам Pakomichi.

## Пример сценария (предлагаемый CLI, ещё не реализован)

```bash
pchi source add https://github.com/matthart1983/netwatch
pchi source list
pchi source inspect <source-id>
pchi source activate <source-id> --packages netwatch
pchi sync
sudo apt update
sudo apt install netwatch
```

`pchi` — основная команда в документации и интерактивных примерах. `pakomichi` — полная команда с тем же CLI: например, `pakomichi status` и `pchi status` равнозначны. Текущий документационный комплект не реализует ни одну из этих команд.

## Статус проекта

Концепция, Rust как язык реализации и начальный операционный стек согласованы. Rust 1.94.1 зафиксирован в [ADR-015](docs/ru/decisions/ADR-015.md); [ADR-017](docs/ru/decisions/ADR-017.md) определяет ограниченный Tokio runtime сетевого процесса, синхронные/процессные границы и путь нативной упаковки на основании [прототипа P0-004](docs/ru/prototypes/P0-004-stack.md). Репозиторий всё ещё не реализует продуктовые функции. Исследования R-001, R-002, R-004, R-005 и R-006 завершены и отражены в ADR-021…ADR-027; R-003 (происхождение GitHub) завершён только в части read-only. Ни один дистрибутив пока не поддерживается: ADR-026 перечисляет первые цели и то, чего каждой из них ещё не хватает. Не представлять архитектуру как реализованную. GitHub — первый адаптер; GitLab, Forgejo, Gitea позже. WinGet — исследовательское направление, не блокирует Linux alpha. GUI не планируется в 0.1.

## Разработка

Установите зафиксированный в `rust-toolchain.toml` Rust, Python 3, PowerShell (7 или Windows PowerShell 5.1) и `cargo-deny` 0.19.0. Запустите тот же quality gate, который выполняет CI:

```powershell
cargo install cargo-deny --version 0.19.0 --locked
./scripts/quality.ps1
```

Gate проверяет распространённые сигнатуры секретов, форматирование, предупреждения Clippy, все тесты workspace, миграции SQLite, уязвимости зависимостей, лицензии и источники зависимостей. Эксперименты с пакетными менеджерами и сетью по-прежнему разрешены только в изолированных средах, описанных в [docs/ru/process/test-environments.md](docs/ru/process/test-environments.md).
